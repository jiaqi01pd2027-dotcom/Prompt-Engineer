Scope (in): a usage dashboard page in the existing web app showing each account's current-billing-period usage against plan limits (e.g. API calls, storage, seats — whatever is already metered for billing), as summary numbers plus a simple trend chart, refreshed at least once daily.

Non-goals: real-time/live counters, usage alerts or forecasting, cross-account or org-level rollups, exportable/downloadable reports, history beyond 12 months, self-serve plan upgrades from the dashboard.

Assumptions and open questions: (assumption) the metrics shown are the same ones already computed for billing, not new product-analytics instrumentation; (assumption) a daily batch rollup is fresh enough — no streaming pipeline needed; (question) is this one dashboard layout for all plans, or do metrics differ enough by plan type to need variants; (question) do customers need a per-seat/per-user breakdown or is an account-level total sufficient; (question) what happens to the "vs. limit" line when a plan changes mid-period — does billing already handle proration we can reuse?

Milestones: 1. confirm metrics and source of truth, build the daily aggregation/rollup job, 1 week. 2. usage API endpoint serving aggregated data per account and period, 3-4 days. 3. dashboard UI — summary cards and trend chart, including zero-usage and new-account empty states, 1 week. 4. reconcile numbers against actual bills, handle mid-period plan-change edge case, and release, 4 days.

Risks: dashboard numbers disagree with the actual invoice, eroding trust — reuse billing's own aggregation logic and reconcile the two before release, not after a support ticket. Large accounts with many metrics make the page slow — serve from precomputed daily rollups, never query raw usage events live on page load. A plan change mid-period makes "usage vs. limit" ambiguous — either prorate the limit line or visually split the chart at the change date; decide before milestone 3, not during QA. Customers with genuinely zero usage see what looks like a broken chart — design and test the empty state explicitly rather than letting it fall out of the trend-chart component by accident.
