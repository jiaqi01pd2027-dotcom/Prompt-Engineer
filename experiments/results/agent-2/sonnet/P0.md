Since the brief ("we want a dashboard so customers can see their usage") is short on specifics, I treated this as a discovery-stage plan rather than assuming a stack. Key points:

- **The one thing that has to happen first:** "usage" isn't defined yet — API calls, seats, storage, compute-minutes? Whatever unit(s) apply drive the data model, the limits, and the UI. That's Phase 1, not an afterthought.
- **Scope split** — MVP (current-period usage vs. limit, trend chart, breakdown, near-limit indicator, CSV export) vs. Phase 2 (alerts, forecasting, org rollup, a usage API, longer retention).
- **Architecture**: don't query raw events live — aggregate into account × unit × day rows on ingest, so the dashboard stays fast regardless of history depth. Usage has to reset on each customer's own billing anchor date, not a shared calendar month.
- **Biggest risks flagged as critical**: the metering data itself being wrong at the source (dashboard just exposes the mess), and cross-tenant leakage in aggregation/API queries — usage data is exactly the kind of thing that leaks across accounts in a rushed build.
- **Rough timeline**: 7–9 weeks across 5 phases, with the Phase 1 data audit being what actually moves that number.
- **5 open questions** that block a real timeline: the metered unit(s), where plan limits currently live, real-time vs. daily-batch freshness, per-seat vs. org-level granularity, and any retention/export compliance constraint.

The artifact includes an illustrative mockup (placeholder numbers, clearly marked) of what the MVP overview could look like, plus tables for the timeline, risks, and access model.

Next useful step would be to actually answer those five open questions with whoever owns billing/metering today — that's what turns this from a plan into a real schedule.
