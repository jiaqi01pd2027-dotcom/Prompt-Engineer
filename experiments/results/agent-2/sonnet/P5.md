**Scope (in)**
- Single dashboard page showing current billing-period usage (e.g., API calls, seats, storage, or the account's primary metered unit)
- Usage broken out by day/week over the current and prior billing period, shown as a simple time-series chart
- Summary tiles for key totals (current usage, plan limit, % consumed)
- Per-customer/account scoping with existing auth — a user sees only their own org's usage
- CSV export of the displayed usage data
- Read-only view; data refreshed at least daily (near-real-time is a stretch goal, not required for v1)
- Basic empty/loading/error states

**Non-goals**
- Real-time (sub-hour) usage streaming
- Usage-based alerting or notification rules
- Historical usage beyond the two periods described above (e.g., 12-month trends)
- Team/role-based views (multiple dashboards per seat, admin vs. member views)
- Self-serve plan changes or upgrade/downgrade flows triggered from the dashboard
- Cost/billing forecasting or anomaly detection
- White-labeling or embedding the dashboard in third-party sites

**Assumptions and open questions**
- (assumption) Usage data already exists in a queryable form (a metering/billing pipeline or event log) and does not need to be built from scratch
- (assumption) "Usage" refers to a single well-defined metric per product; multi-metric products will need this scoped per metric
- (assumption) Existing customer auth/session system can be reused for access control; no new auth work is required
- (question) What is the source of truth for usage data — a data warehouse, the billing provider (e.g., Stripe), or an internal service — and what is its query latency?
- (question) Does "usage" mean one metric or several (e.g., API calls AND storage AND seats)? This changes scope significantly
- (question) Is there an existing design system/component library to build against, or does this need new UI components?
- (question) What billing period definition applies (calendar month vs. anniversary billing)?
- (question) Do customers need to see usage for sub-accounts/multiple environments, or is it one usage stream per account?

**Milestones**

| # | Milestone | Deliverable | Size (days or weeks) |
|---|-----------|-------------|----------------------|
| 1 | Data access spike | Confirmed source of truth, query pattern, and latency for usage data; sample data pulled into a script/notebook | 2-3 days |
| 2 | API layer | Backend endpoint(s) returning scoped, time-bucketed usage for the authenticated account | 1 week |
| 3 | Dashboard UI (static) | Summary tiles + chart + table rendered from mocked/API data, responsive layout | 1 week |
| 4 | Wire-up and auth scoping | UI connected to live API, per-account access control verified, loading/error/empty states | 3-4 days |
| 5 | CSV export | Export button producing a correctly formatted CSV of the visible data | 1-2 days |
| 6 | QA, edge cases, launch | Zero-usage accounts, mid-period signups, timezone/period-boundary correctness, staged rollout | 3-5 days |

**Risks**
- Usage data source is slower or less structured than assumed, forcing a new aggregation pipeline: spike on data access (Milestone 1) before committing to the API design
- Ambiguity over which metric(s) count as "usage" causes scope creep mid-build: lock the metric definition with product/stakeholders before Milestone 2 starts
- Billing-period boundaries (timezone, mid-cycle plan changes) produce incorrect totals that erode customer trust: write explicit test cases for period-boundary and plan-change scenarios in QA
- Large accounts with high-cardinality usage data slow down the dashboard or export: cap default query range and paginate/stream the CSV export rather than loading all rows at once
- Customers expect real-time data but v1 only refreshes daily, causing support tickets: state refresh cadence explicitly in the UI (e.g., "as of 6:00 AM UTC") to set expectations
