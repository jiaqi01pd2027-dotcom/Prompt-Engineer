**Usage Dashboard Plan**: https://claude.ai/code/artifact/282ed81a-5878-48b6-a1ab-cb4271701168

The plan is scoped tightly around the one-sentence brief, treating everything not stated as either an explicit assumption or a question for the PM rather than filling it in silently.

Structure:
- **Assumptions** (6): what "usage" likely means, self-serve/account-scoped, daily refresh is fine, ~90-day trailing window, small team sizing basis, etc.
- **Open questions for PM** (6): the metric(s) themselves, whether a metering pipeline already exists, whether this ties to plan limits/overage, audience/roles, time granularity, existing design system.
- **Non-goals**: no billing/upgrade changes, no alerts, no export, no forecasting, no internal analytics, no backfill, no white-labeling.
- **Milestones** (M1–M7, ~29 engineer-days / 5–6 elapsed weeks for a small team): discovery & data audit → usage API contract → aggregation & caching → dashboard UI → auth/account scoping → QA/edge states → beta rollout. Rendered as a proportional timeline bar plus a detail table, with a callout flagging that M2/M3 could blow up if no metering pipeline exists yet.
- **Risks** (4, each with a specific mitigation, not generic): no existing data foundation → gate the schedule on the M1 discovery outcome; ambiguous metric definition → PM/support sign-off before UI work starts; cost/performance of live queries at scale → build on pre-aggregated rollups and load-test; cross-account data leakage → enforce scoping at the query layer with an explicit isolation test, not just UI hiding.

It's a single v1 plan — no phase 2 proposed — and closes with a note that the PM questions should be resolved before M2 starts, since several size estimates depend on the answers.
