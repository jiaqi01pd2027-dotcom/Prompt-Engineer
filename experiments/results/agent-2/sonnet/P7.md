## Reasoning

**What the brief doesn't say, and which gaps matter most:**

- *What "usage" means* — which metric(s), for which product surface. This is the single biggest unknown: it determines the whole data model.
- *Where usage data currently lives* — is there already an events/metrics pipeline or billing system to read from, or does one need to be built? This decides whether this is a 2-week frontend project or a multi-month data engineering project wearing a dashboard's clothes.
- *Real-time vs periodic* — "see their usage" doesn't imply live updates. Assuming batch/periodic unless told otherwise avoids building streaming infra nobody asked for.
- *Auth/tenancy model* — does customer login and account-to-usage mapping already exist? If not, that's its own project.
- *Who asked for this and why* — support deflection, sales requirement, or compliance changes what "done" looks like, but isn't specified.

**Smallest version that satisfies the sentence:** one page, behind existing customer login, showing a small fixed set of usage numbers/charts for the current billing period, updated on a schedule (e.g. hourly/daily job), sourced from whatever system of record already tracks usage.

**Explicitly out of scope for v1:** historical trend charts, custom date ranges, CSV/PDF export, threshold alerts, an internal/admin view across all customers, multi-user roles within one account, white-labeling, real-time streaming, and cost/billing projections. Each is a legitimate v2 ask but none is required by the brief as written.

**Where this is most likely to slip:** not the UI — the data source. If usage isn't already captured in a clean, queryable form, "build a dashboard" quietly becomes "design a usage-tracking pipeline, backfill it, then build a dashboard," which is a different project with a different timeline. The second most likely slip is scope creep once stakeholders see the first mock and start asking for trends/exports/alerts mid-build.

## Plan: Customer Usage Dashboard (v1)

**Goal:** Logged-in customers can see their own current-period usage on one page. Nothing more.

### Milestone 0 — Scoping spike (before estimating the rest)
- Confirm: which metric(s) count as "usage," and pull one real example number by hand.
- Confirm: source of truth for that metric (existing table/pipeline vs. needs building).
- Confirm: refresh cadence is periodic (not real-time) unless stated otherwise.
- **Exit criteria:** a one-paragraph data-source answer signed off by an engineer who's queried it.

### Milestone 1 — Data availability
- If usage data exists: build a read-only aggregation query/materialized view per account for the current period.
- If it doesn't: this milestone becomes "define and start capturing the metric" — treat as a separate, larger project and re-scope the timeline before proceeding.
- **Exit criteria:** for a handful of test accounts, the aggregated number matches manual calculation.

### Milestone 2 — API
- One endpoint: `GET /accounts/{id}/usage` returning current-period totals for the authenticated account only.
- Reuses existing auth; no new tenancy logic.
- **Exit criteria:** endpoint enforces "own account only," has a basic rate limit, returns in <1s for a typical account.

### Milestone 3 — UI
- One page, one or two charts/numbers, loading/empty/error states.
- No date picker, no export button, no comparisons.
- **Exit criteria:** a customer with zero usage and a customer with heavy usage both render sensibly.

### Milestone 4 — Ship
- Feature-flagged rollout to a small customer cohort, then everyone.
- Basic dashboard/alert on the aggregation job (did it run, did it error).
- **Exit criteria:** one week of successful scheduled refreshes with no data discrepancies reported.

### Risks
| Risk | Why it matters | Mitigation |
|---|---|---|
| Usage data isn't cleanly captured today | Turns this into a data-pipeline project; timeline could 3-5x | Resolve in Milestone 0 before committing dates |
| "Usage" means different things to different stakeholders | Rework after build starts | Get one written definition + example number signed off before Milestone 1 |
| Stakeholders ask for trends/export/alerts mid-build | Scope creep, missed date | Explicitly list these as v2 in the kickoff doc; park requests in a backlog |
| Aggregation query is slow/expensive at scale | Page times out or costs spike as customer count grows | Load-test with realistic account count in Milestone 1, not after launch |
| Auth/tenancy edge cases (multiple users per account, impersonation) | Wrong customer sees wrong data — a trust-breaking bug | Explicit test cases for shared accounts and support-impersonation flows before ship |
