Here's the plan, in brief:

**Framing.** The one-liner brief hides several product decisions, so the plan surfaces them as explicit assumptions to confirm before anyone commits dates: one primary usage metric in v1 (not a metrics builder), events already recorded somewhere, daily refresh is fine, read-only (no limits/alerts).

**Scope.** In: current-period total, 90-day usage chart, per-account admin view, empty state, CSV export. Out: plan limits/quota bars, alerts, per-user/endpoint breakdowns, real-time refresh, multi-metric views.

**Milestones (≈6 weeks, 2 engineers):**
- M0 (1 wk) — data audit & rollup design: confirm the metric is actually reliably tracked before estimating the rest
- M1 (1.5 wk) — nightly rollup job + usage API (current total, time series)
- M2 (2 wk) — dashboard UI: tile, chart, date range, empty/loading states, export
- M3 (1.5 wk) — backfill, load-test on largest accounts, staged rollout

**Risks flagged:** unreliable usage tracking today (high — why M0 exists), no agreed cross-plan definition of "usage" (high — needs a product call before M1), rollup query performance at scale, backfill drift vs. billing records, scope creep toward limits/alerts.

**Open questions for the meeting:** which metric ships first, whether daily refresh is actually acceptable, backfill window, and whether dashboard numbers need to reconcile exactly with invoices.
