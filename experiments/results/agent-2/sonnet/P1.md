# Usage Dashboard — Implementation Plan (v1)

## Scope

**In scope (v1):**
- A single "Usage" page in the customer-facing app showing per-account usage against plan limits (e.g., API calls, storage, seats — whichever meters already exist in billing/metering).
- Current billing-period totals + a simple time-series chart (daily/monthly granularity).
- Breakdown by the 1–2 dimensions we already track cleanly (e.g., by product/feature or by API key), not arbitrary custom breakdowns.
- Data refreshed on a delay (e.g., hourly/nightly), not real-time.

**Explicitly out of scope for v1** (flag as fast-follow):
- Real-time/streaming usage.
- Exportable reports, alerts/threshold notifications, usage forecasting.
- Team-level or role-based views (assume one view per account/org for now).
- Self-serve plan changes triggered from the dashboard.

*Why this scope:* the brief is one sentence — we're choosing the smallest slice that gives customers real visibility without committing to infra we haven't validated (streaming pipelines, notification rules, etc.).

## Milestones

| # | Milestone | Description | Rough estimate |
|---|-----------|-------------|-----------------|
| 1 | **Data contract** | Agree on what "usage" means per plan/product; confirm source of truth (metering service, billing system, or raw event logs) and aggregation grain | 1 week |
| 2 | **Backend: usage API** | Read-only endpoint(s) serving aggregated usage per account, period, and dimension; caching/precomputation as needed | 1–2 weeks |
| 3 | **Frontend: dashboard UI** | Usage page with summary stat(s), time-series chart, and breakdown table; empty/loading/error states | 1–2 weeks |
| 4 | **Internal beta** | Ship behind a flag to internal accounts + a few friendly customers; validate numbers against billing | 1 week |
| 5 | **GA rollout** | Fix discrepancies, add basic monitoring/alerting on the pipeline, roll out to all customers | 1 week |

Total: roughly 5–7 weeks depending on how much aggregation infra already exists (Milestone 1 can shrink this a lot or blow it up).

## Key open questions (resolve before estimating further)

1. Does a metering/aggregation pipeline already exist, or does this require building one from raw events?
2. What counts as "usage" — is it one metric or several across products?
3. What's the acceptable data lag (real-time vs. daily)?
4. Do numbers need to reconcile exactly with billing invoices, or is "close enough for visibility" okay?

## Risks

- **Data accuracy mismatch with billing** — if the dashboard and the invoice disagree, it erodes trust fast. Mitigate by sourcing from the same system billing uses, and reconciling in beta before GA.
- **No existing aggregation layer** — if usage must be computed from raw event logs, backend effort could balloon well past the estimate above. Needs to be confirmed in Milestone 1 before committing dates externally.
- **Ambiguous "usage" definition** — different products may meter different things; scope creep risk if we try to unify them all in v1. Push multi-metric support to fast-follow.
- **Performance on historical queries** — computing time-series on demand for high-usage accounts could be slow; may need precomputed rollups sooner than planned.
- **Underspecified brief** — the one-line brief has no target customer segment, success metric, or plan-limit context. Recommend a 30-minute scoping conversation with product before Milestone 2 starts, to avoid rework.
