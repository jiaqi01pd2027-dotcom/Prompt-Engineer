# Usage Dashboard — V1 Implementation Plan

**Scope:** Self-serve usage dashboard behind existing login. Current-month usage vs. plan limit, 6-month trend, CSV export, one 80%-threshold email alert. No billing display, no per-user breakdown, no public API, no mobile, no custom date ranges.

**Team:** 1 backend + 1 frontend engineer, 6 weeks; designer for week 1. No new infra.

**Key dates:** Pilot (20 accounts) by **Oct 19**; full rollout to all ~1,200 accounts by **Nov 2** (pricing change).

**Open dependency to confirm day one:** where "plan limit per metric" is sourced from (accounts/plans config table, presumably existing since billing already enforces limits). Nothing below works without this — resolve before backend work starts.

## Risks

1. **Plan-limit source undefined in the brief.** Highest-priority unknown; blocks the core "usage vs. limit" feature. Confirm in week 1.
2. **6-month backfill cost unknown.** No rollup table exists yet, so the first backfill reads potentially months of raw `usage_events` for ~1,200 accounts. Test this in week 1–2, not week 5, in case it needs batching or a longer runway.
3. **Account isolation.** An admin seeing another account's usage is a data-leak, not a bug. Needs explicit, first-class test coverage, not incidental QA.
4. **Alert duplication/spam.** Usage can hover around the 80% line across days; the job needs "fire once per account/metric/period" logic or admins get repeat emails.
5. **"Current month" boundary ambiguity.** Pipeline runs in UTC; decide once whether month/day boundaries are UTC-based and document it, so numbers don't look wrong to admins in other timezones.
6. **Timeline is tight for the scope.** Rollup pipeline + 2 chart views + CSV + email alerting + auth integration in 6 weeks with 2 engineers and a hard external deadline (pricing change) leaves little slack. Recommend a week-3 checkpoint: if behind, the CSV export or the email alert (not the core usage view) is the candidate to push past Nov 2.
7. **"No new infra spend" constraint.** Confirm the nightly job can run on existing scheduler/cron infra and the email alert can ride the existing mail service — don't discover a new queue/worker is "needed" in week 4.
8. **Designer bandwidth ends after week 1.** Any design iteration after that is absorbed by the frontend engineer under deadline pressure — expect the UI to stay close to the week-1 wireframes.
