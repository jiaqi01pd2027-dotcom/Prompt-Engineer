## What's in it

**Calendar.** Kickoff Mon 14 Sep → six weeks end Fri 23 Oct. Pilot to 20 accounts Mon 19 Oct (start of W6, not the end), GA Mon 2 Nov. That leaves exactly one buffer week, which the plan names as the only slack.

**Build approach (five decisions).**
- One nightly rollup table `usage_monthly` at 03:30 UTC, recomputing current + previous month; the dashboard never queries `usage_events`.
- A `/usage` route in the existing app; `account_id` comes from the session only.
- Alerts are step two of the same nightly job; a `usage_alerts_sent` table enforces one email per metric per month.
- Plan limits read from wherever billing keeps them, with a date-effective `plan_limits` fallback table because limits change on 2 Nov.
- Per-account feature flag gates both the page and the alerts for the pilot.

**Milestones.** One row per week with backend / frontend work and a concrete "done when" (e.g. W2: job has run three nights on staging; W4: a staging account crossing 80% gets exactly one email and none the next night; W5: scope freeze and go/no-go).

**Scope-cut order, decided now.** If behind at end of W3: pilot ships without alerts, then CSV, then trend depth.

**Eight risks with mitigations.** Three rated high: plan limits not queryable / not matching what billing enforces; the 2 Nov pricing change landing the same day as GA; and cross-account data leakage.

**Five open questions for the PM** to close before kickoff. The most important one the brief didn't answer: *where do plan limits actually live?* "Usage against the plan limit" is the headline feature and there is no data source named for the limit side of it.

One judgment call worth flagging in the meeting: I treated "this month" as a UTC calendar month. If billing uses a different boundary, the numbers will disagree with invoices and that's question 5.
