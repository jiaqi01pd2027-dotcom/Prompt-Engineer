What's in it (one screen-length per section, built to be read in a meeting):

- **What we're building** — a page where an account admin sees period-to-date consumption per metered resource against plan limits, with recent-period trend. The governing constraint: the number on the page equals the number on the invoice.
- **Assumptions A1–A4** — since the brief is one sentence, the plan states what it's resting on (usage = the quantities we already bill on; audience = account admins; billing event stream is the source of truth; web only) so the meeting can confirm or overturn each by label.
- **Scope** — in/out split, with a reason attached to every exclusion (alerts, cost projection, real-time, custom views, public API).
- **Shape of the system** — one architectural call worth discussing: hourly rollups into a `usage_rollups` table rather than querying raw billing events on page load, which also makes the reconciliation test possible.
- **Milestones M0–M5**, 8 weeks, 2.5 engineers — scope lock, data foundation with backfill, read API, page, beta, GA. Each has a checkable exit criterion (e.g. rollups match invoiced quantities within 0.5% in CI; p95 under 500 ms on the five largest accounts).
- **Risks** ranked by severity — invoice mismatch and large-account query cost are the two Highs; each has a concrete mitigation tied to a milestone.
- **Open questions Q1–Q5** — resource list, non-admin access, history window, parent/child accounts, glossary ownership.
