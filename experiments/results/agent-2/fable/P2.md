# Customer Usage Dashboard — v1 Implementation Plan

## Goal
Give customers a self-serve view of what they've consumed on their plan, so they stop asking support "how much have I used?" and can anticipate overages before they happen.

## Assumptions (confirm before estimating)
The brief is one line, so these are my calls. Push back on any of them.

1. **"Usage" = the metered quantities we bill on** (e.g. API calls, storage GB, seats). Not product analytics, not audit logs.
2. **Audience is the account admin/owner**, viewing their own organization only.
3. **Source of truth is the billing/metering pipeline** that already exists for invoicing. We are not building new metering.
4. **Web app only**, inside the existing authenticated customer console. No public API, no mobile.
5. **Near-real-time is not required.** Data up to ~1 hour stale is acceptable for v1.

## Scope

**In v1**
- Current billing period: usage to date per metered dimension, plan limit, % consumed
- Daily usage over the current period (line/bar chart per dimension)
- Previous periods selectable (last 6)
- CSV export of the daily series
- Empty and error states; loading under 2s at p95 for accounts with 90 days of data

**Explicitly out (v2 candidates)**
- Usage alerts / threshold notifications
- Breakdown by sub-entity (API key, project, user)
- Cost projection or "estimated bill"
- Real-time streaming updates
- Embeddable widgets or a public usage API

## Milestones

| # | Milestone | Deliverable | Owner | Rough size |
|---|-----------|-------------|-------|-----------|
| 0 | **Data audit** | Written answer: which tables/events hold usage, their latency, granularity, and retention. Sign-off on assumption #3. | Backend | 2–3 days |
| 1 | **Aggregation layer** | Nightly/hourly job rolling raw metering into a `usage_daily(org, dimension, date, qty)` table. Backfilled 6 periods. | Backend | 1 wk |
| 2 | **Read API** | `GET /orgs/{id}/usage?period=…` returning per-dimension totals, limits, and daily series. Authz scoped to org admins. | Backend | 1 wk |
| 3 | **Dashboard UI** | Page behind a feature flag: summary tiles + chart + period selector + CSV export. Design handoff assumed available by end of M1. | Frontend | 1.5 wk |
| 4 | **Reconciliation** | Dashboard totals match invoiced totals for last 2 closed periods across a sample of 20 accounts. Discrepancies triaged. | Backend + Finance | 3 days |
| 5 | **Beta → GA** | Flag on for 10 friendly accounts, 1 week soak, then all accounts. Support macro updated. | PM + Support | 1.5 wk |

Milestones 1–2 and 3 can run in parallel once the API contract is agreed (mock it in week 1). Total: ~5–6 weeks calendar with 1 backend + 1 frontend engineer.

## Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|-----------|
| **Dashboard disagrees with the invoice.** Customers will open disputes the first time the numbers differ. | High | High | M4 is a hard gate to GA. Use the same aggregation logic billing uses, or read from billing's output rather than re-deriving. |
| **Metering data isn't queryable at daily granularity** (only per-invoice totals, or raw events too large to scan). | Medium | High | M0 exists to find this out early. Fallback: v1 ships period totals only, no chart. |
| **Slow queries for large accounts** blow the 2s budget. | Medium | Medium | Pre-aggregate (M1); never query raw events from the request path. Cap history at 6 periods. |
| **Plan limits aren't stored in one place** (spread across billing, config, contracts). | Medium | Medium | Ship "usage" without "% of limit" if limits aren't reliable; add later. |
| **Scope creep toward alerts and cost projection** because they're "obviously" next. | High | Low–Med | Out-of-scope list above; PM owns the line. |
| **Authz bug exposes another org's usage.** | Low | Very high | Org scoping enforced in the API layer, not the UI; add a negative test in CI. |

## Success criteria (30 days post-GA)
- Support tickets tagged "usage inquiry" down 40%
- ≥25% of active admin accounts view the page at least once
- Zero billing disputes attributable to dashboard/invoice mismatch
