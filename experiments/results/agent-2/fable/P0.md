# Plan: Customer Usage Dashboard

## 0. Questions to settle before building (blocks everything below)

1. **What is "usage"?** API calls, tokens, seats, storage, minutes, events? Which 2–3 metrics do customers actually get billed on or capped by? Those are the headline numbers; everything else is secondary.
2. **Who is the customer?** Single user, or an org with many users (needs per-user/per-key breakdown and roles)?
3. **Where does usage data live today?** Billing system (Stripe/Metronome/Orb), an events table, logs, nothing? This decides whether the work is a UI project or a data-pipeline project.
4. **Freshness requirement:** near-real-time, hourly, or daily is fine? Daily is 10x cheaper to build.
5. **Does it need to reconcile with the invoice?** If yes, the dashboard must read from the same source as billing, not a parallel aggregation.
6. **Plan limits and alerts:** should it show quota remaining and warn at thresholds, or just report history?

## 1. Scope (v1)

In:
- Current billing period: usage to date, plan limit, % consumed, projected end-of-period.
- Time series (daily) for the trailing 30/90 days, selectable range.
- Breakdown by one dimension (product/feature, API key, or user, whichever Q2 dictates).
- CSV export of the underlying rows.
- Link to plan/upgrade page.

Out (v2 candidates): custom date ranges beyond 90d, per-minute granularity, cost forecasting, usage alerts via email, embeddable widgets.

## 2. Architecture

```
events (raw) --> aggregation job --> usage_daily (rollup table) --> Usage API --> Dashboard UI
                      |
                      +--> billing (must agree with rollups)
```

- **Raw events:** append-only, keyed by `customer_id`, `metric`, `timestamp`, `quantity`, plus one breakdown dimension. If this doesn't exist yet, this is phase 1.
- **Rollup table `usage_daily`:** `(customer_id, metric, dimension, day, quantity)`. Precomputed so the UI never scans raw events. Backfill once; then an hourly/daily incremental job.
- **Usage API:** `GET /usage/summary` (current period vs limit), `GET /usage/series?metric=&from=&to=&group_by=`, `GET /usage/export.csv`. Tenant-scoped via the customer's auth; never accept `customer_id` from the client.
- **UI:** one page in the existing customer portal (or a standalone page if there is none). Summary tiles on top, one time-series chart, one breakdown table, export button.

## 3. Phases

| Phase | Work | Exit criteria |
|---|---|---|
| 1. Data foundation | Confirm event source; create `usage_daily`; backfill 90 days; incremental job; reconciliation check against billing | Rollups match invoices for 3 sample customers within 0.1% |
| 2. API | Three endpoints above; auth scoping; pagination on export; rate limits | Integration tests per endpoint, including cross-tenant access denial |
| 3. UI | Summary tiles, chart, breakdown table, range picker, export | Loads under 1s on a customer with 90 days of data; renders empty and partial-period states correctly |
| 4. Hardening and launch | Feature flag; internal dogfood; docs/help text explaining how usage is counted; monitoring on the aggregation job | Beta with 5–10 customers, then general rollout |

Rough sizing (one engineer, data source already exists): 1 week / 1 week / 1.5 weeks / 0.5 week. If raw events don't exist yet, add 2–3 weeks to phase 1.

## 4. Risks

- **Numbers don't match the bill.** The single biggest source of support tickets for usage dashboards. Mitigate by reading from the billing source of truth, or reconciling nightly and alerting on drift.
- **Timezone and period boundaries.** Define the billing day in UTC (or the customer's billing timezone) and state it in the UI.
- **Late-arriving events.** Rollup job must re-aggregate the last 2–3 days, not just "today."
- **Tenant leakage.** Scope every query by the authenticated customer; test it explicitly.
- **Slow queries on big customers.** Rollups solve this; don't ship a UI that queries raw events.

## 5. Success metrics

- Fewer "how much have I used?" support tickets (baseline the current count first).
- % of active customers who open the dashboard at least once per billing period.
- Zero reconciliation-drift alerts over the first month.
