## Scope (in)

- A "Usage" page inside the existing web app, reachable only through the existing session login. Every query takes `account_id` from the server-side session; an admin can never see another account.
- Current-month section: for each metric in `usage_events`, month-to-date quantity, the account's plan limit, and percent of limit used. Month = UTC calendar month.
- Trend section: for each metric, one monthly total for each of the six full months before the current one, plus the current month to date (seven data points). Fixed window, no date picker.
- CSV download button that returns exactly the numbers shown on the page: columns `month, metric, quantity, limit`.
- A new Postgres table `usage_monthly_rollups (account_id, metric, month, quantity, computed_at)` in the existing database, filled by a daily job that runs after the billing pipeline (04:00 UTC), recomputes the current month, and backfills the six prior months on first run. The page reads only this table, never `usage_events` directly.
- One email alert, sent to the account admin, the first time a metric reaches 80% of its plan limit in a given month. Sent at most once per account, per metric, per month, tracked in an `usage_alerts_sent` table. Evaluated by the daily job, so the alert arrives the day after the threshold is crossed.
- "Updated <date> UTC" label on the page, taken from the last successful rollup.
- Per-account feature flag: on for 20 pilot accounts from October 12, on for all ~1,200 paid accounts at general availability on October 22.
- Designer deliverables in week 1: page mockup (both sections, empty state, error state), the alert email, and plain-language copy for a non-technical admin.

## Non-goals

Per the PM's list (answer 8):
- No billing or invoice display.
- No per-user breakdown within an account.
- No public API. The read endpoints are internal to the web app and session-authenticated only.
- No mobile app. The page is desktop web; it is not designed or tested for mobile.
- No custom date ranges.

Also excluded, from answers 3 and 7:
- No real-time or intra-day refresh; data is daily.
- No notification other than the 80% email (no 100% email, no in-app banner, no weekly digest).

## Risks

- Plan limits have no known home in the data model, and the whole page compares against them: resolve the source by September 16 in milestone 1; if none exists, backend adds a `plan_limits` table seeded by the PM the same week, so nothing downstream slips.
- `usage_events` may be large enough that a daily full scan is slow or contends with the billing pipeline: the job reads only, runs at 04:00 UTC after the pipeline, recomputes only the current month after backfill, and its runtime is measured against a production-size copy in week 2 before anything depends on it.
- Wrong or duplicate 80% emails would land with non-technical admins and are hard to take back: the sent ledger enforces once per account, metric, and month; it is pre-seeded on backfill so no historical alerts fire; and the 20-account pilot runs the alert path for ten days before it reaches 1,200 accounts.
- The pipeline finishing late or failing after 03:00 UTC would show stale numbers or fire alerts on partial data: the job records its last successful run, the page shows "Updated <date> UTC" from that value, and the alert check only runs on a day whose rollup completed.
- The November 2 pricing change may change limits after the code is written: limits are read from the account's current plan at request time, never stored in the rollup, so a limit change on November 2 is reflected the same day with no deploy.
- The designer is available only in week 1, so UI changes discovered in pilot have no design support: mockups are signed off by September 18 including empty and error states, and post-pilot changes are limited to copy and data fixes unless the PM accepts an engineer-designed change.
