Scope (in)
- A "Usage" page in the existing customer web app, reachable from the main navigation, visible to any authenticated user of an account.
- Usage shown per account (the billing entity), aggregated across all of that account's users, keys, and projects.
- Metrics: the metered quantities the customer is billed on (e.g. API calls, storage, seats — confirm exact list, see questions), shown as (a) current billing-period total against plan limit and (b) a daily time series.
- Time range picker: current billing period (default), last 30 days, last 90 days.
- Simple CSV export of the daily series for the selected range.
- Backend: a usage aggregation job that rolls raw metering events into daily-per-account buckets, plus one read API that serves the page.
- Data freshness target: usage visible within one hour of occurrence.
- Basic analytics events (page viewed, export clicked) so we can tell whether anyone uses it.

Non-goals
- Real-time or streaming updates; sub-hour freshness.
- Per-user, per-API-key, or per-project breakdowns (data model should not preclude this, but no UI).
- Cost or invoice display, spend forecasting, or budget alerts.
- Configurable alerts, email digests, or notifications of any kind.
- Custom dashboards, saved views, or chart customization.
- Public API or webhooks for usage data (internal read API only).
- Admin/internal view of usage across customers.
- Backfill of usage history older than 90 days before launch.
- Mobile-specific layout beyond the app's existing responsive behavior.

Assumptions and open questions
- (assumption) Metering events already exist somewhere (billing pipeline, event log, or DB tables) and are reliable enough to be shown to customers. We are not building metering.
- (assumption) The existing web app has authentication, an account model, and a component/chart library we can reuse; no new frontend stack.
- (assumption) One engineer on backend, one on frontend, part-time design and PM review; sizes below assume that.
- (assumption) Numbers on the dashboard may differ slightly from the invoice; the page will carry a "may lag up to 1h, invoice is authoritative" note.
- (question) Exactly which metrics does "usage" mean, and which of them have a plan limit to show a bar against?
- (question) What is the source of truth for usage today, and what does the billing team consider the correct number when the two disagree?
- (question) Should every user on an account see usage, or only admin/billing roles?
- (question) Which customers get it first — all accounts, or a beta cohort behind a feature flag?
- (question) Is there a data-retention or compliance constraint on keeping daily per-account aggregates?

Milestones

| # | Milestone | Deliverable | Size |
|---|-----------|-------------|------|
| 1 | Definition | Answered questions above; metric list and plan-limit source confirmed; one-page wireframe signed off by PM and design | 1 week |
| 2 | Aggregation pipeline | Daily per-account usage table; scheduled job rolling up metering events hourly; reconciliation script comparing totals to billing for a sample of accounts | 2 weeks |
| 3 | Read API | Authenticated endpoint returning period totals, plan limits, and daily series for a date range; load-tested at expected request volume; unit and integration tests | 1 week |
| 4 | Usage page | Navigation entry, totals-vs-limit cards, daily chart, range picker, CSV export, empty/error/loading states; behind a feature flag | 2 weeks |
| 5 | Beta and hardening | Enabled for a beta cohort; analytics events verified; discrepancies from reconciliation resolved; support docs and a short internal FAQ | 1 week |
| 6 | General availability | Flag on for all accounts; monitoring and alert on aggregation job failure/lag; release note | 3 days |

Risks
- Usage numbers disagree with invoices and customers file billing disputes: reconcile against billing for sampled accounts before beta, label the page as non-authoritative, and route the aggregation off the same source billing uses.
- Metering data is incomplete or inconsistent across products, stalling milestone 2: milestone 1 audits the sources first; launch with only the metrics that reconcile cleanly and add the rest later.
- Aggregation job falls behind under load or on backfill, showing stale data: idempotent hourly job with a lag metric and alert; backfill limited to 90 days and run in batches.
- Scope grows into per-key breakdowns, alerts, and cost views: non-goals list is the contract for v1; new requests go into a v2 backlog and do not move milestone 6.
- Large accounts produce slow queries on the read API: pre-aggregated daily table keyed by account and date, indexed, with the range capped at 90 days.
