# Usage Dashboard v1 — Implementation Plan

**Goal:** Every paid account admin can see current-month usage per metric against their plan limit, a six-month trend, download monthly numbers as CSV, and get one email when they hit 80% of a limit. Live for 20 pilot accounts by **Oct 19**, all 1,200 accounts before the pricing change on **Nov 2**.

**Team:** 1 backend, 1 frontend for six weeks (Sept 14 – Oct 23); designer in week 1. No new infrastructure.

## Approach

- **Nightly rollup, not live queries.** A job runs at 04:00 UTC (after billing finishes at 03:00) and writes `usage_rollup_monthly (account_id, metric, month, quantity)`, recomputing the current and previous month so late-arriving events are absorbed. One-time backfill of the last six months. The dashboard reads only this table, so `usage_events` is never queried per page view.
- **Limits come from the existing plan data.** The API joins rollup rows to the account's plan limits per metric. (See open question 1.)
- **Alerts ride the same job.** After the rollup, compare current-month usage to limits; send one email per account/metric/month via the existing transactional email sender, recording sends in `usage_alerts_sent` so nothing repeats.
- **One page behind existing login.** Account ID comes from the session, never from the URL. Three read endpoints: current month, six-month trend, CSV export. Feature flag gates the page for the pilot.
- **Non-technical audience.** A metric catalog maps raw `metric` keys to plain-language labels and units; unknown metrics are hidden rather than shown raw.

## Milestones

| When | Milestone | Done means |
|---|---|---|
| Week 1 (Sept 14–18) | **Groundwork** | Designer delivers wireframe for the page and the alert email. Backend profiles `usage_events`, confirms plan-limit source, merges rollup schema and metric catalog. API contract agreed between the two engineers. |
| Weeks 2–3 (to Oct 2) | **Rollup + current month** | Nightly job and backfill running in staging; current-month cards with limit bars rendered from real data. |
| Week 4 (to Oct 9) | **Trend + CSV** | Six-month chart per metric; CSV download of monthly numbers. |
| Week 5 (to Oct 16) | **Alerts + pilot prep** | 80% email sending from staging with dedupe; feature flag, error monitoring, QA pass against a handful of real accounts. Code freeze Oct 16. |
| Week 6 (Oct 19–23) | **Pilot** | Flag on for 20 accounts Oct 19; fix feedback; verify the nightly job succeeds every day. |
| Oct 26 – Nov 2 | **General availability** | Flag on for all accounts by Oct 30, giving one business day of buffer before Nov 2. |

## Risks

| Risk | Mitigation |
|---|---|
| **Plan limits are not stored in a queryable form**, or change on Nov 2 with the pricing update. | Resolve in week 1. If limits live only in code or a spreadsheet, add a small `plan_limits` table now and seed it with both current and post-Nov-2 values with effective dates. |
| **Backfill is slow** if `usage_events` is large and lacks an index on `(account_id, timestamp)`. | Profile in week 1; backfill month by month off-peak. Adding an index is within the no-new-infra constraint. |
| **Billing pipeline runs late** and the 04:00 rollup sees a partial day. | Job checks for a pipeline completion marker (or last event timestamp past 03:00) and retries hourly until noon; dashboard shows "updated as of" so stale data is visible, not silent. |
| **Alert emails go out wrong** (duplicates, wrong threshold, sent during backfill). | Dedupe table plus a dry-run mode that logs instead of sends; enable real sends only for pilot accounts first. |
| **The six weeks end Oct 23 but GA is Nov 2.** | Pilot-fix work must fit in week 6; the final flag flip needs one engineer available for ~2 days the week of Oct 26. Confirm that allocation now. |
| **Raw metric names confuse admins.** | Metric catalog with labels reviewed by the designer and someone from support in week 1. |

## Open questions (need answers by end of week 1)

1. Where do per-plan limits per metric currently live, and what are they after Nov 2?
2. Which transactional email service does the app already use, and who owns the template?
3. Are months defined in UTC for billing? (Plan assumes yes; the dashboard will say so.)

## Out of scope for v1

Billing and invoice display, per-user breakdown within an account, public API, mobile app, custom date ranges, real-time data, alerts at thresholds other than 80%.
