**Reasoning (brief)**

*What the brief doesn't say:*
- What "usage" means: API calls, seats, storage, compute minutes, messages? One metric or several?
- Who the "customer" is: every logged-in user, or only account admins? Are there orgs/sub-accounts?
- Where usage data lives today: a metering service, raw event logs, or only the billing system?
- How fresh it must be: real-time, hourly, or "as of yesterday"?
- Whether it must match the invoice. If customers compare the dashboard to their bill, any mismatch is a support ticket.
- Whether it ties to limits (quota, overage warnings) or is purely informational.
- Where it lives: existing customer portal or a new surface?

*Gaps that change the plan most:*
1. **Data source.** If a metering pipeline exists, this is mostly a UI project (weeks). If usage only exists as raw events or inside the billing system, building trustworthy aggregates is the majority of the work (months).
2. **Invoice reconciliation.** Determines whether we can show "approximate" numbers with a disclaimer or must match billing to the unit.
3. **Freshness.** Daily aggregates are cheap; real-time means streaming and a different architecture.

*Smallest version that satisfies the sentence:* one page in the existing portal, visible to account admins, showing (a) usage so far this billing period per metered unit, against the plan limit if one exists, and (b) a daily bar chart for the last 90 days. Data comes from a nightly aggregate table; page says "updated daily."

*Explicitly out of v1:* threshold alerts/emails, CSV export, breakdown by project/API key/user, custom date ranges, real-time counters, forecasting, cost-in-dollars, a public usage API, admin impersonation view.

*Where it slips:* getting the numbers to agree with billing; backfilling history for large customers; aggregation performance on the biggest tenants; tenant-scoping bugs (showing one customer another's data is a security incident, not a bug); and scope creep from "can it also show...".

**Plan:**

**Assumptions (confirm in the meeting)**
- A1: Usage = the 1–3 units we already bill on. Product to name them.
- A2: Data source is [billing events / metering DB] — to be confirmed in M0.
- A3: Daily freshness is acceptable for v1.
- A4: Visible to account admins in the existing portal, behind existing auth.

**Scope (v1)**
- Current-period usage per unit, with plan limit and % consumed where applicable.
- Daily usage chart, last 90 days, per unit.
- "Last updated" timestamp and a note that invoices are authoritative.
- Nothing else (see exclusions above).

**Milestones** (estimate: 2 engineers + part-time design, ~6–7 weeks; M0 outcome may revise this)

| # | Milestone | Exit criteria | Est. |
|---|---|---|---|
| M0 | Discovery spike | Usage units named; data source confirmed; sample query reproduces last month's invoice for 3 customers within 1%; decision on freshness | 1 wk |
| M1 | Aggregation pipeline | Nightly job writes `usage_daily(tenant, unit, day, amount)`; idempotent; backfill of 90 days for all tenants complete; runtime under budget for largest tenant | 2 wks |
| M2 | API + UI | Tenant-scoped read endpoint; dashboard page with period summary + 90-day chart; empty/loading/error states; design review passed | 2 wks |
| M3 | Reconciliation + beta | Dashboard totals match billing for prior closed period across all tenants (automated check); 5–10 beta customers enabled via feature flag; support briefed | 1–1.5 wks |
| M4 | GA | Flag on for all; monitoring on job failures and stale data; release note | 0.5 wk |

**Risks**

| Risk | Impact | Mitigation |
|---|---|---|
| No clean metering source; usage must be derived from raw events | Timeline doubles | M0 is a hard gate; re-plan if reconciliation query can't be written in a week |
| Dashboard disagrees with invoice | Trust loss, support load | Automated reconciliation check in M3; disclaimer text; invoices remain source of truth |
| Cross-tenant data leak | Security incident | Tenant ID enforced at query layer, not in UI; explicit test for it before beta |
| Backfill/aggregation too slow for largest tenants | M1 slips | Test against top-10 tenants early in M1; cap history at 90 days |
| Scope creep (alerts, export, breakdowns) | Nothing ships | Exclusions listed above are the agreed line; new asks go into v1.1 backlog |
| Late data (events arrive after the nightly run) | Numbers change retroactively | Job recomputes last 3 days each run; "updated daily" label sets expectations |
