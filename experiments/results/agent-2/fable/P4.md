# Customer Usage Dashboard — v1 Implementation Plan

## What the brief says

"We want a dashboard so customers can see their usage." That is the whole brief. Everything below that goes beyond that sentence is marked as an assumption (A) or a question for the PM (Q). Nothing here should be read as a fact we have confirmed.

## Assumptions (confirm or correct in M0)

- **A1.** "Customers" means authenticated users of our existing product; the dashboard is a page inside the logged-in app, not a separate site.
- **A2.** "Usage" means quantities we already record today (for billing, rate limiting, or logs). v1 does not instrument new events.
- **A3.** A customer sees only their own account's usage, scoped by the product's existing tenancy model.
- **A4.** Data that is up to ~24 hours old is acceptable (nightly aggregation rather than real-time).
- **A5.** Read-only. v1 shows numbers; it does not let customers change plans, set alerts, or export.

## Questions for the PM

- **Q1.** Which metrics, exactly? Name the 1–3 that matter most, with units.
- **Q2.** Who inside the customer account sees it: admins only, or every seat?
- **Q3.** What time ranges and granularity? (e.g., current billing period by day; last 12 months by month.)
- **Q4.** Must the numbers reconcile exactly with the invoice? If yes, the dashboard has to read from the billing source of truth rather than a separate pipeline.
- **Q5.** Is there a quota or plan limit to show against ("40 of 100 used")?
- **Q6.** Is "as of yesterday" acceptable freshness?
- **Q7.** What prompted this (support tickets, churn, sales asks)? It changes what "done" means.
- **Q8.** Is there a deadline or launch this is tied to?

## Non-goals for v1

- Usage alerts, thresholds, or notifications
- CSV or API export of usage data
- Spend projections, cost estimates, or pricing calculators
- Internal/support-facing views of customer usage
- Per-user breakdown within an account (unless Q2 says otherwise)
- Real-time or streaming updates
- Backfilling history beyond what the source system already holds
- Native mobile app (responsive web is sufficient)
- Instrumenting new usage events

## Milestones

| # | Milestone | Size | Exit criteria |
|---|-----------|------|---------------|
| M0 | **Scope lock.** PM answers Q1–Q8; A1–A5 confirmed or corrected. Produce a one-page metric definition per v1 metric: name, unit, source table/field, aggregation rule. | 2–3 days | Eng and PM sign off on metric definitions. Nothing else starts before this. |
| M1 | **Data path.** Locate where each metric lives. Build a daily rollup job (per customer, per metric) into a table the dashboard can query cheaply. Validate rollups against the source for a sample of accounts. | 1–2 weeks | Rollup table populated for all active customers; spot-checks match source within an agreed tolerance. |
| M2 | **API.** One read endpoint returning usage for the calling customer by metric, time range, and granularity. Tenant is derived from the session; the client never passes a customer ID. | ~1 week | Behind auth, integration-tested, acceptable p95 latency on the largest account. |
| M3 | **UI.** One page in the existing app: metric selector (if more than one), time-range picker, one chart, one summary number, quota if Q5 says yes. Empty state and a visible "data as of <timestamp>" label. | 1–2 weeks | Works at desktop and mobile widths, design reviewed, chart has a table fallback for accessibility. |
| M4 | **Hardening and rollout.** Load test against top-10 accounts by volume, feature flag, internal dogfood, staged rollout to a customer subset, then 100%. Basic page-view and error instrumentation. | ~1 week | Flag at 100%, no P1 issues for one week. |

**Total: roughly 5–7 weeks for one to two engineers.** M1 → M2 → M3 are sequential, though M3 can start once the M2 API contract is agreed.

## Risks specific to this project

**R1. The dashboard number does not match the invoice.**
Customers will compare the page against their bill. Any gap becomes a support ticket and undermines trust in both.
*Mitigation:* Decide in M0 whether billing is the source of truth (Q4). If yes, read from the billing pipeline's data instead of re-deriving. Add a reconciliation check in M1 that compares rollups to billed totals for closed periods and fails loudly on drift.

**R2. Cross-tenant data exposure.**
A usage endpoint that accepts a customer identifier from the client is a classic IDOR. This is the one place where a bug is a security incident rather than a display glitch.
*Mitigation:* The API derives the tenant from the authenticated session only (M2). Add an explicit test that a user in account A cannot retrieve account B's data. Security review gate before rollout in M4.

**R3. Query cost on the largest accounts.**
If usage is stored as raw events, querying months of data live for the biggest customers will be slow or expensive, and those customers are the most likely to open this page first.
*Mitigation:* Pre-aggregate daily rollups in M1 so the API reads a small table. Load-test against the top-10 accounts in M4. Cap the v1 time range if needed.

**R4. The definition of "usage" changes mid-build.**
Because the brief names no metric, "usage" is likely to be redefined during development ("we also meant X"). Each added metric touches M1, M2, and M3.
*Mitigation:* M0 produces a written metric list that is frozen for v1. Anything added afterward goes to the backlog, not this release.

**R5. Freshness mismatch.**
If customers expect today's usage and the rollup is nightly, they will report the page as broken.
*Mitigation:* Confirm the freshness expectation (Q6). Show "data as of <timestamp>" prominently in the UI (M3).

## Definition of done for v1

A logged-in customer opens one page, sees the agreed metric(s) for their account over the agreed time range, and the numbers agree with billing to the agreed tolerance. Nothing else.
