## What I did

Wrote a one-page implementation plan sized for a meeting review (~10 min). No product context existed to ground it in — the working directories hold only the user's unrelated "Prompt Engineer" research repo — so the plan is built on **explicitly stated assumptions rather than invented specifics**, and says so up front.

## The key judgment call

The brief ("a dashboard so customers can see their usage") is underspecified in ways that swing the estimate by 3-4x, so the most useful thing engineering can hand back is not a schedule but **a list of what must be decided before a schedule means anything**. Section 02 names five load-bearing assumptions, each paired with what it costs if wrong (e.g. "if usage is computed inside billing with no queryable event store, add 3-4 weeks"). Section 06 turns those into five questions to answer in the meeting itself.

## Plan shape

- **Scope**: read-only page, current + previous billing period, daily granularity, one breakdown dimension. Explicit non-goals list (custom ranges, alerts, forecasting, per-key attribution, real-time) which doubles as the anti-scope-creep contract.
- **Approach**: one architectural decision — the dashboard never queries raw events; an idempotent job rolls into `usage_daily`, closed periods frozen, open period served with an "as of" timestamp and labelled provisional.
- **Milestones**: M0 definitions (1wk) → M1 rollups+API with *no UI* (2wks) → M2 dashboard (2wks) → M3 hardening (2wks) → M4 beta→GA (2wks), plus a held buffer week. Each has a hard exit gate rather than a soft deliverable.
- **Risks**: six, severity-ranked. The top one is that the dashboard disagrees with the invoice — so reconciliation against real invoice line items is M1's *exit criterion*, not a QA task, and M1 deliberately precedes anything visible.

## Two things worth flagging to the user

1. **The 10-week figure is presented as a plan, not a commitment** — it firms up after M0. I'd resist letting it get quoted as a date before the assumptions are answered.
2. **Owner is marked TBD** and the team size (2 eng + design at 30%) is my assumption. Both need real names before this is actionable.
