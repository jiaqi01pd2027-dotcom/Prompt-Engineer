## The brief is one sentence and three words in it are load-bearing

"Customers," "see," and "usage" each hide a decision that changes what gets built. Rather than guess all three, here's the plan plus the questions that would reshape it.

**What is "usage"?** If it's the metric they're *billed* on, this is a billing-trust surface and it must reconcile to the invoice exactly. If it's a metric they *operate* on (API calls, seats active, storage), it's an analytics surface where approximation is fine and the bar is much lower. These are different products.

**Who is the "customer"?** One person, or an account with many seats? Multi-seat adds per-member breakdown, an access-control decision (can a member see other members' usage?), and in some jurisdictions a privacy question, since per-employee usage is monitoring-adjacent.

**Why now?** A usage dashboard is almost always a proxy for a specific pain: support tickets asking "why is my bill this," churn from overage surprise, sales wanting expansion signals, or a contractual reporting requirement. Bill-shock churn needs forecasting and threshold alerts, not charts. Support load needs the exact line items tickets ask about. Worth naming the pain before scoping.

## Phase 0 — Data audit (do this first, it can kill the project)

Before any design, take a handful of real accounts and trace events → aggregation → invoice. Do the numbers tie out?

This is the step teams skip and regret. If billing is computed from a different code path than the event stream the dashboard would read, the dashboard *will* disagree with the invoice, and a dashboard that's one cent off generates the exact support tickets it was meant to deflect. It's worse than no dashboard. Also check: is there a per-event record with customer ID and timestamp, is retention long enough to show a trailing year, and how are late-arriving events handled?

If reconciliation fails, that's the project. Everything else is downstream of it.

## Phase 1 — Write the metric contract

A plain-language definition of every number shown: what counts as one unit, which timezone period boundaries use, how partial periods, cancellations, refunds, and credits are treated. This document is also what support and sales should be answering from — the same definition in three places is most of the value.

## Phase 2 — Aggregation

Pre-computed rollups (hourly or daily, per customer per metric) rather than querying raw events at page load. Make them idempotent and backfillable so a restatement is a rewrite rather than a patch. Freshness is the biggest cost driver here — daily is almost always enough if the page states its as-of time honestly. Real-time is a large expense customers rarely asked for.

## Phase 3 — Read API + export

One endpoint shaped to what the UI needs, auth scoped to the account, plus CSV export. Export is cheap and deflects a surprising share of tickets from power users who want to do their own math.

## Phase 4 — The thinnest UI that works

Current period at a glance: what's used, against what limit, projected to period end, with a visible as-of timestamp. One trend chart. One breakdown table with export. That's it.

Deliberately cut from v1: real-time updates, custom date ranges, saved views, per-endpoint drilldown, peer comparison, and in-app upgrade flow (unless expansion is the actual pain).

## Phase 5 — Threshold alerts

Notify at 80% / 100% of limit. For bill-shock churn this is usually worth more than the dashboard, because it reaches customers who never log in.

## Risks worth deciding on deliberately

- **Invoice mismatch** — the failure mode that destroys trust. Phase 0 exists for this.
- **Honest usage data can trigger downgrades.** Customers who discover they're paying for more than they use will act on it. That's often the right trade, but it should be a decision, not a surprise.
- **Success metric should tie to the pain** — usage-related ticket volume, or overage churn rate — not dashboard page views.

## Rough sizing

Data audit: about a week. If the pipeline exists and reconciles, v1 in roughly 3–5 weeks. If it doesn't, the pipeline *is* the project and it's more like 8–12.

I kept this as text rather than publishing it as a shareable page, because with the three questions above unresolved, a polished document tends to launder assumptions into settled decisions. Once the pain and the definition of "usage" are pinned down, this is worth publishing as a page the team can work from.
