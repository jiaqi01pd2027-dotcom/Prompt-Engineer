# Usage Dashboard — v1 Implementation Plan

**Status:** draft for eng review · **Owner:** PM · **Target:** ~7 weeks, 2 eng (1 BE, 1 FE) + design part-time

## 1. The brief is under-specified; here's the interpretation we're building to

"Customers can see their usage" most plausibly means: **a logged-in account admin can answer "how much have we used this billing period, and are we near a limit?" without emailing support.** That framing drives every scoping call below.

Assumptions we are proceeding on. Each is cheap to correct now and expensive later — please challenge in the meeting:

| # | Assumption | If wrong, impact |
|---|---|---|
| A1 | Audience is account admins/billers, not end users seeing personal usage | Changes authz model and UI entirely — **material** |
| A2 | Usage means the metered dimension(s) we already bill on, not product analytics (DAU, feature adoption) | Different data source, different team — **material** |
| A3 | Hourly freshness is acceptable; real-time is not required for v1 | Real-time forces a streaming path, +3–4 weeks |
| A4 | We already emit a durable, per-account usage event stream with ≥13 months retention | No backfill means the dashboard launches empty — **material** |
| A5 | Numbers must reconcile with the invoice | Drives most of the QA cost below; if "directional is fine," M4 shrinks a lot |

## 2. Scope

**In (v1)**
- Current-period total per metered dimension, vs. plan limit, with % consumed
- Time-series chart, daily granularity, presets: this period / last period / last 30 days
- Breakdown table by one grouping dimension (e.g. project, API key, or seat — team picks the one that exists today)
- CSV export of the visible table
- Empty, loading, error, and "no data yet" states
- "Last updated" timestamp, visible, so support has something to point at

**Out (v1) — deliberately**
Usage alerts and notification thresholds · custom date ranges · multi-dimension pivots · forecasting/projected spend · cost in dollars (usage only; dollars invite invoice disputes) · public API for usage · per-end-user drilldown · real-time/sub-hour freshness · non-admin roles

Dollars and alerts are the two most likely to get argued back in. Both are reasonable v2 fast-follows; neither should block v1.

## 3. Shape of the build

Three layers, and the middle one is where the work actually is:

1. **Rollup pipeline** — batch job aggregating raw usage events into `usage_rollup_daily (account_id, dimension, group_key, day, quantity)`, plus an hourly table for the current day. Idempotent, re-runnable, with a backfill mode. Query-on-raw-events was considered and rejected: it fails on the largest accounts and gives no place to fix historical data.
2. **API** — `GET /v1/usage/summary` and `/v1/usage/series`, account-scoped at the middleware layer, reading rollups only.
3. **UI** — one page, chart + table + limit meters.

## 4. Milestones

| M | Deliverable | Size | Exit criteria |
|---|---|---|---|
| **M0** | Data spike | 1 wk | Confirmed: events exist, are attributable to an account, and 13 months are queryable. Reconciliation gap vs. a sample invoice measured and written down. **Go/no-go gate.** |
| **M1** | Rollup pipeline + backfill | 2 wks | Daily + hourly rollups running on schedule; full historical backfill complete; re-run produces identical output |
| **M2** | Usage API | 1 wk | Both endpoints behind auth; cross-account access covered by tests; p95 < 300ms for the 99th-percentile account |
| **M3** | Dashboard UI | 2 wks | All states implemented; CSV export; responsive; a11y pass on chart and table |
| **M4** | Reconciliation + rollout | 1 wk | Automated daily check comparing rollup totals to billing totals; internal dogfood; flagged rollout 5% → 50% → 100% |

M2 and M3 overlap once the API contract is frozen at the end of M1 — the FE builds against a stub. That's the ~7 week figure; strictly serial it's 8.

Sizes are for calibration, not commitment. The team should replace them after M0.

## 5. Risks

| Risk | L | Impact | Mitigation |
|---|---|---|---|
| **Dashboard disagrees with the invoice.** The single biggest threat — a usage number a customer can't reconcile generates more support load than having no dashboard at all. | High | High | M0 measures the gap before we build; M4 is a standing automated reconciliation check; ship a "how we calculate this" help link |
| **Event data is incomplete or not cleanly attributable** (missing account_id, gaps, dedupe issues) | Med | High | M0 is explicitly a go/no-go on this; if it fails, the real project is fixing metering, not building a dashboard |
| **Cross-tenant data leakage** | Low | Critical | Account scoping enforced in one middleware layer, not per-endpoint; explicit negative tests in M2; security review before flag-on |
| **Scope creep into "analytics"** | High | Med | The Out list above is the contract; alerts/dollars/forecasting go to a named v2 |
| **Large-account query performance** | Med | Med | Pre-aggregation by design; test against the biggest real account, not synthetic data |
| **Backfill is slow or expensive** | Med | Low | Backfill windowed and resumable; worst case v1 launches with 90 days and fills in behind the flag |

## 6. Open questions blocking the estimate

1. Which metered dimensions, and what is the authoritative source of truth for each?
2. What is the grouping dimension for the breakdown table — does it exist in the event stream today?
3. Do we show dollars? (Recommendation: no, not in v1.)
4. Who is the buyer of this — is it churn/support-load driven, or a sales ask? That determines whether limits-and-alerts or historical trend is the more important half.
5. What's the success metric? Suggested: % of accounts with an admin viewing it monthly, plus change in usage-related support ticket volume.

---

Two things worth flagging to whoever relays this: **M0 is a genuine go/no-go**, not a formality — if the metering data isn't trustworthy, this project is really a data-quality project wearing a UI. And the assumptions table in §1 is the part to spend meeting time on; A1, A2, and A4 each change the plan materially if they're wrong.
