## Usage Dashboard — v1 Implementation Plan

**Team:** 1 backend, 1 frontend (6 weeks), designer (week 1 only). No new infrastructure.
**Window:** Mon Sep 14 → Fri Oct 23. Pilot Oct 19 (20 accounts). GA Oct 29, ahead of the Nov 2 pricing change.

### Scope

In: current-month usage per metric vs. plan limit; 6-month trend per metric; CSV of monthly numbers; one email alert at 80% of a limit.

Out: billing/invoice display, per-user breakdown within an account, public API, mobile app, custom date ranges. Not negotiable inside these six weeks — anything added displaces something above.

### Approach

- **Rollup, not live queries.** Nightly job aggregates `usage_events` into `usage_daily (account_id, metric, day, quantity)`, run after the billing pipeline finishes at 03:00 UTC. Six months of history backfilled once from `usage_events`. At ~1,200 accounts the table stays small enough that month and trend views aggregate on read; no second rollup needed.
- **Reuse the existing session auth.** Page sits behind current web app login. `account_id` comes from the session, never from a request parameter — one explicit authz test that a signed-in admin cannot read another account.
- **Alerts run off the same nightly job.** After the rollup, evaluate each account/metric against its limit; send one email per metric per billing period, tracked in a `usage_alerts_sent` table so a customer sitting at 85% for a week gets one email, not seven. Uses the existing transactional email path.
- **No new infra.** Nightly job goes on the existing scheduler; no new database, queue, or BI tool.

### Milestones

| Week | Milestone | Done means |
|---|---|---|
| 1 (Sep 14) | Data model + design | `usage_daily` schema agreed, backfill script runs against a prod snapshot, designer delivers screens for the month view, trend, and over-limit state |
| 2 (Sep 21) | Pipeline live | Nightly rollup running in staging on real data, reconciled against `usage_events` totals for a sample of accounts |
| 3 (Sep 28) | API + shell | Read endpoints for current month and 6-month trend, behind session auth; frontend renders real data for one metric |
| 4 (Oct 5) | Feature-complete UI | All metrics, limits, trend chart, CSV download; authz test suite green |
| 5 (Oct 12) | Alerts + hardening | 80% email sending in staging with dedupe verified across a simulated month boundary; internal dogfood on our own account |
| 6 (Oct 19) | Pilot | 20 accounts behind a flag; daily check on data accuracy and alert volume |
| Oct 29 | GA | Flag on for all 1,200 accounts |

Weeks 5 and 6 carry the schedule risk. If something slips, the alert email is the piece to cut and ship in November — the dashboard is what customers need before the pricing change.

### Risks

1. **Plan limits have no agreed source.** The brief assumes a limit per account per metric, but nobody said where it lives. This is the one open dependency that can stall week 1 — settle it Monday. If no authoritative source exists, seed a `plan_limits` table from finance and treat it as a manual input for v1.
2. **The dashboard's month must match the invoice's month.** If we define the month in UTC and billing uses account-local time or an anniversary date, customers will compare the two and file tickets. Confirm the definition with billing before week 2 and use theirs.
3. **The billing pipeline is a hard upstream dependency.** If it runs late or fails, the dashboard shows stale numbers silently. Add a "data as of" timestamp on the page and an internal alert if the rollup has not run by 05:00 UTC.
4. **Backfill correctness.** Six months of `usage_events` may contain corrections, retries, or duplicates the billing pipeline handles and we would not. Reconcile a sample against invoices before pilot rather than after.
5. **Alert volume at the pricing change.** A pricing change moves limits, which could fire 80% alerts to a large share of accounts at once. Check the projected send count before GA and coordinate with whoever owns the pricing comms.
6. **Designer is available only in week 1.** Any UI question that opens in week 4 gets answered by the frontend engineer. Get the over-limit and empty/new-account states designed up front, since those are where improvisation shows.

### Open question for the meeting

What does an account over 100% of its limit see? That is a product and pricing decision, not an engineering one, and it needs an answer before the designer's week ends.
