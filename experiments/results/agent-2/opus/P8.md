# Scope (in)

**Data layer (backend)**
- New rollup table `usage_daily` (account_id, metric, day, quantity_sum), populated from `usage_events`. Source table is read-only for this project; the billing pipeline is not modified.
- Nightly job triggered after 03:00 UTC that rebuilds the last 3 days of `usage_daily` (to absorb late-arriving events) and refreshes a `usage_monthly` view/table (account_id, metric, month, quantity_sum) for the current month plus the previous 6.
- One-time backfill of 7 calendar months of history (current month + 6 prior), run in chunks outside business hours.
- Job records a `last_successful_run_at` watermark that the UI reads.

**API (backend, session-authenticated, existing web app)**
- `GET /usage/summary` — for the caller's account only: per metric, current-month-to-date quantity, the plan limit for that metric, percent of limit, and the data-as-of timestamp.
- `GET /usage/trend` — for the caller's account only: per metric, monthly totals for the last 6 complete months plus the current partial month.
- `GET /usage/export.csv` — monthly numbers for the same 7-month window, one row per (month, metric), columns: `month, metric, quantity, plan_limit`. Filename `usage_<account_slug>_<YYYY-MM-DD>.csv`.
- `account_id` is always taken from the session. No account identifier is accepted from the client on any of these endpoints.

**Dashboard UI (frontend, inside existing authenticated web app)**
- One page, one route, linked from the existing main navigation.
- Section 1 — current month: one row per metric showing used / limit, a progress bar, and percent. Bar turns to the warning style at ≥80% of limit. Metrics with no limit show the number only, no bar.
- Section 2 — trend: one chart per metric, 7 points (6 complete months + current partial, labelled as partial), plain month labels.
- Section 3 — "Download CSV" button hitting the export endpoint.
- "Usage as of <date> 03:00 UTC" line on the page. If the nightly job has not succeeded in the last 36 hours, a non-blocking banner says data may be stale.
- Empty state (new account, no events), zero-usage state, and error state are all designed and built.
- Written for a non-technical admin: no jargon, metric display names from a lookup, tooltips explaining each metric.

**Email alert (backend)**
- Daily check after the rollup job: for each account and metric with a plan limit, if current-month-to-date usage ≥80% of the limit, send one email to the account admin(s).
- Sent at most once per (account, metric, calendar month), tracked in a `usage_alerts_sent` table. Crossing 100% does not send a second email in v1.
- Email uses the existing transactional email sender and existing template shell; contains metric, current usage, limit, percent, and a link to the dashboard.
- Alerts are suppressed for non-pilot accounts until GA.

**Rollout**
- Gated to an allowlist of 20 pilot accounts from Oct 19; opened to all paid accounts in the same week.

# Non-goals

- No billing or invoice display.
- No per-user breakdown within an account.
- No public API.
- No mobile app.
- No custom date ranges.

# Risks

- **The plan-limit source does not exist or is not queryable per account and metric**: this is the single hardest dependency, so it is the first item on Monday; if no source is found by Wednesday of week 1, fall back to a `plan_limits` config table seeded from whatever the pricing owner can supply as a spreadsheet, and treat metrics without a limit as display-only.
- **`usage_events` is large or unindexed, making the backfill and nightly job slow enough to affect the billing database**: measure row count and index coverage on day 1 of week 1; run the backfill in month-sized chunks outside business hours; add a covering index on (account_id, metric, timestamp) if missing; all user-facing reads hit the rollup tables, never `usage_events`.
- **The billing pipeline finishes late or partially, so the dashboard shows wrong numbers on the day a pricing change lands**: the nightly job checks the pipeline's completion watermark before running, retries hourly until 09:00 UTC, re-windows the last 3 days each night to absorb late events, and the UI shows a staleness banner rather than silently displaying old data.
- **The 80% alert misfires at scale — duplicate emails, or a burst of hundreds on the first run after backfill**: dedupe per (account, metric, calendar month) in a sent table; run the first pass in dry-run mode with sending disabled and review the recipient list; keep alerts limited to the 20 pilot accounts for the whole pilot week before enabling account-wide.
- **A bug leaks one account's usage to another admin, which is worse than shipping late**: account is read only from the session and never from a request parameter, every endpoint gets an automated test asserting a cross-account request fails, and the pilot week includes a manual two-account check before the flag is widened.
- **The six-week budget ends Oct 23 and the designer leaves after week 1, leaving no capacity for post-GA fixes before Nov 2**: front-load design decisions into week 1 with all states specified, keep milestones 9 and 10 deliberately light on new code, and hold the 7 working days between GA and the pricing change as fix-only time with no new scope.
