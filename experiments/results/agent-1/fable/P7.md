**Reasoning**

- **Layers a persisted field crosses.** Column in `app/models.py` → Alembic migration (production only) → `TodoCreate`/`TodoUpdate`/`TodoOut` in `app/schemas.py` → create/patch handlers and the list query in `app/routes.py` → tests. `app/db.py` doesn't change.
- **"In the past" on a server.** Must be `now` in UTC, computed per request, compared against a value stored in the same convention as `created_at`. SQLite has no real datetime type; SQLAlchemy stores ISO strings, so mixing tz-aware and naive values (or UTC and local) silently breaks `<` comparisons. Pydantic will accept both `"2026-09-01T10:00:00Z"` and `"2026-09-01T10:00:00"`, so normalization has to happen deliberately at the boundary.
- **Existing rows.** They have no due date, so the column must be nullable with no default; SQLite's `ALTER TABLE ADD COLUMN` handles that without batch mode. `NULL` must mean "never overdue", so the filter has to include `due_date IS NOT NULL` explicitly and `TodoOut.due_date` must be `Optional` or serializing old rows fails.
- **Two tricky semantics.** PATCH needs to distinguish "field omitted" from "set to null" (clearing a due date) — the existing `TodoUpdate` pattern with `exclude_unset` covers it if the field is added the same way. And `overdue` must combine sanely with the existing `done` filter (`overdue=true&done=true` is a contradiction; returning an empty list naturally is fine, just decide and test it).
- **Tests.** The suite builds tables from models, so the migration is invisible to it and needs a separate check. The filter is proven with four todos in one database: past+not done (in), past+done (out), future+not done (out), no due date (out). Using `now ± 1 day` avoids flakiness without clock mocking.

**Plan:**

1. **`app/models.py`** — Add `due_date` as a nullable `DateTime` column with no default, declared the same way as `created_at` (same timezone flag) so both columns share one storage convention.

2. **`alembic/versions/0002_add_due_date.py`** — New migration with `down_revision` pointing at `0001`. `upgrade` adds the nullable `due_date` column to `todos`; `downgrade` drops it (use `batch_alter_table` for the drop, since SQLite can't `DROP COLUMN` directly on older versions). Verify by copying a real `todo.db`, running `alembic upgrade head`, confirming existing rows read back with `due_date = NULL`, then `alembic downgrade -1` to confirm the reverse works.

3. **`app/schemas.py`** — Add `due_date: datetime | None = None` to `TodoCreate`, `TodoUpdate`, and `TodoOut`. Add a validator (shared between Create and Update) that normalizes input: convert tz-aware values to UTC, and either treat naive values as UTC or reject them with 422 — pick one, document it in the field description, and make it match how `created_at` is produced. Do not reject past due dates on create; backfilling is legitimate.

4. **`app/routes.py`, POST and PATCH** — Pass `due_date` through on create. On PATCH, keep using `exclude_unset=True` so `{}` leaves the due date alone while `{"due_date": null}` clears it.

5. **`app/routes.py`, GET /todos** — Add an optional `overdue: bool | None` query param alongside `done`. When `overdue=true`, add three conditions to the query: `due_date IS NOT NULL`, `due_date < now`, `done == false`, where `now` is `datetime.now(timezone.utc)` computed inside the handler (not at import time) and shaped to match the column convention from step 3. When `overdue=false`, apply the negation (no due date, or future, or done). When omitted, no filter. Let it compose with `done` via plain AND; `overdue=true&done=true` yields an empty list, which is acceptable — don't special-case it.

6. **`tests/test_todos.py`** — Add tests, using `datetime.now(timezone.utc) ± timedelta(days=1)` for past/future values:
   - Create without `due_date` → response has `due_date: null`; existing twelve tests stay green unchanged.
   - Create with `due_date` → round-trips in the response in the same format as `created_at`.
   - Create with an unparseable `due_date` → 422; if step 3 chose to reject naive datetimes, test that too.
   - PATCH sets a due date; PATCH with `{"due_date": null}` clears it; PATCH with only `title` leaves it untouched.
   - Overdue filter: seed the four todos above in one client session, call `GET /todos?overdue=true`, assert exactly the past+not-done one is returned. Then mark it done via PATCH and assert the list becomes empty.
   - `GET /todos?overdue=false` returns the other three; `GET /todos` with no param returns all four; `overdue=true&done=true` returns empty.

7. **Manual production check** — Run step 2's migration verification against a copy of the real database, then hit `GET /todos` and `GET /todos?overdue=true` to confirm legacy rows serialize and are excluded from the overdue list.
