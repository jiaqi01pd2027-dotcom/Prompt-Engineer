# Implementation plan: optional `due_date` + `?overdue=true`

## 0. Decisions to lock in before coding

These affect several files at once; settle them first so the migration, schemas and tests agree.

1. **Storage is UTC, naive.** SQLite has no real timezone-aware datetime type; `created_at` is already stored as UTC. Store `due_date` the same way: convert every incoming value to UTC and strip tzinfo before it hits the ORM. On the way out, attach UTC tzinfo so responses serialize with an explicit offset (`...+00:00` / `Z`). Never emit a naive string, because the web and mobile clients are in different zones and would interpret it differently.
2. **Input must be timezone-aware.** Reject naive ISO-8601 strings (no offset) with a 422 rather than guessing the client's zone. This is the single most important guard for the multi-timezone requirement. (If the team would rather accept naive input, document "naive = UTC" explicitly; do not leave it implicit.)
3. **Past due dates are allowed on create/patch.** A todo created with a due date that is already past is simply overdue immediately. Do not add a "must be in the future" validation.
4. **PATCH must distinguish "omitted" from "null".** `{"title": "x"}` leaves `due_date` untouched; `{"due_date": null}` clears it. This needs the "exclude unset" pattern in the patch handler, not "ignore None".
5. **Overdue definition:** `due_date IS NOT NULL AND due_date < now_utc AND done = false`. Strict less-than; a due date equal to "now" is not overdue.
6. **`overdue=false` semantics:** pick one and document it. Recommended: `overdue=true` applies the filter, `overdue=false` (or omitted) applies no filter. Implementing "not overdue" as the inverse is possible but is a third-state filter the team did not ask for.
7. **Combining with `done`:** filters are ANDed. `?overdue=true&done=true` is legal and always returns an empty list; that is fine and should have a test so nobody "fixes" it later.
8. **"Now" must be injectable.** The overdue comparison needs a clock the tests can control. Add a small `utcnow()` helper (in `app/db.py` is acceptable since it is tiny, or a new `app/clock.py`) that routes call it, so tests can monkeypatch it instead of sleeping or relying on wall time.

## 1. Model (`app/models.py`)

1. Add `due_date` as a nullable `DateTime` column with no server default. Nullable is what makes existing rows in `todo.db` keep working with no backfill.
2. Do not use `DateTime(timezone=True)` expecting SQLite to honor it; it will not. Rely on the UTC normalization in step 0.1.
3. No index for now. The table is small and the filter is on a single column; add one later only if the list endpoint gets slow.

## 2. Migration (`alembic/versions/0002_add_due_date.py`)

1. Create a new revision whose `down_revision` is the `0001` revision id. Copy the id from the existing file rather than retyping it.
2. `upgrade`: add the nullable `due_date` column to `todos`. SQLite supports `ADD COLUMN` for a nullable column with no default directly, so no batch mode is required for upgrade.
3. `downgrade`: drop the column. On SQLite this needs `batch_alter_table` (table-rebuild), so write it that way; do not leave `downgrade` as `pass`.
4. Verify by hand against a **copy** of the production `todo.db`: run `alembic upgrade head`, confirm existing rows read back with `due_date = NULL`, run `alembic downgrade -1`, then `upgrade head` again. Do this because the test suite creates tables from the models and will never exercise this file.
5. Add a guard against model/migration drift (the real risk given tests skip Alembic): either run `alembic check` in CI after `alembic upgrade head` on a throwaway file-based SQLite DB, or add one pytest test that upgrades a temp file DB to head and asserts the `todos` columns match `Base.metadata`. Pick whichever the team finds less intrusive, but add one of them.

## 3. Schemas (`app/schemas.py`)

1. `TodoCreate`: add optional `due_date`, default `None`, typed as a timezone-aware datetime so naive strings fail validation (per 0.2). Add a validator that normalizes any offset to UTC.
2. `TodoUpdate`: add optional `due_date` with the same aware-datetime type and UTC normalization. Keep the default `None`; the patch handler will use "fields set" to tell omitted from null (0.4).
3. `TodoOut`: add `due_date` (nullable). Add a serializer/validator that, when the ORM hands back a naive UTC datetime, attaches UTC tzinfo before serialization so the JSON always carries an offset. Check whether `created_at` currently comes out naive; if it does, fix it the same way in this change so the two fields are consistent (this is a small behavior change for clients, so call it out in the release note).
4. Make sure `TodoOut` still builds from ORM objects (`from_attributes`), since `due_date` is a new attribute on the model.

## 4. Routes (`app/routes.py`)

1. **POST /todos**: pass `due_date` from the request body through to the new row. Nothing else changes.
2. **PATCH /todos/{id}**: switch the update loop to iterate over fields that were explicitly set in the request (exclude-unset), and apply them even when the value is `None`. This is what makes `{"due_date": null}` clear the date while a body without `due_date` leaves it alone. Confirm this does not change behavior for `title`/`done` (it should not, since `null` for those was already invalid or unused; if `title: null` previously slipped through and was ignored, keep that behavior explicitly).
3. **GET /todos**: add an optional boolean query param `overdue`. When true, add the three-part condition from 0.5, using the injectable `utcnow()` and comparing against a Python `datetime` (not a string) so SQLAlchemy binds it in the same format the ORM writes. Compose it with the existing `done` filter rather than replacing it.
4. **GET /todos/{id}** and **DELETE**: no logic changes; responses pick up `due_date` via `TodoOut`.

## 5. Tests (`tests/test_todos.py`)

Keep the existing twelve green; they will now see `due_date: null` in responses, which should not break them unless any test asserts on the exact response dict. Add:

1. Create without `due_date` returns `due_date: null`.
2. Create with an offset-bearing ISO-8601 string (e.g. `+05:30`) returns the same instant expressed in UTC. This is the timezone test; make the expected value differ visibly from the input.
3. Create with a naive datetime string returns 422.
4. Create with a past due date succeeds.
5. PATCH setting `due_date` on an existing todo.
6. PATCH with `due_date: null` clears it.
7. PATCH with only `title` leaves an existing `due_date` untouched (regression for 0.4).
8. `?overdue=true` with a fixed monkeypatched "now" and four seeded todos: past+not done (returned), past+done (excluded), future+not done (excluded), no due date (excluded).
9. `?overdue=true&done=true` returns an empty list.
10. `?overdue=true&done=false` returns the same as `?overdue=true`.
11. A due date exactly equal to "now" is not overdue (boundary).
12. Omitting `overdue`, or `overdue=false`, returns all todos as before.
13. The migration-vs-model drift check from step 2.5, if it is implemented as a pytest test.

## 6. Deploy and rollout

1. Merge order is not an issue: migration and code ship together, and `alembic upgrade head` already runs on deploy before the app starts. The new column is nullable, so a rolling deploy where old app code briefly runs against the migrated schema is safe.
2. Take a backup of `todo.db` before the deploy that runs `0002`, since the downgrade path is a table rebuild.
3. Release note to the web and mobile teams: `due_date` is optional, must include a UTC offset when sent, is always returned in UTC, `null` in PATCH clears it, and `?overdue=true` is evaluated server-side against server UTC time (so a todo due "today" in a client's local zone may already be overdue or not yet overdue by the server's clock; that is expected).
4. Rollback: `alembic downgrade -1` plus redeploying the previous app version. Note that downgrade discards any due dates users have entered.

## 7. Definition of done

- `pytest` green locally and in CI, including the new tests.
- `alembic upgrade head` and `downgrade -1` verified on a copy of production `todo.db` with pre-existing rows.
- Existing todos return `due_date: null` and are never reported overdue.
- Responses for `due_date` (and `created_at`) always carry an explicit UTC offset.
