# Implementation plan: optional due date + `overdue` filter

## Decisions to lock in before coding

1. **Type and name.** Use a nullable datetime column named `due_at` (not a calendar `Date`), stored as naive UTC exactly like `created_at`. "In the past" then means `due_at < now (UTC)`, with no day-boundary/timezone ambiguity. If product genuinely wants a day-granularity date, switch to `Date` and define overdue as `due_date < today (UTC)` — but pick one now, because it changes the migration, the schema, and the tests.
2. **Timezone handling on input.** Accept ISO 8601. Aware datetimes are converted to UTC and stored naive; naive datetimes are treated as already-UTC. Document this in the field description. SQLite's `DateTime` type silently drops tzinfo, so every value that reaches the DB (including the `now` used for comparison) must be naive UTC or filtering will be subtly wrong.
3. **No past-date rejection.** Do not validate that `due_at` is in the future on create/update. Users legitimately backfill overdue items, and the filter tests depend on creating them.
4. **`overdue=false` semantics.** Mirror the existing `done` param: `overdue` is `bool | None`. `true` = `due_at IS NOT NULL AND due_at < now AND done = false`. `false` = the logical complement, which deliberately includes todos with no due date. `None` = no filtering. Combining with `done` is a plain AND (`overdue=true&done=true` returns an empty list, which is correct, not an error).

## Steps

### 1. `app/models.py`
- Add `due_at` as a nullable `DateTime` column with no default. Nothing else on the model changes.

### 2. `alembic/versions/0002_add_due_at.py`
- New revision with `down_revision` pointing at `0001`.
- `upgrade`: add the nullable `due_at` column to `todos`. Adding a nullable column with no default is safe on SQLite without batch mode.
- `downgrade`: drop the column. SQLite cannot drop columns directly, so wrap it in `batch_alter_table`.
- Because the test suite creates tables from the models and never runs migrations, nothing in CI will catch model/migration drift. Verify by hand: copy `todo.db`, run `alembic upgrade head`, confirm the column exists, run `alembic downgrade -1`, confirm it is gone, then `upgrade head` again. If the installed Alembic supports it, run `alembic check` against the upgraded DB to confirm the model and schema agree.

### 3. `app/schemas.py`
- `TodoCreate`: add `due_at: datetime | None = None`.
- `TodoUpdate`: add `due_at: datetime | None = None`.
- `TodoOut`: add `due_at: datetime | None`.
- Add one shared field validator (applied to both input models) that normalizes aware datetimes to naive UTC per decision 2. Keep it in `schemas.py`; do not do the normalization in the route.
- Update existing `TodoOut` consumers only if any test asserts exact response dicts (see step 6).

### 4. `app/routes.py` — PATCH
- Check how the existing PATCH applies `TodoUpdate` to the model. It must use `exclude_unset=True` (not `exclude_none=True`) when dumping the payload. Otherwise a client cannot clear a due date: `{"due_at": null}` and an omitted `due_at` become indistinguishable, and the null gets dropped. If the route currently uses `exclude_none`, change it; `title` and `done` behavior is unaffected because they were never legitimately settable to null.

### 5. `app/routes.py` — GET /todos
- Add query param `overdue: bool | None = None` alongside `done`, with a description string so it shows in the OpenAPI docs.
- Compute `now` once at the top of the handler as naive UTC via a single small helper (put it next to whatever sets `created_at`, or in `routes.py` if that's where it lives) so the definition of "now" exists in exactly one place.
- Build the query with independent, composable clauses: apply the `done` clause if provided, then the `overdue` clause if provided, per decision 4. Do the comparison in SQL, not by filtering Python objects after loading everything.
- No change needed to `POST`, `GET /todos/{id}`, or `DELETE`; `due_at` flows through `TodoCreate` and `TodoOut` automatically.

### 6. `tests/test_todos.py`
- Run the existing twelve tests first after steps 1 and 3. Any test that compares a full response body to a literal dict will now fail on the missing `due_at` key; update those to include `"due_at": None` rather than loosening them to partial matches.
- Add a tiny helper that returns "one day ago" and "one day from now" as ISO strings computed from real UTC now. Avoid mocking the clock; relative offsets of a day are far outside any test-run jitter.
- New tests:
  - Create with `due_at` → response echoes it; create without → `due_at` is `null`.
  - Create with an unparseable `due_at` → 422.
  - Create with an aware offset (e.g. `+02:00`) → stored/returned value is the UTC-normalized equivalent.
  - PATCH sets `due_at` on a todo that had none.
  - PATCH with explicit `{"due_at": null}` clears it.
  - PATCH with a body that omits `due_at` leaves the existing value untouched (this is the `exclude_unset` regression guard).
  - `GET /todos?overdue=true` with a seeded mix — past+not done, past+done, future+not done, no due date — returns only the first.
  - `GET /todos?overdue=false` returns exactly the other three.
  - `GET /todos?overdue=true&done=true` returns an empty list.
  - `GET /todos` with no params still returns everything (no accidental filtering when both params are `None`).

### 7. Rollout
- Ship in this order: merge, run `alembic upgrade head` in production, then deploy the new app code. The order is safe in both directions briefly (old code ignores the new nullable column; new code would 500 on the missing column, so migrate first).
- `app/db.py` needs no changes.

## Things intentionally left out
- A computed `is_overdue` boolean on `TodoOut`. Easy to add later; not required by the ask, and it would duplicate the filter definition in a second place.
- Sorting by `due_at`. Separate feature.
