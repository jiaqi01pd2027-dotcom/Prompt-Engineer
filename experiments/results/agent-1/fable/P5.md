# Implementation plan: optional due date + `overdue` filter

## 0. Decisions to lock before coding

Settle these first so every file agrees; each one shows up in the tests below.

- **Column name and type:** `due_date`, nullable datetime, stored and compared in UTC exactly the same way `created_at` already is. Use a datetime rather than a calendar date so "in the past" has one unambiguous meaning. No default, no index (the table is tiny and SQLite; add an index later only if list queries get slow).
- **Overdue definition:** `due_date IS NOT NULL AND due_date < now_utc AND done = false`. Strictly less-than: a todo due exactly "now" is not yet overdue.
- **`now` is computed in Python** once per request (`datetime.now(timezone.utc)`) and passed as a bound parameter, not via SQL `CURRENT_TIMESTAMP`. This keeps the value format identical to what SQLAlchemy writes for stored datetimes, and it lets tests reason about the clock.
- **`overdue=false` means the complement**: done todos, todos with no due date, and todos due in the future. It must be written as an explicit OR (`done = true OR due_date IS NULL OR due_date >= now`), not as `NOT (overdue expression)`. See Risk 1.
- **Combining with `done`:** the two filters AND together. `overdue=true&done=true` is contradictory and simply returns an empty list; no special-case error.
- **Past due dates on create/patch are allowed.** A user may legitimately record something that was already due.
- **Timezone handling on input:** accept ISO-8601 with or without offset; convert offset-aware values to UTC, treat naive values as UTC. Output is always UTC, matching `created_at`.

## 1. `app/models.py`

Add a `due_date` column to the `Todo` model: nullable, `DateTime`, configured with the same timezone settings as `created_at`, with no server or Python default. Nothing else in the model changes. Because the test suite builds tables from the models, this alone makes the column exist in tests.

## 2. New migration: `alembic/versions/0002_add_due_date_to_todos.py`

- Set `down_revision` to the revision id of `0001_create_todos.py` (read it from that file; do not guess).
- `upgrade`: add the nullable `due_date` datetime column to `todos`. SQLite supports `ALTER TABLE ... ADD COLUMN` for a nullable column with no constraint, so a plain `add_column` is fine here.
- `downgrade`: drop the column inside a `batch_alter_table` block. SQLite only gained native `DROP COLUMN` in 3.35, and batch mode works on every version by rebuilding the table.
- Verify locally: run `alembic upgrade head` against a copy of `todo.db`, inspect the schema (`sqlite3 todo.db ".schema todos"`) and confirm the column is present and nullable; then run `alembic downgrade -1` and `alembic upgrade head` again to prove reversibility. Confirm existing rows survive with `due_date` NULL.

## 3. `app/schemas.py`

- `TodoCreate`: add optional `due_date` defaulting to `None`.
- `TodoUpdate`: add optional `due_date` defaulting to `None`. The route (step 4) will distinguish "field omitted" from "field explicitly null" so that null clears the date.
- `TodoOut`: add `due_date` as an optional datetime so it serializes as `null` when unset.
- Add a validator (shared between `TodoCreate` and `TodoUpdate`, or on a small mixin) that normalizes incoming datetimes to UTC per Decision 0. Keep it as a validator on the schema rather than logic in the route so both endpoints behave identically.

## 4. `app/routes.py`

- **POST /todos**: pass `due_date` from the request body through to the model constructor. If the handler currently builds the model from explicit fields, add the new one; if it uses `model_dump`, nothing changes beyond the schema.
- **PATCH /todos/{id}**: make sure updates are applied from `model_dump(exclude_unset=True)` (or the equivalent already in use). With that, a body of `{"due_date": null}` includes the key and sets the column to NULL, while a body that omits `due_date` leaves it untouched. If the existing patch code skips `None` values (a common pattern for title/done), it will silently ignore the clear request; fix that so only unset fields are skipped.
- **GET /todos**: add an optional boolean query parameter `overdue` alongside the existing `done` parameter. Compute `now` once at the top of the handler. When `overdue` is true, add the overdue condition from Decision 0 to the query; when false, add the explicit complement; when omitted, add nothing. Keep the existing `done` filter as-is and let both conditions AND together.
- **GET /todos/{id}** and **DELETE**: no changes; `TodoOut` already carries the new field.

`app/db.py` needs no changes.

## 5. `tests/test_todos.py`

Existing twelve tests should pass unchanged; that is the backward-compatibility check. Add the following cases. To avoid time-based flakiness, build due dates as "now minus one day" and "now plus one day" rather than anything near the boundary.

Create / read:
1. Create with a `due_date`; response includes it and GET /todos/{id} returns the same value.
2. Create without `due_date`; response has `due_date: null`.
3. Create with a malformed `due_date` string; expect 422.
4. Create with a due date carrying a non-UTC offset; response shows the UTC equivalent.
5. Create with a past due date succeeds (no rejection).

Patch:
6. Patch a todo that has no due date to set one; verify via GET.
7. Patch with `{"due_date": null}` clears an existing due date.
8. Patch only `title` on a todo with a due date; due date is unchanged (proves omitted vs null is handled).

Overdue filter (seed four todos in one setup: past-due not done, past-due done, future-due not done, no due date not done):
9. `overdue=true` returns only the past-due-not-done todo.
10. `overdue=false` returns the other three, and specifically includes the no-due-date todo (guards Risk 1).
11. No `overdue` param returns all four (unchanged default behaviour).
12. `overdue=true&done=false` returns the same single todo as case 9.
13. `overdue=true&done=true` returns an empty list.
14. `overdue=false&done=true` returns only the past-due done todo.
15. A todo that was overdue stops appearing in `overdue=true` after it is patched to `done: true`.
16. `overdue=maybe` (non-boolean) returns 422.

## 7. Risks and how to handle them

**Risk 1: SQL NULL semantics silently drop rows from `overdue=false`.** If the complement is written as `NOT (due_date < now AND done = false)`, rows with a NULL `due_date` evaluate to NULL, not true, and vanish from the "not overdue" list. Handle by writing the complement as the explicit three-way OR in Decision 0, and by keeping test case 10, which fails if anyone later "simplifies" the expression.

**Risk 2: Timezone mismatch between stored values and the comparison bound.** SQLite stores datetimes as text and compares them lexically, so an aware `now` compared against naive stored strings, or values stored in local time, gives wrong results that tests near the boundary will not catch. Handle by normalizing everything to UTC at the schema layer, generating `now` in UTC in Python, and mirroring whatever convention `created_at` already uses rather than inventing a second one. Test case 4 covers the input side.

**Risk 3: Model and migration drift.** The test suite creates tables from the models, so a wrong or missing migration passes CI and only breaks in production at `alembic upgrade head`. Handle with the manual round-trip in step 2, and note in the PR description that it was done. If this bites again later, a follow-up could add a test that runs the migrations against a temp SQLite file and compares against the model metadata, but that is out of scope here.

**Risk 4: PATCH cannot clear a due date.** If the existing update handler filters out `None` values, `{"due_date": null}` becomes a no-op and users have no way to remove a date. Handle by switching to `exclude_unset` semantics as in step 4; test case 7 fails if this regresses.
