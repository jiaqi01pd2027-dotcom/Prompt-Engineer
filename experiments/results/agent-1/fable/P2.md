# Implementation plan: optional due date + `overdue` filter

## Decisions made up front (do not re-decide these while implementing)

- **Column/field name:** `due_at`. It is a full datetime, not a calendar date, because "in the past" needs a time-of-day comparison and it keeps the naming consistent with `created_at`.
- **Nullable.** A todo with no `due_at` is never overdue.
- **Timezone convention:** everything is UTC. Before touching any code, open `app/models.py` and check exactly how `created_at` is stored (timezone-aware `DateTime(timezone=True)` vs naive UTC). Store `due_at` the same way. SQLite does not preserve tzinfo, so mixing naive and aware datetimes will raise `TypeError: can't compare offset-naive and offset-aware datetimes` in the filter. Pick the convention `created_at` already uses and apply it everywhere below.
- **Overdue definition (exact):** `due_at IS NOT NULL AND due_at < now_utc AND done = false`.
- **"Now" is computed in Python** (`datetime.now(timezone.utc)`, normalized to the storage convention) and passed into the query, not computed with SQL functions. This keeps behavior identical between SQLite in tests and any future database, and makes tests deterministic.

## Step 1: Model (`app/models.py`)

1. Add a `due_at` column to the `Todo` model: `DateTime`, nullable, no default. Match the `timezone=` argument used by `created_at`.
2. Nothing else changes. Because the test suite creates tables from the models, this step alone makes the column exist in tests.

## Step 2: Schemas (`app/schemas.py`)

1. `TodoCreate`: add `due_at` as an optional datetime, default `None`.
2. `TodoUpdate`: add `due_at` as an optional datetime, default `None`. Important: a PATCH must be able to *clear* a due date by sending `"due_at": null`, which is different from omitting the field. When applying the update in the route (Step 4), use `exclude_unset=True` when dumping the model so "not sent" and "sent as null" are distinguishable. Do not filter out `None` values.
3. `TodoOut`: add `due_at` as optional datetime so it appears in every response, as `null` when unset.
4. Add a validator (on both `TodoCreate` and `TodoUpdate`) that normalizes incoming datetimes to the storage convention: if the client sends a value with an offset, convert it to UTC; if it sends a naive value, treat it as UTC. Then either keep it aware or strip tzinfo, matching the `created_at` convention from the decisions section. Pydantic already rejects unparseable strings with a 422, so no extra validation is needed for format.
5. Decide and document in a comment: past due dates are allowed on create/update (a user can legitimately record something that was already due). Do not add a "must be in the future" rule.

## Step 3: Alembic migration (`alembic/versions/`)

1. Create `0002_add_due_at_to_todos.py` with `down_revision` pointing at the `0001` revision id (copy the exact revision string from `0001_create_todos.py`, do not guess it).
2. `upgrade()`: add the nullable `due_at` column to `todos`. No server default is needed; existing rows get `NULL`, which is correct.
3. `downgrade()`: drop the column. Because this is SQLite, wrap the drop in Alembic's batch mode (`batch_alter_table`) so it works on SQLite versions that lack native `DROP COLUMN`. Use batch mode for the add as well for symmetry; it is harmless.
4. Verify locally: copy the existing `todo.db` to a scratch file, point the Alembic URL at the copy, run `alembic upgrade head`, confirm the column exists with `sqlite3 <copy> ".schema todos"`, then run `alembic downgrade -1` and confirm it is gone, then `upgrade head` again. Do not run migrations against the real `todo.db` during development.
5. Remember: the test suite never runs migrations, so a passing test suite does not prove the migration works. Step 3.4 is the only verification of it.

## Step 4: Routes (`app/routes.py`)

1. `POST /todos`: pass `due_at` from `TodoCreate` through to the model when constructing the row. Nothing else changes.
2. `PATCH /todos/{id}`: when applying fields from `TodoUpdate`, dump with `exclude_unset=True` and set every key present, including keys whose value is `None`. Confirm the existing patch code does not already drop `None` values; if it does (for example a `if value is not None` guard), remove that guard, since with `exclude_unset` it is no longer needed and it would make clearing `due_at` impossible.
3. `GET /todos`: add an optional boolean query parameter `overdue`, default `None`, alongside the existing `done` parameter.
   - If `overdue` is `None`: no change to the query.
   - If `overdue` is `True`: add the three conditions from the definition (`due_at` is not null, `due_at < now`, `done` is false), all ANDed.
   - If `overdue` is `False`: add the logical negation: `done` is true OR `due_at` is null OR `due_at >= now`.
   - Compute `now` once at the top of the handler and reuse it for both branches.
   - The `done` and `overdue` filters combine with AND. `overdue=true&done=true` legitimately returns an empty list; do not special-case it.
4. Keep the `done` parameter behavior exactly as it is. Existing tests must stay green without modification.

## Step 5: Tests (`tests/test_todos.py`)

Add these tests. Use fixed datetimes far in the past (e.g. year 2000) and far in the future (e.g. year 2100) rather than "now minus one minute", so tests cannot flake near the boundary and do not need time-freezing libraries.

1. Create a todo with a `due_at`; response echoes it and it round-trips through `GET /todos/{id}`.
2. Create a todo without `due_at`; response has `"due_at": null`.
3. Create with an invalid `due_at` string; expect 422.
4. Create with an offset-bearing timestamp (e.g. `+05:00`); response value equals the UTC-normalized equivalent. This test pins the timezone convention.
5. PATCH sets `due_at` on a todo that had none.
6. PATCH with `"due_at": null` clears an existing due date. This is the test most likely to catch the `exclude_unset` bug.
7. PATCH that omits `due_at` entirely leaves the existing due date unchanged.
8. `overdue=true`: seed four todos: past-due not done (expect included), past-due done (excluded), future-due not done (excluded), no due date not done (excluded). Assert only the first is returned.
9. `overdue=false`: same seed; assert the other three are returned and the first is not.
10. `overdue` omitted: all four returned, confirming no regression to the default list.
11. `overdue=true&done=false`: returns the same as test 8. `overdue=true&done=true`: returns empty.
12. Update the existing list test's expected response shape if it asserts exact keys, since `due_at` is now present on every todo.

Run the full suite; all twelve existing tests plus the new ones must pass.

## Step 6: Wrap-up

1. If the repository has a README or API doc that lists the `GET /todos` query parameters or the todo JSON shape, add `due_at` and `overdue` there.
2. Check FastAPI's generated docs (`/docs`) once locally to confirm `due_at` shows as optional on the request bodies and `overdue` shows as an optional boolean query parameter.
3. Commit in two commits for easier review: (a) migration only, (b) model, schemas, routes, tests. The migration must be reviewable on its own.

## Things that will go wrong if skipped

- Naive/aware datetime mismatch in the overdue comparison (Decisions section, Step 2.4).
- PATCH unable to clear `due_at` because `None` is treated as "not sent" (Step 4.2, Test 6).
- Migration never actually exercised because tests bypass Alembic (Step 3.4).
- Wrong `down_revision` string breaking the migration chain (Step 3.1).
- Boundary flakiness from computing test timestamps relative to "now" (Step 5 preamble).
