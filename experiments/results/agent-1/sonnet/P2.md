# Implementation Plan: Optional Due Date + `overdue` Filter

## 0. Decisions to lock in before writing any code

These aren't obvious from the ticket, so decide them now instead of discovering an inconsistency mid-implementation:

1. **Type of `due_date`**: store it as a calendar date (no time-of-day component), not a datetime. A due date is "today," not "today at 14:32." This also sidesteps time-zone-of-day ambiguity when comparing to "now."
2. **What "in the past" means**: compare the stored `due_date` against **today's UTC date** (`datetime.utcnow().date()`), consistent with how `created_at` already uses UTC. A todo due *today* is not overdue yet — only `due_date < today` counts.
3. **`overdue` param semantics**: `GET /todos?overdue=true` returns only todos where `due_date < today AND done is false`. `overdue=false` returns everything else (todos that are done, have no due date, or have a future/today due date). This mirrors the existing symmetric behavior of the `done` filter.
4. **Combining `overdue` with the existing `done` filter**: apply both as AND when both are supplied. Don't special-case it — `done=true&overdue=true` will simply return an empty result, and that's correct, not a bug.
5. **Clearing a due date via PATCH**: `TodoUpdate` must distinguish "field not sent" from "field explicitly set to null," the same way the endpoint currently must already handle `title`/`done` as optional-but-independently-settable. Confirm the existing PATCH handler builds its update dict with something like "exclude unset fields" — if so, follow that exact pattern for `due_date` so `{"due_date": null}` clears it while omitting the key leaves it untouched.

Write these five decisions into the PR description or a code comment near the route — the next person touching this code needs them spelled out.

## 1. `app/models.py`

1. Import the `Date` type from SQLAlchemy.
2. Add a new nullable column `due_date` to the `Todo` model, typed as `Date`, no default value (defaults to `NULL`/`None` for existing and new rows that don't specify one).
3. (Optional, not required for correctness) Consider whether the `todos` table will be large enough that filtering on `due_date`/`done` needs an index. If not sure, skip it — don't add speculative indexes.

## 2. New Alembic migration

1. Generate a new revision file in `alembic/versions/`, e.g. `0002_add_due_date_to_todos.py`, with `down_revision` pointing at the existing `0001_create_todos` revision.
2. In `upgrade()`, add a single nullable `due_date` column (`Date` type) to the `todos` table. No default, no backfill needed since it's nullable and existing rows should end up as `NULL`.
3. In `downgrade()`, drop the `due_date` column.
4. Do **not** touch `app/db.py` — it only holds the engine/session factory and doesn't need changes for a nullable column addition.

## 3. `app/schemas.py`

1. Import `date` from `datetime` (or `Optional[date]` via `typing`).
2. `TodoCreate`: add `due_date: Optional[date] = None`.
3. `TodoUpdate`: add `due_date: Optional[date] = None`, and make sure the route continues to use the "only apply fields that were actually present in the request body" pattern (see decision #5 above) so this new field behaves consistently with `title`/`done`.
4. `TodoOut`: add `due_date: Optional[date] = None` so it's returned in every response (POST, GET single, GET list, PATCH).

## 4. `app/routes.py`

1. Add a new optional query parameter `overdue: bool | None = None` to the `GET /todos` handler, alongside the existing `done` param.
2. At the top of the handler, compute `today = datetime.utcnow().date()` once (import `datetime` if not already imported).
3. Build the query incrementally:
   - Start from the base `select`/query on `Todo`.
   - If `done` is provided, filter `Todo.done == done` (existing behavior, unchanged).
   - If `overdue is True`, filter `Todo.due_date.isnot(None)`, `Todo.due_date < today`, and `Todo.done == False`.
   - If `overdue is False`, filter the negation: `Todo.due_date.is_(None) OR Todo.due_date >= today OR Todo.done == True`.
   - If `overdue` is not provided, don't touch the query at all.
4. Leave `POST /todos`, `GET /todos/{id}`, `PATCH /todos/{id}`, and `DELETE /todos/{id}` route signatures unchanged — `due_date` flows through automatically via the schema changes in step 3, since `POST` already passes the full `TodoCreate` payload into the model constructor and `PATCH` already applies whatever fields are set on `TodoUpdate`.
5. Update the route's docstring / OpenAPI description for `GET /todos` to document the new `overdue` param and its semantics (this becomes the app's user-facing API docs via FastAPI's auto-generated schema, so it's not optional busywork).

## 5. `tests/test_todos.py`

Add these cases; don't just add one happy-path test and call it done:

1. **Create with due date**: POST a todo with `due_date` set; assert the response echoes it back correctly (and as a plain date string, not a datetime).
2. **Create without due date (backward compatibility)**: POST a todo omitting `due_date`; assert the response has `due_date: null` and the existing create test still passes unmodified.
3. **List filtered by `overdue=true`**: seed four todos — (a) past due date, not done → should appear; (b) past due date, done=true → should NOT appear; (c) future due date, not done → should NOT appear; (d) no due date, not done → should NOT appear. Assert the response contains exactly (a).
4. **List filtered by `overdue=false`**: using the same seed data, assert the response contains (b), (c), and (d) but not (a).
5. **List with no `overdue` param**: assert behavior is unchanged from before this change (all four appear, subject to any `done` filter).
6. **Combining `done` and `overdue`**: e.g. `done=true&overdue=true` returns an empty list (sanity check on decision #4).
7. **PATCH sets a due date** on a todo that had none.
8. **PATCH explicitly clears a due date** (`{"due_date": null}`) on a todo that had one.
9. **PATCH omitting `due_date` leaves the existing value untouched** — this is the test most likely to catch a mistake in step 4's schema/route wiring, so don't skip it.
10. Check whether the file has any shared helper function for constructing a todo (e.g. a `create_todo(...)` helper used across multiple tests). If so, give it an optional `due_date=None` parameter so existing calls don't need to change.
11. Run the full existing suite and confirm all twelve original tests are still green, unmodified in behavior.

## 6. Manual verification (outside pytest)

The test suite builds tables directly from the models and never runs Alembic, so the migration itself is unverified by `pytest`. Before calling this done:

1. Run `alembic upgrade head` against a scratch copy of `todo.db` (or a fresh temp SQLite file) and confirm it applies cleanly with no errors.
2. Inspect the resulting schema (e.g. `.schema todos` in the `sqlite3` CLI) and confirm `due_date` exists, is nullable, and has no unexpected default.
3. Run `alembic downgrade -1` against that same scratch DB and confirm the column is removed cleanly, then `alembic upgrade head` again to leave it in a known-good state.
4. Start the app locally and manually exercise: create a todo with a past due date and `done=false`, hit `GET /todos?overdue=true` and confirm it shows up; mark it done via PATCH; hit the same endpoint again and confirm it disappears.
5. Run the full `pytest` suite one final time after all changes to confirm nothing regressed.
