Implementation Plan: Optional Due Date + Overdue Filter for Todos

Answers assumed: `due_date` is optional/nullable datetime, sent/returned as ISO-8601 (offset allowed), stored in UTC (naive inputs treated as UTC), `overdue` means `due_date < now(UTC) AND done is false` (null due dates never overdue), `?overdue=true` combinable with existing `?done=`, requires a new Alembic migration, tests build tables from models (not migrations) so the migration and model change are independently verifiable.

## 1. Model change (`app/models.py`)

- Add `due_date` column to the `todos` table/model: nullable datetime, no default, timezone-aware storage (SQLAlchemy `DateTime(timezone=True)` or equivalent for the SQLite dialect in use).
- Confirm SQLite's handling of `DateTime(timezone=True)` under SQLAlchemy 2.0 (SQLite has no native tz-aware column type — SQLAlchemy stores it as naive UTC under the hood). Decide and document the convention: values are always persisted as naive UTC in the DB, and conversion to/from timezone-aware Python `datetime` happens at the schema/service boundary, not in the model layer.

## 2. Schema changes (`app/schemas.py`)

- `TodoCreate`: add optional `due_date: datetime | None = None`.
- `TodoUpdate`: add optional `due_date: datetime | None = None` (already has optional-field pattern for `done`); needs to distinguish "field omitted" from "field explicitly set to null" so PATCH can clear the due date — confirm the existing `TodoUpdate` mechanism (e.g. `exclude_unset` in routes) supports this, and reuse the same pattern for `due_date`.
- `TodoOut`: add `due_date: datetime | None`.
- Add a validator (Pydantic v2 `field_validator` or equivalent) on the incoming `due_date` field for `TodoCreate`/`TodoUpdate` that:
  - Accepts ISO-8601 strings with or without offset (Pydantic's datetime parsing already does this).
  - If the parsed value is naive (no tzinfo), attaches UTC.
  - If the parsed value has an offset, converts it to UTC.
  - Ensures the value stored/passed onward is always UTC-aware (or a consistent internal representation), so route/service logic never has to re-check timezone-ness.
- Confirm serialization of `TodoOut.due_date` back to clients renders as an ISO-8601 string with explicit UTC offset (e.g. `Z` or `+00:00`) so clients see a well-formed instant.

## 3. Route/query changes (`app/routes.py`)

- POST /todos: pass `due_date` from `TodoCreate` through to the created model instance.
- PATCH /todos/{id}: include `due_date` in the set of updatable fields, using the same "only touch fields explicitly present in the request" logic already used for `title`/`done`, so that:
  - Omitting `due_date` leaves the existing value untouched.
  - Explicitly sending `due_date: null` clears it.
- GET /todos:
  - Add an optional `overdue: bool | None` query parameter alongside the existing `done` parameter.
  - When `overdue=true`, add a filter clause: `due_date IS NOT NULL AND due_date < <current UTC time> AND done == false`.
  - Decide and document behavior for `overdue=false` (either "no additional filter" or "explicitly excludes overdue items" — pick one and be consistent; recommend: only `overdue=true` triggers filtering, absence/false is a no-op, matching how `done` currently behaves if `done` follows the same "absence means no filter" convention — verify against current `done` param semantics first).
  - Ensure `overdue` and `done` filters combine with AND, not override each other, since they must be usable together per requirements.
  - Source "current UTC time" from a single, mockable/injectable place (e.g. a small `now_utc()` helper or `datetime.now(timezone.utc)` called directly) so tests can control or reason about the boundary reliably rather than each call site inventing its own time source.

## 4. Migration (`alembic/versions/`)

- Add a new revision (e.g. `0002_add_due_date_to_todos.py`) with `down_revision` pointing to `0001_create_todos`.
- `upgrade()`: `op.add_column('todos', sa.Column('due_date', sa.DateTime(timezone=True), nullable=True))`.
- `downgrade()`: `op.drop_column('todos', 'due_date')`.
- Confirm the column type used in the migration matches the type used in `app/models.py` exactly, since they are maintained independently (tests use the model directly; production uses the migration) — a mismatch would only surface in production, not in tests.
- Manually verify (outside the test suite, since tests don't run migrations) that `alembic upgrade head` and `alembic downgrade -1` both succeed against a throwaway SQLite DB file.

## 5. Test plan (`tests/test_todos.py`)

Add/extend cases, one assertion-focused test per named scenario:

- `test_create_todo_without_due_date` — POST with no `due_date`; response has `due_date: null`.
- `test_create_todo_with_due_date` — POST with an ISO-8601 `due_date` (include one variant with an explicit non-UTC offset to confirm UTC normalization); response echoes it back correctly (converted to UTC).
- `test_patch_sets_due_date` — PATCH an existing todo (created without one) to add a `due_date`; verify it's persisted and returned.
- `test_patch_clears_due_date` — PATCH a todo that has a `due_date` with `due_date: null`; verify it's cleared (not left untouched).
- `test_patch_without_due_date_field_leaves_existing_value` — PATCH some other field (e.g. `title`) without mentioning `due_date`; verify the existing `due_date` is unchanged (guards against accidental overwrite-with-null bugs from the omitted-vs-null distinction in step 2).
- `test_overdue_filter_includes_past_and_not_done` — todo with `due_date` in the past, `done=false`; appears when `overdue=true`.
- `test_overdue_filter_excludes_done` — todo with `due_date` in the past, `done=true`; does not appear when `overdue=true`.
- `test_overdue_filter_excludes_future_due_date` — todo with `due_date` in the future, `done=false`; does not appear when `overdue=true`.
- `test_overdue_filter_excludes_null_due_date` — todo with no `due_date` at all; does not appear when `overdue=true`, regardless of `done`.
- `test_overdue_combined_with_done_filter` — verify `?overdue=true&done=false` (or whatever combination is meaningful) returns the AND of both filters, not just one.
- Consider a fixed/frozen "now" for these tests (e.g. via `freezegun` or by constructing due dates as clear offsets like `now_utc() - timedelta(days=1)` / `+ timedelta(days=1)` at test run time) rather than hardcoded date literals, so tests don't become time-bomb flaky as the calendar moves forward — recommend the offset-from-now approach since it needs no new test dependency.

## 6. Regression check

- Re-run the full existing test suite (twelve current tests) to confirm the new nullable column and route changes don't break `TodoOut` serialization, existing filters, or CRUD paths that don't reference `due_date`.

## 7. Documentation/consistency pass

- If there's any OpenAPI-facing description or docstring on the GET /todos route documenting the `done` param, update it to also document `overdue` and the combination behavior, since this is the only place API consumers would discover the new query parameter's semantics.
