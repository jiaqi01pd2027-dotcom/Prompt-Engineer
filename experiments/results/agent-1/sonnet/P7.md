## Reasoning

**Layers a new persisted field passes through:** model (`app/models.py`) → migration (`alembic/versions/`) → schemas (`app/schemas.py`, three places: create input, update input, output) → route logic (`app/routes.py`, for both accepting due_date on write and filtering on read) → tests (`tests/test_todos.py`).

**Column shape:** `due_date` must be nullable with no default, since it's optional. Nullable also has to be the answer for `TodoUpdate` semantics: since the field is optional, the API needs a way to distinguish "don't change due_date" from "clear due_date to null" — that's a `PATCH` semantics decision, not just a schema one (typically requires `exclude_unset` on the Pydantic model rather than checking truthiness).

**What "in the past" means on a server:** `created_at` is already stored as UTC, so `due_date` must follow the same convention for comparisons to be meaningful — comparing a naive/local time against a UTC-stored column would silently misclassify rows near midnight or across DST. The "now" used for the overdue comparison must be computed once per request (not per-row) using `datetime.now(timezone.utc)` (or SQLite's UTC equivalent), and the same convention (naive-UTC vs aware-UTC) that `created_at` already uses must be matched exactly, or SQLite/SQLAlchemy comparisons can silently do string comparison instead of datetime comparison. The boundary (`due_date == now`) needs an explicit decision — "in the past" should mean strictly `<`, not `<=`.

**What can go wrong with existing rows:** the migration adds the column to a table that already has rows, so those rows get `NULL` due_date. `NULL < now` evaluates to `NULL`/false in SQL, which is actually the desired behavior (a todo with no due date is never "overdue") — but this has to be verified rather than assumed, since it's easy to instead write a filter that mishandles NULL and either crashes or wrongly includes/excludes those rows. Also: the test suite builds tables straight from models and never runs the migration, so the migration must be written and tested independently of the pytest suite — a broken migration wouldn't be caught by `pytest`.

**Filter interaction:** `overdue=true` already implies `done=false`; the plan needs to state what happens if a caller passes `done=true&overdue=true` simultaneously (either treat as a combinable AND filter that returns nothing, or document/ignore — pick one explicitly rather than leaving it ambiguous).

**Proving the filter works in tests:** need rows in each of the four (due_date, done) quadrants — past+not done (should appear), past+done (should not appear), future+not done (should not appear), null due_date+not done (should not appear) — plus a boundary case, plus confirming existing `done`-filter tests and unfiltered `GET /todos` still pass unchanged, plus a migration-specific check that upgrading a DB with pre-existing rows doesn't error and leaves due_date NULL.

## Plan:

1. **Model change (`app/models.py`)**
   - Add `due_date` column: nullable datetime, timezone-aware/UTC, no server default, no `nullable=False`.
   - Confirm the datetime convention (aware vs naive UTC) matches whatever `created_at` already uses, so later comparisons are apples-to-apples.

2. **Migration (`alembic/versions/`)**
   - Create a new revision (e.g. `0002_add_due_date_to_todos.py`) chained after `0001_create_todos`.
   - `upgrade()`: add nullable `due_date` column to `todos` with no default (existing rows become NULL, no backfill needed).
   - `downgrade()`: drop the column.
   - Note that this migration is not exercised by the test suite (which builds tables from models directly) — it needs its own manual/CI verification against a DB seeded with pre-existing rows (run `alembic upgrade head` against a copy of a populated `todo.db` and confirm no errors and old rows read back with `due_date = NULL`).

3. **Schemas (`app/schemas.py`)**
   - `TodoCreate`: add optional `due_date` (defaults to `None` if omitted).
   - `TodoUpdate`: add optional `due_date`, and confirm the update path can express "clear the due date" (set to `null`) distinctly from "leave unchanged" (field omitted) — this depends on how `TodoUpdate` is consumed in the route (see step 4).
   - `TodoOut`: add `due_date` (nullable) so it round-trips in every response.

4. **Route changes (`app/routes.py`)**
   - `POST /todos`: pass through `due_date` from `TodoCreate` into the new row.
   - `PATCH /todos/{id}`: update `due_date` only when the client actually supplied it in the request body (use "field was set" semantics, e.g. `exclude_unset`, not "field is truthy") so that omitting `due_date` leaves it unchanged, while explicitly sending `due_date: null` clears it.
   - `GET /todos`: add an optional `overdue` query parameter (boolean).
     - Compute one "now" timestamp per request in the same UTC convention as `due_date`/`created_at`.
     - When `overdue=true`, filter to rows where `due_date` is not null, `due_date < now` (strict, not `<=`), and `done is false`.
     - Decide and document the behavior when both `done` and `overdue` are supplied together (e.g. apply both as an AND, which is naturally consistent since overdue already implies not-done); do not leave this unhandled/undefined.
     - Leave existing unfiltered and `done`-only filtering behavior untouched.

5. **Tests (`tests/test_todos.py`)**
   - Create-with-due-date: POST accepts and returns `due_date`; POST without it returns `due_date: null`.
   - Update: PATCH can set a due date on a todo that had none, change an existing one, and explicitly clear it back to null; confirm PATCH without `due_date` in the body leaves the existing value untouched.
   - Overdue filter, one row per case:
     - past due_date + not done → included when `overdue=true`.
     - past due_date + done → excluded.
     - future due_date + not done → excluded.
     - null due_date + not done → excluded.
   - Boundary case: due_date equal to "now" (or a few seconds in the future set right at the edge) is not classified as overdue, matching the strict-`<` decision.
   - Regression: existing `done`-filter tests and unfiltered `GET /todos` still pass with the new column present.
   - Combined-params case: `done=true&overdue=true` returns whatever behavior was decided in step 4 (empty set, most likely) — assert that explicitly so the decision is pinned down by a test rather than left implicit.
   - Use relative offsets from `datetime.now(UTC)` computed inside the test (not hardcoded literal dates) so tests remain valid regardless of when they run.
