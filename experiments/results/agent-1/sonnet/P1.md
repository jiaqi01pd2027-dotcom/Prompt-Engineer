## Implementation Plan: Optional Due Date + `overdue` Filter

### 1. Data model (`app/models.py`)
- Add a `due_date` column to the `Todo` model: nullable datetime, no default (absence means "no due date").
- Store due dates the same way `created_at` is stored — UTC, and decide now whether values are tz-aware or naive-but-UTC-by-convention. Whichever convention `created_at` already uses, make `due_date` follow it exactly, since SQLite has no native tz type and mixing conventions will cause silent comparison bugs later.

### 2. Migration (`alembic/versions/`)
- Add a new revision, e.g. `0002_add_due_date_to_todos.py`, with `down_revision` pointing at `0001_create_todos`.
- `upgrade()`: add `due_date` as a nullable column (no server default needed since it's optional and existing rows should simply have `NULL`).
- `downgrade()`: drop the column.
- Note for the developer: this migration must be applied via `alembic upgrade head` in any real environment; it has no effect on the test suite (see step 5), so don't rely on running it as a substitute for updating the model.

### 3. Schemas (`app/schemas.py`)
- `TodoCreate`: add an optional `due_date` field (default `None`).
- `TodoUpdate`: add an optional `due_date` field. Since this schema already supports partial updates (title/done optional), decide and document how "field omitted" is distinguished from "field explicitly set to null" (i.e., clearing a due date) — this should follow whatever pattern the existing PATCH handler already uses for optional fields, applied consistently to `due_date`.
- `TodoOut`: add `due_date` to the response model so it's returned on all read/write endpoints.

### 4. Routes — create/update (`app/routes.py`)
- `POST /todos`: persist `due_date` from `TodoCreate` if provided.
- `PATCH /todos/{id}`: apply `due_date` updates using the same "only touch fields that were actually sent" logic used for `title`/`done`, including the ability to explicitly clear a due date back to `NULL`.

### 5. Routes — `GET /todos` overdue filter (`app/routes.py`)
- Add a new optional query parameter, e.g. `overdue: bool | None = None`.
- Define "overdue" precisely: `due_date IS NOT NULL AND due_date < now() AND done = false`. Compute "now" once per request in the same UTC convention chosen in step 1.
- Decide and document the interaction with the existing `done` query parameter rather than leaving it implicit:
  - Since overdue already implies `done = false`, if a caller passes `overdue=true&done=true`, the query is internally contradictory — decide whether to (a) let the filters AND together and return an empty list, or (b) treat `overdue` as taking precedence and ignore `done` in that case. Recommend (a) for simplicity/predictability, but write down the choice so it's testable.
  - `overdue=false` should mean "not overdue" (i.e., either no due date, due date in the future, or already done) — confirm this is the desired semantics before implementing, since "false" filters are easy to get backwards.
- Build the filter as an additional SQLAlchemy `where` clause composed with the existing `done` filter logic, rather than a separate code path, to keep the query construction consistent.

### 6. Database layer (`app/db.py`)
- No changes expected here — table creation continues to come from the models (for tests) and from Alembic (for production), and `get_db` is unaffected. Confirm during implementation that no schema-specific logic leaked into this file.

### 7. Tests (`tests/test_todos.py`)
Extend the suite (the in-memory SQLite test DB is created from `app/models.py`, so no migration step is needed for tests — just make sure the model change alone is sufficient):
- Create a todo with a `due_date` and verify it round-trips through `TodoOut`.
- Create a todo without a `due_date` and verify it's `null` in the response.
- PATCH a todo to add a `due_date`, then PATCH again to clear it back to `null`; verify both operations.
- `GET /todos?overdue=true` returns only todos whose `due_date` is in the past and `done` is false.
- A past-due but completed todo (`done=true`) must NOT appear under `overdue=true`.
- A todo with a future `due_date` must NOT appear under `overdue=true`.
- A todo with no `due_date` must NOT appear under `overdue=true` (and should appear under `overdue=false`, per the semantics chosen in step 5).
- A test covering the combined `overdue=true&done=...` case per the decision made in step 5.
- Existing 12 tests should keep passing unmodified except wherever they assert on the exact shape of `TodoOut` (they may need a `due_date: None` addition to expected response bodies).

### 8. Verification
- Run the full `pytest` suite.
- Separately (outside the test suite), run `alembic upgrade head` against a scratch SQLite file to confirm the new migration applies cleanly on top of `0001`, and that `alembic downgrade -1` reverts it without error.
