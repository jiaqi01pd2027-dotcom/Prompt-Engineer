1. alembic/versions/0002_add_due_date_to_todos.py: New revision with `down_revision` pointing at 0001. In `upgrade()`, use `op.batch_alter_table("todos")` to add a nullable `due_date` column (DateTime, no server default, no default value) so every existing row gets NULL without a table rewrite failing on SQLite. In `downgrade()`, use the same batch pattern to drop the column.
2. app/models.py: Add `due_date = Column(DateTime, nullable=True)` to the `Todo` model, right after `created_at`. No default and no `onupdate` — value is always supplied by the client, never generated server-side. Store it the same way `created_at` is stored (naive UTC), so comparisons stay consistent.
3. app/schemas.py: Add `due_date: datetime | None = None` to `TodoCreate`, `TodoUpdate`, and `TodoOut`. On `TodoCreate` and `TodoUpdate`, add a field validator for `due_date` that: rejects a naive (no offset/`Z`) datetime with a 422-triggering `ValueError`, and converts any timezone-aware value to UTC then strips the tzinfo before it's handed to the DB layer — this is what makes web-UI and mobile-app timestamps from different zones comparable later.
4. app/routes.py: In `POST /todos`, pass `due_date` through when constructing the `Todo` row (it already flows through if the handler builds the model from the full `TodoCreate` object — verify it isn't field-by-field). In `PATCH /todos/{id}`, build the update dict with `TodoUpdate.model_dump(exclude_unset=True)` (or equivalent) so an omitted `due_date` leaves the stored value untouched, while an explicit `"due_date": null` in the request body clears it to NULL. In `GET /todos`, add an optional query param `overdue: bool | None = None`; when `overdue=True`, AND an additional filter onto the existing query: `due_date IS NOT NULL AND due_date < <current UTC time, naive> AND done == False`. Leave the existing `done` query param filter as-is so the two params compose with AND (no special-casing needed for the case where they contradict — the query legitimately returns zero rows).
5. tests/test_todos.py: Add the new test cases listed below, reusing the existing TestClient fixture. No changes to test infrastructure are needed since tests already build tables from the models, not from Alembic.

Risks:
- Clients in different time zones sending inconsistent ISO-8601 offsets, causing wrong overdue results: normalize every incoming `due_date` to naive UTC in the schemas.py validator, and compare against `datetime.now(timezone.utc)` (also stripped to naive) in routes.py, with a dedicated test asserting a non-UTC-offset timestamp is stored and compared correctly.
- SQLite's limited ALTER TABLE support breaking the migration against the real `todo.db`: use `batch_alter_table` in the migration (step 1) and run `alembic upgrade head` against a copy of the production `todo.db` before deploying, to catch failures before they hit real data.
- PATCH ambiguity between "field omitted" and "field explicitly set to null" silently wiping a due date the client didn't intend to touch: use `exclude_unset` when building the PATCH update payload (step 4), and lock the two behaviors in with the `test_patch_todo_explicit_null_clears_due_date` and `test_patch_todo_omitting_due_date_leaves_existing_value_unchanged` tests.
