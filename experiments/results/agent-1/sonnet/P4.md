# Implementation Plan: Optional Due Date + `overdue` Filter

## Scope

Add an optional `due_date` field to each todo, and support `GET /todos?overdue=true` to return todos whose `due_date` is in the past and whose `done` is `false`. Everything happens in the five existing files plus one new Alembic migration; no new dependencies, services, or frontend work.

## Step 1 — Add the database migration first

Create `alembic/versions/0002_add_due_date_to_todos.py`, chained via `down_revision` to `0001_create_todos`.

- `upgrade()`: add a new column `due_date` to the `todos` table — a nullable datetime column with no server-side default, so every existing row gets `NULL` and the migration is non-destructive on tables that already have data.
- `downgrade()`: drop the `due_date` column, restoring the table to its `0001` shape.
- Because SQLite has limited `ALTER TABLE` support, verify the migration only adds a column (no rename/constraint change) so Alembic can express it as a plain `ADD COLUMN` without needing batch-mode table rebuilding. If Alembic's autogenerate/batch mode is not already configured for this project's `env.py`, confirm this migration still applies cleanly against the SQLite file, since `alembic upgrade head` is what production runs.

## Step 2 — Update the model

In `app/models.py`, add a `due_date` column to the `todos` table mapping: a nullable datetime column, stored in UTC (consistent with how `created_at` is already handled), with no default value (it stays `None` unless the client supplies one). This is the source of truth the test suite uses directly (tests build tables from models, not migrations), so this change and Step 1 must describe the identical column shape.

## Step 3 — Update the schemas

In `app/schemas.py`:

- `TodoCreate`: add an optional `due_date` field (defaulting to `None`) so creation without a due date keeps working unchanged.
- `TodoUpdate`: add an optional `due_date` field. Since this model already supports partial updates, confirm the route logic (Step 4) distinguishes "field omitted" from "field explicitly set to null" so a client can clear a due date via PATCH, not just set one.
- `TodoOut`: add `due_date` (optional) so it's returned on all read/write responses.

## Step 4 — Update the routes

In `app/routes.py`:

- `POST /todos`: pass the incoming `due_date` (if any) through to the created row.
- `PATCH /todos/{id}`: when `due_date` is present in the update payload, apply it, including the case where it's explicitly set to `null` to clear a previously-set due date. Use the same "only touch fields that were actually sent" mechanism already used for `title`/`done`.
- `GET /todos`: add a new optional query parameter, `overdue` (boolean). When `overdue=true`, filter the query to rows where `due_date` is not null, `due_date` is earlier than the current UTC time (computed once per request, not per row, so all rows are compared against the same instant), and `done` is `false`. Decide and document the behavior when both `done` and `overdue` are supplied together — treat them as independent, ANDed filters (e.g., `done=true&overdue=true` legitimately returns an empty list rather than raising an error), so the two params compose predictably instead of one silently overriding the other.
- No changes needed to `app/db.py` — the existing engine/session/`get_db` dependency is unaffected by an added column.

## Step 5 — Tests to add to `tests/test_todos.py`

Name each case explicitly rather than a single "add tests" item:

1. Creating a todo without `due_date` still succeeds and the response has `due_date: null`.
2. Creating a todo with a `due_date` persists it and returns the same value in the response.
3. `GET /todos?overdue=true` includes a todo whose `due_date` is in the past and `done=false`.
4. `GET /todos?overdue=true` excludes a todo whose `due_date` is in the past but `done=true`.
5. `GET /todos?overdue=true` excludes a todo whose `due_date` is in the future.
6. `GET /todos?overdue=true` excludes a todo whose `due_date` is `null`.
7. `PATCH /todos/{id}` can set a `due_date` on a todo that previously had none.
8. `PATCH /todos/{id}` can clear an existing `due_date` back to `null`.
9. `GET /todos` with no `overdue` param returns the same results as before this change (regression check that the new filter is opt-in and doesn't affect default listing).
10. `GET /todos?overdue=false` (or omitted) does not accidentally exclude non-overdue todos — confirms the filter is only applied when explicitly requested/true.

## Risks

- **Timezone/naive-vs-aware datetime mismatch**: SQLite has no native datetime type — it stores whatever string/ISO format is written and does not enforce timezone awareness. If `due_date` values are ever stored or compared inconsistently (e.g., a naive datetime compared against `datetime.now(timezone.utc)`), the `overdue` filter can silently misclassify rows near the boundary or across environments with different local timezones. Mitigation: standardize on storing and comparing UTC-naive (or consistently UTC-aware) datetimes everywhere `due_date` and the "now" comparison are constructed — mirror however `created_at` already handles this in `app/models.py` — and cover the boundary explicitly with a test using a `due_date` set a few seconds in the past/future rather than relying on wall-clock timing during test runs.
