# Implementation Plan: Optional Due Date + `overdue` Filter

## 1. Design decisions to lock in before coding

1. **Storage representation**: store `due_date` as a timezone-aware UTC `datetime` in the database (consistent with how `created_at` is already handled). All incoming ISO-8601 strings — regardless of which offset the web UI or mobile app sends — get normalized to UTC before persisting, so "is it in the past" comparisons never depend on client timezone.
2. **Nullability**: `due_date` is nullable at the DB level, schema level, and API level. This is what makes existing rows (and clients that never set it) keep working with no backfill required.
3. **Overdue semantics**: a todo is overdue only if `due_date IS NOT NULL AND due_date < now(UTC) AND done = false`. Todos with no due date are never overdue, and a `null` `due_date` must not accidentally satisfy any comparison.
4. **`overdue` query param semantics**: decide and document behavior for `?overdue=false` and for combining `?overdue=true&done=...` (e.g. `overdue=true` implies `done=false` already, so an explicit `done=true` combined with `overdue=true` should yield an empty result rather than silently ignoring one filter). Write this down so the route logic and tests agree.
5. **Clock source**: pick one place (e.g. a small helper) that returns "now" as UTC, so the route and any future code compute overdue consistently and it's easy to mock in tests.

## 2. Data model (`app/models.py`)

1. Add a `due_date` column: nullable, timezone-aware datetime type, no default (defaults to `NULL`).
2. Do not touch `created_at` or any existing column — this must be a strictly additive change.

## 3. Database migration (`alembic/versions/`)

1. Create a new revision (e.g. `0002_add_due_date_to_todos.py`) chained onto `0001_create_todos`.
2. `upgrade()`: add the `due_date` column as nullable with no server default, using SQLite-safe batch mode (`op.batch_alter_table`) since SQLite's `ALTER TABLE` support is limited and Alembic's batch mode handles it safely regardless of backend.
3. `downgrade()`: drop the column, again via batch mode, for symmetry/rollback.
4. Explicitly do **not** attempt to populate `due_date` for existing rows — leaving it `NULL` is the correct backward-compatible value.
5. Note in the migration or PR description that this must be applied via the team's normal `alembic upgrade head` deploy step, and mention that it's safe to run against the live `todo.db` because it only adds a nullable column.

## 4. Request/response schemas (`app/schemas.py`)

1. `TodoCreate`: add `due_date` as an optional field (default `None`) accepting an ISO-8601 datetime string; document that naive strings (no offset) are rejected or interpreted as UTC — pick one and be explicit, since clients are in different time zones.
2. `TodoUpdate`: add `due_date` as an optional field, following the existing pattern used for `title`/`done` (i.e. distinguishing "field omitted" from "field explicitly set to null") so a client can clear a due date via PATCH by sending `due_date: null`, if that's a capability the team wants — confirm with the API shape agreed and decide whether "clear the due date" is in scope; if not, document that omission is the only supported PATCH behavior for now.
3. `TodoOut`: add `due_date` as an optional field so responses for old rows serialize it as `null`.
4. Ensure the datetime field's validation/serialization normalizes to UTC on the way in and emits a consistent, unambiguous ISO-8601 representation (with explicit offset/`Z`) on the way out, so both the web UI and mobile app can parse it unambiguously.

## 5. Routes (`app/routes.py`)

1. `POST /todos`: pass `due_date` from `TodoCreate` through to the created model instance (defaulting to `None` when absent).
2. `PATCH /todos/{id}`: apply `due_date` the same way other optional-update fields are already applied (only update if provided).
3. `GET /todos`: add an `overdue` optional boolean query parameter alongside the existing `done` parameter.
   - When `overdue=true`, filter to rows where `due_date` is not null, `due_date` is before the current UTC time, and `done` is false.
   - Decide and implement the combination behavior with `done` decided in step 1.5 above.
   - Compute "now" via the shared helper from step 1.5 so it's consistent and testable.
4. `GET /todos/{id}` and `DELETE /todos/{id}`: no behavioral change needed beyond the schema already including `due_date` in the response.

## 6. `app/db.py`

1. No structural change expected; only touch this file if the "current UTC time" helper from step 1.5 is placed here for shared access (alternatively put it in `models.py` or a new small utils module — pick one and be consistent).

## 7. Tests (`tests/test_todos.py`)

Add tests covering, at minimum:
1. Creating a todo without `due_date` still works and returns `due_date: null` (regression test for backward compatibility).
2. Creating a todo with a valid ISO-8601 `due_date` (including a non-UTC offset) returns it correctly normalized.
3. Rejecting or correctly handling a malformed/naive datetime string, per the decision in step 4.4.
4. Patching a todo to add/change a `due_date`.
5. Patching a todo to clear `due_date` (if that behavior was included per step 4.2).
6. `GET /todos?overdue=true` returns only todos with a past `due_date` and `done=false`.
7. `GET /todos?overdue=true` excludes todos with `due_date` in the future.
8. `GET /todos?overdue=true` excludes todos with no `due_date` at all.
9. `GET /todos?overdue=true` excludes todos that are overdue by date but already `done=true`.
10. `GET /todos?overdue=false` (and/or the param's absence) behaves as decided in step 1.4.
11. A way to control "now" in the overdue tests deterministically (e.g. by inserting rows with fixed due dates far in the past/future rather than depending on wall-clock time at test run), so tests are not flaky.
12. Since the suite builds tables directly from `models.py` in an in-memory DB rather than running Alembic, confirm no test depends on the migration file itself — the migration's correctness is a separate manual/deploy-time concern, not something pytest verifies. Note this explicitly so nobody assumes CI is exercising the migration.

## 8. Manual/deploy-time verification (not covered by pytest)

1. Run `alembic upgrade head` against a copy of the real `todo.db` (or a staging copy) before deploying, and confirm existing rows come back from `GET /todos` unchanged with `due_date: null`.
2. Spot-check that a request from a client in a non-UTC timezone (simulate both a positive and negative offset) round-trips through create → get → overdue filter correctly.

## 9. Rollout order

1. Land model + migration first (additive, safe on its own).
2. Land schema + route changes together with tests.
3. Deploy: `alembic upgrade head` runs automatically per the team's existing deploy process, then the new API code goes live — order matters only in that the column must exist before the new code that reads/writes it runs, which the standard "migrate then deploy" sequence already guarantees.
