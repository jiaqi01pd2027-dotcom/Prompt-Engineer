# Implementation plan: optional due date + `overdue` filter

## Decisions to make before writing code

These shape several files at once; settle them first.

1. **Column name and type.** `due_at`, nullable `DateTime`, to match the existing `created_at` naming. Nullable is what makes it optional — no default, no sentinel value.
2. **Timezone representation.** SQLite has no native timezone type, so whatever the app does with `created_at` today is the convention `due_at` must follow. Open `app/models.py` and `app/routes.py` and confirm whether `created_at` is stored as a naive UTC datetime or an aware one, then match it exactly. Mixing the two is the single most likely source of a `TypeError: can't compare offset-naive and offset-aware datetimes` at query time.
3. **Clearing a due date via PATCH.** `TodoUpdate` cannot distinguish "field omitted" from "field explicitly set to `null`" using `Optional[...] = None` alone. Decide now: either (a) treat explicit `null` as "clear the due date" and use `model_dump(exclude_unset=True)` in the PATCH handler so omission is untouched, or (b) declare clearing unsupported. Option (a) is the better API and only costs one line in the handler — but check whether the existing PATCH handler already uses `exclude_unset`; if it uses `exclude_none`, it must change, and that change affects `title`/`done` behavior too.
4. **Semantics of `overdue`.** `due_at` is not null AND `due_at < now` AND `done` is false. Strictly less-than, so a todo due exactly now is not yet overdue. A todo with no due date is never overdue. A done todo is never overdue regardless of date.
5. **`done` and `overdue` together.** Compose them with AND (both filters apply independently). `?done=true&overdue=true` then returns an empty list, which is correct and needs no special-casing. Also decide whether `?overdue=false` should mean "not overdue" or "no filter"; recommend `Optional[bool] = None` where `None` means no filter and `false` means the negation, or restrict to a flag that only filters when true — either is fine, but document it and test it.
6. **Validation on create.** Do not reject past due dates. Backdating is legitimate and the overdue tests depend on it.

## Steps

**Step 1 — `app/models.py`: add the column.**
Add `due_at` as a nullable datetime to the `Todo` model, following the same type and timezone convention as `created_at`. No server default, no index for now (the table is tiny; add an index only if the overdue query later shows up as slow). Nothing else in this file changes.

**Step 2 — `alembic/versions/`: new migration `0002_add_due_at.py`.**
Create a revision with `down_revision` pointing at `0001_create_todos`. Upgrade adds the nullable column to `todos`; because it is nullable with no default, existing rows need no backfill and the operation is a plain `ADD COLUMN`, which SQLite supports natively. Downgrade drops the column — wrap the drop in Alembic's `batch_alter_table` so it works on SQLite versions without native `DROP COLUMN`. Prefer writing the revision by hand over `--autogenerate` unless you can point autogenerate at a database already at `0001`.

**Step 3 — verify the migration separately from the test suite.**
This is the step most likely to be skipped and most likely to bite. The test suite creates tables from the models and never runs Alembic, so a broken or missing migration produces a fully green test run and a broken production deploy. Against a scratch copy of the database (or an empty file database), run `alembic upgrade head`, confirm the column exists, then run `alembic downgrade -1` and `upgrade head` again to confirm the downgrade path works. Optionally run `alembic revision --autogenerate` afterward against the upgraded database and confirm it produces an empty diff — that proves the models and the migration chain agree.

**Step 4 — `app/schemas.py`: extend the three schemas.**
- `TodoCreate`: add an optional `due_at`, defaulting to `None`.
- `TodoUpdate`: add an optional `due_at`, following whatever pattern step 3 of the decisions settled for explicit-null clearing.
- `TodoOut`: add `due_at`. Note this changes the response body of *every* endpoint that returns a todo, which matters for step 7.

If the app stores naive UTC, add a validator that normalizes incoming aware datetimes (Pydantic will happily parse `2026-01-01T12:00:00+09:00`) to UTC and strips the offset before it reaches the ORM. Without this, a client in a non-UTC timezone gets silently wrong overdue results. If the app stores aware datetimes, add the inverse: attach UTC to naive input.

**Step 5 — `app/routes.py`: accept and persist `due_at`.**
- POST `/todos`: pass `due_at` through to the model on create.
- PATCH `/todos/{id}`: apply `due_at` using the update pattern chosen above; make sure clearing to `null` actually writes `NULL` rather than being filtered out as a falsy/None value.
- GET `/todos/{id}` and DELETE: no changes.

**Step 6 — `app/routes.py`: the `overdue` query parameter on GET /todos.**
Add `overdue: bool | None = None` alongside the existing `done` param. Build the query by conditionally appending filter clauses, keeping the existing `done` clause untouched and independent. When `overdue` is true, append the three-part condition from decision 4: `due_at IS NOT NULL`, `due_at < now`, `done` is false. Two details:

- Compute "now" once, at the top of the handler, into a local variable, in the same timezone representation as stored values. Do not use SQLite's `CURRENT_TIMESTAMP` or a SQL-side `now()` — it will not match the app's convention and behaves differently across backends.
- Write the not-done condition as an explicit comparison against false rather than a Python `not`, so it becomes SQL and not a Python-side truth test on a column object.

**Step 7 — `tests/test_todos.py`: fix existing tests, then add new ones.**
First run the twelve existing tests. Any that assert on a whole response dict will now fail because `due_at` was added to `TodoOut`; update those assertions rather than removing the new field from the response.

Then add coverage for:
- Create with a `due_at`; it round-trips in the response and in a subsequent GET.
- Create without `due_at`; it is `null`, not an error.
- PATCH sets a due date on a todo that had none.
- PATCH changes an existing due date.
- PATCH clears a due date to `null` (if decision 3 chose to support it).
- PATCH of `title` alone leaves an existing `due_at` untouched — this is the regression that `exclude_unset` vs `exclude_none` decides, so it is worth its own test.
- `?overdue=true` returns a past-due, not-done todo.
- `?overdue=true` excludes a past-due todo that is done.
- `?overdue=true` excludes a future-due todo.
- `?overdue=true` excludes a todo with no due date.
- Boundary: a todo due a moment in the future is not overdue; one due a moment in the past is. Use offsets from "now" computed in the test rather than hardcoded timestamps, so the suite does not rot.
- `?done=false&overdue=true` composes correctly; `?done=true&overdue=true` returns empty.
- Marking an overdue todo done removes it from the overdue list.
- A due date submitted with a non-UTC offset is interpreted correctly (guards the step 4 normalization).
- Malformed `due_at` returns 422.

**Step 8 — final verification.**
Full test suite green; `alembic upgrade head` clean on a database at `0001`; check `/docs` shows `due_at` on all three schemas and `overdue` on the list endpoint. If the README documents the API surface, add the new field and query parameter there.

## Sequencing note

Steps 1–2 (model + migration) should land together in one commit — a model change without its migration is the failure mode this repo's test setup cannot detect. Steps 4–6 can be one commit, and step 7's tests can accompany it or precede it if you want to write the overdue tests first; they are the clearest specification of the filter's semantics.
