It must be nullable with no server default so existing rows read back as `None`. Store it the same way `created_at` already is: a naive `datetime` whose value is UTC. Do not add an index yet; the table is small and an index is a separate decision.

2. `alembic/versions/0002_add_due_date_to_todos.py`: new migration file. Set `revision = "0002_add_due_date_to_todos"` and `down_revision = "0001_create_todos"`. `upgrade()` calls `op.add_column("todos", sa.Column("due_date", sa.DateTime(), nullable=True))` — SQLite supports `ALTER TABLE ADD COLUMN` natively, and because the column is nullable, existing rows get `NULL` without a table rewrite. `downgrade()` drops the column inside `with op.batch_alter_table("todos") as batch_op:` because dropping a column on older SQLite requires Alembic's copy-and-move batch mode. Then run `alembic upgrade head` locally against a copy of `todo.db` and confirm with `.schema todos` that the column exists and old rows are `NULL`; also run `alembic downgrade -1` once to prove the downgrade path works, then upgrade again.

3. `app/schemas.py`: add `due_date: datetime | None = None` to `TodoCreate` and to `TodoOut`. On `TodoUpdate`, add `due_date: datetime | None = None` as well — Pydantic parses ISO-8601 strings with offsets automatically, so no custom parser is needed.

4. `app/schemas.py`: add a shared field validator (a `@field_validator("due_date")` on `TodoCreate` and `TodoUpdate`) that normalizes incoming values. If the parsed `datetime` has `tzinfo is None`, raise a `ValueError` so FastAPI returns 422 — a bare `2026-09-10T17:00:00` from a mobile client in another time zone is genuinely ambiguous and must not be silently treated as UTC. Otherwise convert with `value.astimezone(timezone.utc).replace(tzinfo=None)` so what reaches the database is naive UTC, matching `created_at`. Pass `None` through unchanged (that is the "clear it" value on PATCH).

5. `app/schemas.py`: add a matching serializer on `TodoOut` (a `@field_serializer("due_date", "created_at")`) that re-attaches UTC before output, so responses carry an explicit `Z`/`+00:00` offset instead of a bare naive timestamp. Both clients are in different time zones and must not have to guess. `None` serializes as `null`.

6. `app/routes.py`: in `POST /todos`, pass `due_date` from the request body through to the `Todo` constructor alongside `title`. If the field is absent the schema default `None` applies, so existing clients that send only `title` keep working unchanged.

7. `app/routes.py`: in `PATCH /todos/{id}`, build the update dict with `payload.model_dump(exclude_unset=True)` rather than checking each field for `None`. This is the only way to distinguish "client omitted `due_date`, leave it alone" from "client sent `due_date: null`, clear it". If the handler currently does `if payload.title is not None: ...` per field, convert it to iterating the `exclude_unset` dict and `setattr`-ing each key; verify `title` and `done` still behave as before.

8. `app/routes.py`: in `GET /todos`, add a second optional query param `overdue: bool | None = None`, keeping the existing `done: bool | None = None`. Leave both defaulting to `None` so a request with no params still returns everything.

9. `app/routes.py`: in `GET /todos`, compute the comparison instant once per request as `datetime.now(timezone.utc).replace(tzinfo=None)` so it is on the same naive-UTC footing as the stored column. Define the overdue predicate as `Todo.due_date.is_not(None) & (Todo.due_date < now) & (Todo.done.is_(False))`. When `overdue is True`, apply that predicate; when `overdue is False`, apply its negation via `~`, which must return todos with a `NULL` due date, todos due in the future, and done todos — a `NULL` due date is never overdue. Chain this filter onto the existing `done` filter with a second `.filter(...)` call so `?done=false&overdue=true` narrows correctly rather than either param overwriting the other.

10. `app/db.py`: no change. The engine, session factory, and `get_db` are column-agnostic; adding a column requires nothing here. Do not add a migration hook to this file — production applies migrations via `alembic upgrade head` on deploy, and the test suite deliberately builds tables from the models.

Risks:
- The test suite creates tables from the models and never runs Alembic, so a wrong or missing migration passes CI and then breaks production on deploy: before merging, run `alembic upgrade head` against a copy of the real `todo.db` and diff `.schema todos` against the schema the models produce; treat that manual check as a required review step recorded in the PR description.
- Mixing naive and timezone-aware datetimes in a SQLite comparison silently yields wrong results or raises `TypeError` at request time: normalize at exactly two boundaries — inbound in the schema validator (step 4) and the `now` value in the list handler (step 9) — and never construct a comparison datetime anywhere else.
- Treating an omitted `due_date` in PATCH as an explicit `null` would wipe due dates whenever the web UI sends a title-only patch: rely on `exclude_unset=True` rather than `is not None` checks, and keep `test_patch_title_only_leaves_due_date_unchanged` as the guard against a future refactor reintroducing the bug.
- Accepting naive timestamps would make a mobile client's local wall-clock time land in the database as UTC, shifting due dates by hours: reject naive input with 422 rather than guessing, and confirm with both clients before merge that they send offsets — if either cannot, that is an API conversation, not a silent server-side default.
- A todo due exactly at the current instant flips between overdue and not overdue depending on microsecond timing, making a boundary test flaky: define overdue as strictly `due_date < now` and seed boundary tests with offsets of at least a second so no test depends on sub-second execution timing.
- Filtering on an unindexed `due_date` scans the whole table as row count grows: acceptable now at current volume, and revisit with a plain index in a later migration if the list endpoint's latency becomes a complaint — do not add one speculatively in this change.
