**Feature: optional `due_date` on each todo, plus an `overdue` filter on GET /todos.**

1. `app/models.py`: add a `due_date` DateTime column, nullable, no default. Store it the same way `created_at` already does (UTC, naive) so the two are comparable and the filter's comparison behaves.

2. `alembic/versions/0002_add_due_date.py`: add the nullable column. No server default and no backfill — existing rows get NULL, which is what "no due date" means.

3. `app/schemas.py`: add `due_date: datetime | None` to TodoCreate (optional, default None), TodoUpdate (optional) and TodoOut. Settle the PATCH clearing semantics before writing code: explicit `"due_date": null` should clear the date, an omitted key should leave it untouched. That distinction only survives if the patch handler builds its update from `model_dump(exclude_unset=True)`. Check what the existing handler uses — if it's `exclude_none=True`, switching it also changes how `title` and `done` behave on patch, so make that change deliberately and cover it in tests rather than as a side effect.

4. `app/routes.py`: add an optional bool query param `overdue` to GET /todos. When true, filter on `due_date IS NOT NULL AND due_date < now AND done IS false`; compute `now` once per request in UTC. Decide what `overdue=false` means and document it in the docstring — recommend the complement (everything not overdue, including todos with no due date at all), with the param omitted filtering nothing. Combine with the existing `done` filter using AND; note that `overdue=true&done=true` is a legal query that always returns an empty list.

5. `tests/test_todos.py`: create without a due date (null in the response), create with one, patch to set one, patch to clear one with an explicit null, patch a different field and confirm the due date survives, `overdue=true` returns only past-dated undone todos, a past-dated *done* todo is excluded, a null due date is excluded, `overdue=false`, and `overdue` combined with `done`. Build fixture times relative to `datetime.now(UTC)` rather than hardcoded dates so the suite doesn't rot. The tests create tables from the models, so the model change alone makes them green; verify the migration separately by running `alembic upgrade head` against a copy of a populated database.

**Risks:** timezone handling is the main one — SQLite has no native datetime type and SQLAlchemy's DateTime stores a naive string, so an offset-aware value from a client has to be normalised to UTC on the way in or the `<` comparison comes out wrong with no error; mirror whatever `created_at` does. Second, "in the past" is evaluated at query time, so a todo can change category between two requests — harmless here, but no test should pin a boundary value. Third, there's no index on `due_date`; fine at this size, worth revisiting if the table grows.
