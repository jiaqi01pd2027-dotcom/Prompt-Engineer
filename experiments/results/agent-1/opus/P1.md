# Implementation plan: optional `due_date` + `?overdue=true`

## Step 0 — Confirm four decisions before writing code

These are the places where a reasonable-looking implementation silently does the wrong thing. Settle them first; each one changes the steps below.

1. **Naive input with no offset.** Clients send ISO-8601, but a web UI may send `2026-09-11T17:00:00` with no offset. Decide: reject it (422) or interpret it as UTC. Recommendation: interpret as UTC and document it, because rejecting breaks any client that is currently formatting without an offset. Whatever you pick, it must be one rule applied in one place.
2. **What `?overdue=false` means.** Either it returns the exact complement (not-yet-due, no due date at all, and done todos) or it is not supported and only `overdue=true` filters. Recommendation: implement the complement, because a client toggling a checkbox will send `false` and expect the full list back, not an error. The agreed API shape only mentions `true`, so raise this with the team.
3. **`?done=true&overdue=true` together.** By definition this is always empty. Decide whether that is a fine (documented) empty result or a 400. Recommendation: allow it and pin the behaviour with a test.
4. **Whether `created_at` output changes.** See Step 3 — if you make `due_date` serialize with an explicit UTC offset, you have to decide whether `created_at` is brought in line with it or deliberately left as-is. Changing `created_at` is a breaking change for existing clients; leaving it means two datetime fields on the same object serialize differently. Recommendation: leave `created_at` alone for now, note the inconsistency in the PR description, and let the team schedule it separately.

## Step 1 — Read three things before editing

- How `created_at` is populated in `app/models.py` (a Python-side `default=` vs a database-side `server_default`, and whether it produces a naive UTC value or an aware one). Your `due_date` storage convention must match it, or the two columns will not be comparable and the codebase will have two conflicting datetime idioms.
- The PATCH handler in `app/routes.py`: specifically whether it applies updates by skipping fields that are `None`. This is the pattern that will block clearing a due date (Step 4).
- How the existing `done` query param is declared and parsed in `app/routes.py`, so `overdue` is declared identically (same optional-bool style, same truthy-string handling). Two query params on one endpoint that parse booleans differently is a bug waiting to happen.

## Step 2 — Model

- Add a nullable `due_date` datetime column to the `Todo` model in `app/models.py`. Nullable with no default is what keeps the existing rows in the deployed `todo.db` valid.
- Store UTC. SQLite has no time-zone-aware type; SQLAlchemy will store whatever it is handed, and if some rows land with an offset suffix and others without, the string comparison SQLite performs on the stored values will produce wrong results for the overdue filter. The normalization to UTC therefore has to be guaranteed before any value reaches the model — that is Step 3's job, not the model's.
- Skip the index for now. The table is small enough that a composite index on `(done, due_date)` is not worth the migration; note it as a follow-up if the table grows.

## Step 3 — Schemas

- `TodoCreate`: add optional `due_date`, defaulting to absent/None.
- `TodoUpdate`: add optional `due_date`. Note that "optional" here has to mean two distinguishable things — omitted, and explicitly `null` — which Step 4 depends on.
- `TodoOut`: add `due_date`, which may be null for every pre-existing row. Make sure client teams know the field is nullable in responses, not just in requests.
- Add one shared validator, used by both `TodoCreate` and `TodoUpdate`, that takes the parsed ISO-8601 value, applies the Step 0.1 rule for naive input, converts any offset-aware value to UTC, and drops to the same naive/aware form the model stores. One validator, referenced twice — do not duplicate the logic per schema, because the two copies will drift.
- Decide serialization on the way out: emit `due_date` as ISO-8601 with an explicit UTC offset so the mobile and web clients can convert to local time without guessing. If the stored value is naive UTC, this requires a serializer that re-attaches UTC on output; a naive string with no offset is the failure mode where a client in UTC+8 renders the wrong day.
- Do **not** validate that `due_date` is in the future. Todos get imported and back-dated, and an overdue filter is pointless if past dates cannot be set.

## Step 4 — Make PATCH able to clear a due date

- Change the PATCH handler to apply only the fields the client actually sent, using Pydantic's unset-field tracking rather than an `is not None` check. Without this, `{"due_date": null}` is indistinguishable from omitting the field and a user can never remove a due date once set.
- Check this rewrite against the existing `title` and `done` behaviour. If the current handler skips `None` values, switching to unset-tracking changes what happens when a client sends `{"title": null}` — previously ignored, now an attempt to write null into a non-nullable column. Guard `title` explicitly, and confirm the existing patch tests still pass unmodified.

## Step 5 — Migration

- Add `alembic/versions/0002_add_due_date.py`, chained with `down_revision` pointing at the `0001_create_todos` revision id. Verify the id by reading the file rather than assuming it matches the filename.
- Upgrade: add the nullable column. No backfill, no server default — existing rows get NULL, which is exactly the "no due date" state.
- Downgrade: drop the column via Alembic's batch operation mode. Plain `drop_column` is the step that fails on SQLite in most Alembic setups; write it in batch mode and actually run the downgrade once locally to confirm.
- Confirm the column name, type, and nullability in the migration match the model exactly. Because the test suite creates tables from the models and never runs migrations, CI cannot catch a mismatch here — a typo in the migration passes every test and then breaks production.

## Step 6 — Route and filter logic

- Add an optional `overdue` bool query param to `GET /todos`, declared in the same style as the existing `done` param.
- Compute "now" once per request as a UTC value in the same form the column stores, obtained through a single small helper rather than inline, so tests can substitute a fixed time.
- `overdue=true` selects rows where `due_date` is not null **and** `due_date` is earlier than now **and** `done` is false.
- For `overdue=false`, write the complement out explicitly as "due_date is null, or due_date is not earlier than now, or done is true". Do not express it as a negation of the true-branch condition: in SQL, negating a comparison against NULL yields NULL, so every todo without a due date would silently vanish from the results. This is the single most likely bug in the whole change.
- Compose the `overdue` condition with the existing `done` condition rather than replacing it, so `?done=...&overdue=...` both apply. Leave list ordering unchanged; sorting overdue results by due date was not part of the agreed API shape.
- Keep the filter in the route layer next to the existing `done` filter unless the route file is already unwieldy — `app/db.py` is explicitly only engine/session/dependency, so nothing query-shaped belongs there.

## Step 7 — Tests in `tests/test_todos.py`

The twelve existing tests must pass untouched; if one needs editing, that is a signal you changed existing behaviour and should re-read Step 4. Add coverage for:

- Create with a `due_date`, and create without one (the second is the regression test for existing clients).
- Create with an offset-bearing timestamp from a non-UTC zone, then read it back and assert it round-trips to the correct UTC instant — not just that a value came back. Use a zone with a non-zero offset; a UTC-only test proves nothing about conversion.
- Create with a naive, offset-free timestamp, asserting whichever behaviour Step 0.1 settled on.
- The response format carries an explicit UTC offset.
- PATCH sets a due date; PATCH clears it with an explicit null; PATCH omitting `due_date` leaves an existing one untouched. All three are needed — the middle two are the ones that fail without Step 4.
- `?overdue=true` returns a past-due, not-done todo, and excludes: a future-due todo, a past-due but done todo, and a todo with no due date.
- `?overdue=false` includes the todo with no due date. This is the guard on the NULL-logic bug.
- `?done=true&overdue=true` behaves as decided in Step 0.3.
- A todo whose due date is a few seconds in the past is overdue and one a few seconds ahead is not, using the injectable "now" from Step 6 rather than real sleeps.

## Step 8 — Close the migration/model gap

CI runs pytest, pytest builds tables from the models, and production runs `alembic upgrade head` — so nothing in the pipeline currently checks that those two agree. Either:

- add a check that runs `alembic upgrade head` against a temporary file-backed SQLite database and asserts the resulting `todos` columns match the model's (the durable fix, and it protects every future migration), or
- at minimum, before merging, copy the deployed `todo.db`, run `upgrade head` against the copy, then start the app against that copy and exercise create-without-due-date, list, `?overdue=true`, and patch.

Do the second one regardless. It is the only step that tests the new code against real existing rows.

## Step 9 — Rollout

- The migration is purely additive and nullable, so old application code runs fine against the new schema and vice versa; deploy order does not matter and there is no downtime or table rewrite.
- FastAPI regenerates the OpenAPI schema automatically. Add a short description to the `overdue` param so the generated docs state the exact definition (past due **and** not done) rather than leaving clients to infer it.
- Tell the web and mobile teams three things: `due_date` is nullable in every response and will be null for all pre-existing todos; responses are UTC with an explicit offset and clients convert for display; and the rule for what happens if they send a timestamp with no offset.
