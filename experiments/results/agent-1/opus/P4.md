# Implementation Plan: optional due date + `overdue` filter

## Decisions to lock in before writing code

Settle these first; every step below depends on them.

1. **Field name and type.** Call it `due_at` (matches `created_at`), a nullable UTC datetime. Nullable is what makes it optional, and it means every existing row is simply "no due date."
2. **Storage convention.** SQLite has no native timezone-aware type; SQLAlchemy's `DateTime` round-trips whatever it is handed. Pick one convention — store **naive UTC**, matching whatever `created_at` already does — and normalize at the API boundary so an aware input with an offset is converted to UTC before it reaches the DB. Do not mix naive and aware values in the same column; comparisons between them raise at runtime in Python and silently mis-sort in SQL.
3. **Overdue definition.** A todo is overdue when `due_at IS NOT NULL AND due_at < now AND done IS false`. Strictly less-than, so a todo due exactly at `now` is not yet overdue. `now` is computed **once per request** and the comparison is done in SQL (in the query's `WHERE`), not by filtering a fetched list in Python.
4. **`overdue=false` semantics.** Define it as the exact logical complement: `due_at IS NULL OR due_at >= now OR done IS true`. Note that this is *not* `NOT (due_at < now)` alone — the NULL and the done cases have to be spelled out, because SQL comparisons against NULL yield NULL, not true.
5. **Interaction with the existing `done` param.** Both filters apply and are ANDed. `overdue=true&done=true` is therefore a legal request that always returns an empty list. Choose deliberately: either allow it (simplest, no extra code) or reject with a 400. Allowing it is recommended; whichever you pick, there is a test case for it below.
6. **Clearing a due date via PATCH.** `TodoUpdate` must distinguish "field absent" (leave unchanged) from "field present and null" (clear the due date). This is the single most likely bug in the change — see Risks.

## Step 1 — `app/models.py`

Add a `due_at` column to the `Todo` model: nullable datetime, no server default, no index for now (the table is small and SQLite will scan it either way; add an index only if a real dataset justifies it). Leave `id`, `title`, `done`, and `created_at` untouched. Because the test suite builds tables directly from the models, this edit alone is what makes the new column exist in tests — which is exactly the drift hazard covered in Step 2 and Risks.

## Step 2 — new migration `alembic/versions/0002_add_due_at_to_todos.py`

Do not skip this. Production applies schema changes only through `alembic upgrade head`; a model-only change leaves production with a column the ORM expects and the database does not have, and every query against `todos` will fail.

- Set `down_revision` to the revision id of `0001_create_todos.py` and give the new file its own revision id, so it chains rather than forking the history.
- **Upgrade:** add the nullable `due_at` column to `todos`. Adding a nullable column with no default is one of the few `ALTER TABLE` forms SQLite supports natively, so a plain add-column works; existing rows get NULL, which is the correct "no due date" value and requires no backfill.
- **Downgrade:** drop the column. SQLite's `DROP COLUMN` support is version-dependent, so wrap the downgrade in Alembic's batch-alter-table mode, which falls back to the copy-and-rename table rebuild. Write the downgrade even though you hope never to run it — a broken downgrade turns a bad deploy into a manual recovery.
- Verify by hand: against a throwaway copy of a database created by `0001`, run `alembic upgrade head`, inspect the resulting `todos` schema, then run `alembic downgrade -1` and confirm the column is gone and the other columns and data survived.

## Step 3 — `app/schemas.py`

- **`TodoCreate`:** add `due_at` as an optional field defaulting to `None`. Pydantic parses ISO-8601 strings automatically and rejects malformed ones with a 422, so no hand-rolled parsing is needed.
- **`TodoUpdate`:** add `due_at` as an optional, nullable field. The type alone is not enough — the route must use "only the fields the client actually sent" semantics (Pydantic's `exclude_unset`) so that an absent `due_at` means "leave it alone" while an explicit `null` means "clear it." If the route currently patches by iterating over all set fields, confirm it uses `exclude_unset` and not `exclude_none`; `exclude_none` makes clearing impossible.
- **`TodoOut`:** add `due_at` so it is returned by every endpoint that returns a todo. It will serialize as `null` for todos without one.
- Add the UTC-normalization validator agreed in Decision 2 to whichever schemas accept `due_at` as input, so a client sending `2026-09-10T09:00:00-05:00` and a client sending `2026-09-10T14:00:00Z` end up with identical stored values.
- Consider rejecting nothing else. In particular, do **not** validate that `due_at` is in the future: backdating is legitimate, and the `overdue` filter exists precisely to surface past dates.

## Step 4 — `app/routes.py`

- **POST /todos:** pass the new field through when constructing the model. If the handler builds the model field-by-field rather than from a dict, this is an easy line to forget — and the omission is invisible until a test checks the response body of a create-with-due-date.
- **PATCH /todos/{id}:** apply the update using the set-fields-only semantics from Step 3 so that clear, change, and leave-unchanged all behave correctly.
- **GET /todos:** add an optional boolean query parameter `overdue`, defaulting to `None` meaning "no overdue filtering." Build the query by starting from the base select and conditionally appending: the existing `done` condition when `done` is not `None`, then the overdue condition when `overdue` is `True` and the complement condition when it is `False`. Compute the comparison timestamp once, before building the query, in the same convention (naive UTC) as the stored values.
- **GET /todos/{id}:** no logic change; it picks up `due_at` automatically through `TodoOut`.
- `app/db.py` needs no changes at all — the session factory and `get_db` are unaffected.

## Step 5 — tests in `tests/test_todos.py`

Add these cases individually. Several of them exist specifically to catch a named bug, noted where relevant.

**Create and read**
1. Create a todo with no `due_at` → succeeds, response `due_at` is `null`.
2. Create a todo with a valid `due_at` → response echoes the same instant.
3. Create with a malformed `due_at` (e.g. `"next tuesday"`) → 422.
4. Create with an offset-bearing timestamp (e.g. `-05:00`) → stored/returned value equals the equivalent UTC instant. *(Catches the naive/aware mixing bug.)*
5. `GET /todos/{id}` and `GET /todos` both include `due_at` in each item.

**Patch**
6. Patch `due_at` onto a todo that had none → set.
7. Patch `due_at` on a todo that already had one → replaced.
8. Patch with `due_at: null` explicitly → cleared to `null`. *(Catches `exclude_none`.)*
9. Patch only `title`, omitting `due_at`, on a todo that has a due date → `due_at` unchanged. *(Catches a naive "apply all model fields" update that silently nulls it.)*

**Overdue filter — the four input classes**
10. `?overdue=true` includes a todo that is past-due and not done.
11. `?overdue=true` excludes a past-due todo that **is** done.
12. `?overdue=true` excludes a not-done todo whose `due_at` is in the future.
13. `?overdue=true` excludes a not-done todo with `due_at` null. *(Catches the NULL-comparison mistake.)*

**Overdue filter — complement and boundary**
14. `?overdue=false` returns exactly the three excluded todos from cases 11–13 and not the overdue one.
15. Boundary: a not-done todo whose `due_at` equals the request's `now` is **not** overdue. Construct this by setting the due date a very small delta in the future rather than trying to hit the exact instant, so the test is not flaky.
16. Omitting `overdue` entirely returns all todos regardless of due date — the pre-existing listing behavior is unchanged.

**Parameter interaction and validation**
17. `?overdue=true&done=false` returns the same set as `?overdue=true` alone.
18. `?overdue=true&done=true` returns an empty list (or 400, matching Decision 5).
19. `?overdue=maybe` → 422.

**Regression**
20. Re-run the twelve existing tests unchanged. If any of them assert an exact response dictionary, they will now fail because of the added `due_at` key — update those assertions to include it rather than loosening them to subset checks, so the response contract stays pinned.

**Migration parity**
21. Add one check that the migration and the models agree: build a database by running `alembic upgrade head` against a temporary file-backed SQLite database, build a second by creating tables from the models, and compare the `todos` column sets. This can be a pytest case or a documented manual step, but it should exist — see Risks.

## Risks and how to handle them

**Risk 1 (most important): the test suite never runs migrations, so a green suite does not prove production will work.** Tests create tables from the models; a missing, misspelled, or mis-chained migration is completely invisible to them, and the failure surfaces only after deploy, as errors on every `todos` query. Handle it with the parity check in test case 21 plus the manual upgrade/downgrade rehearsal in Step 2. At minimum, do the manual rehearsal before merging — an automated parity check is better because it keeps catching drift on the *next* schema change too.

**Risk 2: clearing a due date via PATCH.** The distinction between "field omitted" and "field explicitly null" is invisible in the type signature and easy to get wrong in either direction — one way makes clearing impossible, the other silently wipes due dates on unrelated title edits. Handle it with the set-fields-only semantics in Steps 3–4, pinned by test cases 8 and 9, which fail loudly for each failure mode.

**Risk 3: naive vs aware datetime mixing.** SQLite stores no timezone. A route that compares an aware `now` against naive stored values will either raise a TypeError in Python or produce wrong results in SQL depending on where the comparison happens, and the bug can hide until someone in a non-UTC timezone posts a due date. Handle it by fixing one convention (Decision 2), normalizing in the schema validator, and covering it with test case 4.

**Risk 4: the response contract changes for every existing consumer.** `TodoOut` gaining a key is additive and usually safe, but any strict-schema client will break. Handle it by confirming the added field is optional in the response and by updating, not weakening, the existing exact-response assertions (case 20).

## Done criteria

All 21 new cases plus the 12 existing ones pass; `alembic upgrade head` followed by `alembic downgrade -1` runs cleanly against a database created by `0001`; no new dependency appears in the project's requirements; the only files touched are `app/models.py`, `app/schemas.py`, `app/routes.py`, `tests/test_todos.py`, and the new `alembic/versions/0002_add_due_at_to_todos.py`.
