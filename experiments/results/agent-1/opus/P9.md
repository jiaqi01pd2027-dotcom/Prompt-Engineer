## Implementation Plan: optional `due_date` + `overdue` filter

No repository was present in the sandbox, so this plan is written against the described layout. File paths below are repo-relative; adjust the root prefix when you open the real tree.

---

### 0. Decisions the plan assumes (confirm before starting)

- **Storage representation:** store `due_date` as a *naive* datetime already normalized to UTC, matching how `created_at` is stored today. Rationale: SQLite has no native timestamp type, and SQLAlchemy's SQLite `DATETIME` silently drops `tzinfo` on write and hands back naive values on read. Mixing aware and naive values is the single largest source of bugs in this change. Normalize once, at the schema boundary.
- **Response representation:** decide whether `due_date` is serialized bare (`2026-03-01T09:00:00`) or with an explicit UTC designator. Recommendation: attach UTC on the way out so the mobile client cannot misread it. If you do that, decide separately whether `created_at` follows — changing `created_at` is a breaking change for existing clients and will touch existing tests, so the safe default is to leave `created_at` as-is and accept the temporary inconsistency, with a follow-up ticket.
- **`overdue=false`:** treat it as the complement (return only todos that are *not* overdue), not as "no filter". Absent param means no filter.
- **`done=true&overdue=true`:** by definition always empty. Do not special-case or 400 it; just let the query return nothing, and note it in the param description.
- **Past due dates are accepted.** No validation rejecting dates in the past — the overdue feature depends on them being creatable.

---

### 1. `app/models.py` — add the column

1. Add a nullable `due_date` column to the `Todo` model, typed the same way `created_at` is typed (plain `DateTime`, no `timezone=True`), with no server default and no Python-side default.
2. Confirm the column is declared `Optional`/nullable in the SQLAlchemy 2.0 typed-mapping style used by the rest of the model, so `mypy`/type checkers and `create_all` agree.
3. Do not add an index yet. At SQLite-with-one-table scale the overdue predicate scans fine; add an index on `due_date` only if list latency becomes a real complaint.

### 2. `alembic/versions/` — new revision

4. Generate a new revision whose `down_revision` points at `0001_create_todos`. Verify the chain by hand rather than trusting autogenerate — confirm `alembic/env.py` actually imports the models' metadata before you rely on `--autogenerate` output.
5. Upgrade: add the `due_date` column as nullable. Plain `ALTER TABLE ... ADD COLUMN` is natively supported by SQLite, so no batch mode is needed here.
6. Downgrade: drop the column inside a `batch_alter_table` block. `DROP COLUMN` is unsupported on SQLite before 3.35, and batch mode makes the downgrade work regardless of the server's SQLite version.
7. Give the revision a descriptive slug (e.g. `0002_add_todo_due_date`) to match the existing naming.
8. Sanity-check the migration against a scratch file database: run `alembic upgrade head` on an empty file, then `downgrade` and `upgrade` again. This matters more than usual here because **the test suite never exercises migrations** — it builds tables from the models — so a broken migration would ship green.
9. As part of that check, compare the migrated schema against the model metadata (an autogenerate run on the migrated database should report no diff). This is the only guard against model/migration drift in this repo.

### 3. `app/schemas.py` — request/response fields and normalization

10. Add a single reusable normalizer for incoming datetimes: if the parsed value carries an offset, convert to UTC and drop `tzinfo`; if it is naive, leave it unchanged (already treated as UTC per spec). Define it once and apply it to every field that takes a due date, so `TodoCreate` and `TodoUpdate` cannot diverge.
11. `TodoCreate`: add optional `due_date`, defaulting to `None`, running through the normalizer.
12. `TodoUpdate`: add optional `due_date` defaulting to `None`, running through the same normalizer. Note that `None` here is ambiguous by itself — see step 15.
13. `TodoOut`: add `due_date` as an optional field. If you chose UTC-marked output in step 0, add a serializer that re-attaches UTC on the way out; keep it scoped to `due_date` only.
14. Let Pydantic own ISO-8601 parsing and rejection. Do not hand-roll string parsing; malformed input should surface as FastAPI's standard 422.

### 4. `app/routes.py` — PATCH semantics

15. **Read the current PATCH handler before changing anything.** The requirement "patch sets and clears it" means an explicit `null` must clear the field while an omitted key must leave it untouched. Which change you need depends on what the handler does today:
    - If it dumps the update model with `exclude_unset=True` and applies the resulting keys, clearing already works — no change beyond letting the new field flow through.
    - If it uses `exclude_none=True`, or applies fields with an `if value is not None` guard, clearing is **impossible** and the handler must be reworked to key off "was this field provided" rather than "is this field non-null."
16. Whichever form it takes, make the applied-fields logic generic over the model's set fields rather than adding a `due_date`-specific branch, so `title`/`done` and the new field stay consistent.
17. Confirm POST passes `due_date` through to the model on insert, and that `created_at` remains server-assigned and is not accidentally settable.

### 5. `app/routes.py` — the `overdue` query param

18. Add `overdue: bool | None = None` to `GET /todos`, with a `Query` description explaining the definition (due date in the past, not done; todos without a due date are never overdue). This description is what shows up in the generated OpenAPI docs.
19. Compute "now" **once per request** as the current UTC time, then strip `tzinfo` before it reaches the query. Comparing a naive stored column against an aware Python datetime in SQLite produces a mis-formatted comparison string and silently wrong results — this is the highest-risk line in the change.
20. Build the overdue predicate as: `due_date IS NOT NULL AND due_date < now AND done IS false`. Keep the `IS NOT NULL` term explicit even though `NULL < now` is already falsy in SQL — it documents the intent and survives future refactors into OR-groups.
21. For `overdue=false`, apply the negation of that predicate (no due date, **or** due date in the future, **or** already done). Write it as an explicit OR-group rather than a SQL `NOT` over the whole clause, so NULL three-valued logic cannot swallow the null-due-date rows.
22. Apply the `overdue` filter as an additional `WHERE` clause on the same query the existing `done` filter uses, so the two compose naturally. Do not build a second query path or post-filter in Python.
23. Leave ordering unchanged. If the current endpoint has no explicit `ORDER BY`, do not add one as part of this change — it would be an unrelated behavior change that could break existing test assumptions.

### 6. `tests/test_todos.py` — new coverage

24. **First, run the existing twelve tests against the new `TodoOut`.** Any test asserting whole-response equality (`response.json() == {...}`) will now fail because of the added key. Update those to the new expected shape rather than loosening the assertion.
25. Build due dates *relative to the current time* (an hour ago, a day ahead) in a fixture or small helper, not as hardcoded calendar dates. Hardcoded absolute dates make the overdue tests rot silently once the date passes.
26. Create todos through the API rather than by direct model insert, so the tests exercise the normalization path.

Cases to write, named:

- `create_without_due_date` → response has `due_date: null`
- `create_with_due_date_utc` → round-trips unchanged
- `create_with_due_date_with_offset` → stored/returned as the UTC equivalent, not the wall-clock local value
- `create_with_naive_due_date_treated_as_utc` → same instant as the equivalent `Z` form
- `create_with_invalid_due_date_returns_422`
- `get_single_todo_includes_due_date`
- `patch_sets_due_date` (todo that previously had none)
- `patch_changes_existing_due_date`
- `patch_clears_due_date_with_explicit_null` → becomes `null`
- `patch_omitting_due_date_leaves_it_unchanged` → the regression guard for step 15
- `overdue_includes_past_and_not_done`
- `overdue_excludes_done_even_if_past_due`
- `overdue_excludes_future_due_date`
- `overdue_excludes_null_due_date`
- `overdue_false_returns_complement` (asserting all three non-overdue kinds are present)
- `overdue_combined_with_done_false` → same set as `overdue=true` alone
- `overdue_true_and_done_true_returns_empty`
- `list_without_overdue_param_returns_all` (guards against the param defaulting to `False` instead of `None`)

27. Structure the overdue tests around one shared fixture that seeds exactly four todos — past/not-done, past/done, future/not-done, no-due-date — and assert on returned IDs. Each case then reads as a one-line set comparison.

### 7. Verification

28. Full `pytest` run green, including the pre-existing twelve.
29. Migration checked independently per steps 8–9 (upgrade, downgrade, re-upgrade, no autogenerate diff), since the suite does not cover it.
30. Eyeball `/docs`: `due_date` appears on the POST and PATCH bodies and in `TodoOut`, and `overdue` appears as an optional boolean with the description from step 18.
31. Manual spot-check against a real file database (not in-memory) with an offset-bearing timestamp — this is where the SQLite naive/aware mismatch from steps 0 and 19 would show up and the in-memory tests might not.
32. Update the README's endpoint documentation if it lists query params by hand.

---

**Two things most likely to bite the implementer:** the PATCH clear-vs-omit distinction (step 15), which depends entirely on how the existing handler dumps the update model, and the naive/aware comparison in the overdue predicate (step 19), which fails silently rather than raising.
