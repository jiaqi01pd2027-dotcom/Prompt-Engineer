## Reasoning

**Layers a persisted field crosses.** `due_at` has to appear in five places, and each is a separate failure mode: the SQLAlchemy column (`app/models.py`), the DDL that reaches an already-populated production database (`alembic/versions/`), the input contracts (`TodoCreate`, `TodoUpdate`) and output contract (`TodoOut`) in `app/schemas.py`, the query filter and PATCH write path in `app/routes.py`, and the tests. `app/db.py` doesn't change — nothing about this touches engine or session setup.

**The trap in this specific repo:** the test suite creates tables from the models, not from migrations. So a developer who edits `models.py` and forgets the Alembic revision gets twelve green tests and a production `OperationalError: no such column`. Tests cannot catch a missing migration here, so migration verification must be a separate manual step.

**"In the past" on a server.** `created_at` is UTC, and SQLite has no timezone type, so whatever it stores is almost certainly naive-UTC. The new column must follow that same convention or comparisons break. Clients will send offsets (`Z`, `+02:00`), so input has to be converted to UTC and stripped of tzinfo at the schema boundary; otherwise you get either a `TypeError` comparing naive and aware datetimes in Python, or silently wrong string comparisons in SQLite. "Now" is `datetime.now(timezone.utc)` normalized the same way, computed once per request (`utcnow()` is deprecated in 3.12). Comparison belongs in SQL, not a Python list comprehension, so it composes with the existing `done` filter. Strict `<`: a todo due exactly now is not yet overdue.

**Existing rows.** The column must be nullable with no server default, so every pre-existing todo becomes "no due date." SQLite's `ALTER TABLE ADD COLUMN` handles a nullable column natively — no batch mode needed for the upgrade (the downgrade drop is the part that wants batch mode). Null means never overdue, which is what the three-valued SQL logic gives you for free on `overdue=true`.

**The subtle bug is the negation.** `overdue=false` naively expressed as `NOT (due_at < now)` evaluates to NULL for rows with no due date, and SQL drops NULL rows from the result — so every todo without a due date silently vanishes from the "not overdue" list. The complement must explicitly include `due_at IS NULL` and `done IS true`.

**How tests prove it.** A four-row fixture separates the axes: past+not-done (the only match), past+done, future+not-done, no-due-date+not-done. That single fixture proves inclusion, that `done` gates it, that the future is excluded, and that NULL is excluded — plus, run through `overdue=false`, that the complement returns the other three. The boundary case needs a controllable clock, which is the reason to route "now" through one small function.

## Plan:

**Step 0 — Lock these decisions before writing anything**

1. Name the field `due_at`, matching `created_at`, and use the same name in the JSON API. It is a datetime, not a date.
2. Storage convention: naive UTC, identical to `created_at`. Confirm this by reading how `created_at` is declared and set in `app/models.py` before you start; if `created_at` turns out to be timezone-aware, match that instead and adjust every step below accordingly.
3. Query param semantics: `overdue` is optional and tri-state, mirroring the existing `done` param. Omitted = no filtering. True = overdue only. False = the explicit complement. `done` and `overdue` are independent, AND-ed filters, so `done=true&overdue=true` legitimately returns an empty list rather than a 400.
4. No validation rejecting past due dates on create — imports and backfills need it, and rejecting it would make the overdue tests awkward to write.
5. Response serialization: emit `due_at` exactly the way `created_at` is already emitted. Do not "fix" the offset on the new field alone; a response where one timestamp carries `Z` and the other doesn't is worse than one that is uniformly naive. If you want offsets, that's a separate change to both fields plus the existing assertions.

**Step 1 — `app/models.py`**

6. Add `due_at` to the `Todo` model as a nullable DateTime column, no default, no `server_default`, positioned after `created_at`.
7. Do not add an index yet. A composite index on (`done`, `due_at`) is the right shape if this table ever grows, but on a SQLite todo list it is unjustified — note it as a follow-up rather than shipping it.

**Step 2 — `alembic/versions/`**

8. Generate a new revision with `alembic revision -m "add due_at to todos"`, with `down_revision` pointing at `0001_create_todos`. Prefer handwriting the operation over `--autogenerate`; autogenerate against a database that may be out of sync can emit surprises.
9. Upgrade: a single `add_column` of a nullable DateTime. This is a plain, non-rewriting `ALTER TABLE` in SQLite and is safe on a populated table.
10. Downgrade: drop the column using `batch_alter_table`, since older SQLite builds can't drop a column in place and Alembic's batch mode does the table-copy dance.
11. Confirm the migration matches the model exactly (type, nullability). Since tests build tables from models, any drift between the two is invisible until production.

**Step 3 — `app/schemas.py`**

12. `TodoCreate`: add `due_at` as an optional datetime defaulting to `None`.
13. `TodoUpdate`: add `due_at` as an optional datetime defaulting to `None`. Note that with this shape, "omit the field" and "send null to clear it" are indistinguishable by value alone — Step 4 resolves that.
14. Add one shared normalizer applied to `due_at` on both input models: if the parsed datetime carries a tzinfo, convert it to UTC and drop the tzinfo; if it's already naive, treat it as UTC and pass it through. Put this in `app/schemas.py` — `app/db.py` is deliberately just engine and session, and routes should stay thin.
15. `TodoOut`: add `due_at` as an optional datetime so existing rows serialize as `null`.

**Step 4 — `app/routes.py`**

16. Add a single module-level helper that returns the current time in the same naive-UTC convention. Every "now" in this feature goes through it, and tests monkeypatch it for the boundary case.
17. POST `/todos`: pass `due_at` through to the model on insert. If the handler currently constructs the model with explicit keyword arguments, add the new one; if it unpacks the schema, verify the new field flows through.
18. PATCH `/todos/{id}`: this is the one place to be careful. Inspect the existing update logic — if it applies fields with an `is not None` check, `due_at` can be set but never cleared. Switch the handler to apply only the fields the client actually sent (Pydantic v2's `exclude_unset` on `model_dump`), so an explicit null clears the due date and an omitted key leaves it untouched. This also quietly fixes the same latent issue for `title` and `done`; make sure the existing PATCH tests still pass after the change.
19. GET `/todos`: add an optional `overdue: bool | None = None` query parameter alongside the existing `done`, with a short description so it shows up usefully in the OpenAPI docs.
20. Build the filters as conditions appended to the existing query, not as post-query Python filtering. Compute "now" once at the top of the handler so every row is evaluated against a single instant.
21. When `overdue` is true, add: `due_at` is not null, AND `due_at` is strictly less than now, AND `done` is false. Use SQLAlchemy's `is_(False)` rather than `== False` for the boolean, so it's NULL-safe and lint-clean.
22. When `overdue` is false, add the explicit complement: `due_at` is null, OR `due_at` is greater than or equal to now, OR `done` is true. Do not write this as a `NOT (...)` wrapper around the overdue condition — NULL `due_at` rows would evaluate to NULL and be dropped from the results. Leave a one-line comment on this branch saying why, or the next person will "simplify" it back into the bug.
23. When `overdue` is None, add nothing. Confirm `done` and `overdue` compose as an AND, and that the existing `done`-only behavior is byte-for-byte unchanged.

**Step 5 — `tests/test_todos.py`**

24. Do not modify the twelve existing tests except where Step 5's response-shape change requires it — if any of them assert an exact response body, they now need `due_at: null`. If they assert field-by-field, they should pass untouched. Run them before writing new ones to see which.
25. Add a fixture that creates four todos in one shot: past-due and not done, past-due and done, due in the future and not done, and no due date and not done. Use offsets of days from real time (not minutes) so the tests can't flake on a slow CI box.
26. Create tests: create without `due_at` returns null; create with a `Z`-suffixed timestamp round-trips; create with a non-UTC offset comes back converted to the equivalent UTC instant; create with a malformed timestamp returns 422.
27. PATCH tests: setting `due_at` on a todo that had none; clearing it by sending explicit null; and a regression test that a PATCH of `title` alone leaves an existing `due_at` untouched. That third one is what guards Step 18.
28. Filter test — the positive case: `overdue=true` against the fixture returns exactly one todo, the past-due not-done one. Assert on the returned ids, not just the count.
29. Filter test — the complement: `overdue=false` returns exactly the other three, and assert explicitly that the no-due-date todo is among them. This is the test that catches the three-valued-logic bug, and it is the most important new test in the file.
30. Filter test — omitted: no `overdue` param returns all four, proving the parameter is genuinely optional.
31. Combination tests: `overdue=true&done=false` matches `overdue=true`; `overdue=true&done=true` returns an empty list.
32. Boundary test: monkeypatch the Step 16 helper to a fixed instant, create a todo due at exactly that instant, and assert it is not overdue; then move the fixed instant one second later and assert it is. This pins the strict `<` and is the reason the helper exists.
33. Full suite green: twelve original plus roughly twelve new.

**Step 6 — Verify what the tests structurally cannot**

34. Because the suite never runs Alembic, verify the migration by hand: take a copy of a `todo.db` that has rows in it, run `alembic upgrade head`, confirm the column exists and existing rows show `due_at` as NULL, then hit `GET /todos?overdue=true` against that database and confirm it returns an empty list rather than erroring.
35. Run `alembic downgrade -1` on that same copy and then upgrade again, confirming the batch-mode drop actually works on your SQLite version.
36. Open `/docs` and check that `overdue` appears on GET `/todos` and that `due_at` appears in the request and response schemas.

The highest-risk items are Step 22 (the NULL-dropping complement), Step 18 (clearing a due date via PATCH), and Step 34 (a migration no test will ever exercise).
