# Implementation Plan: optional due date + `overdue` filter

## Design decisions to know before you start

Read these first — they explain the "why" behind several steps and are where this feature usually goes wrong.

**D1. Field name and type.** Add one column, `due_at`, nullable `DateTime`. Name it `due_at` (not `due_date`) because it stores a timestamp, matching `created_at`. Nullable is the whole point: a todo without a due date is normal, not an error.

**D2. Timezone storage.** `created_at` is described as UTC. SQLite has no native timestamp type — SQLAlchemy's SQLite dialect serializes a `datetime` into a string using its date/time fields and **silently ignores `tzinfo`**. So if a client sends `2026-01-01T09:00:00+05:00` and you persist it unchanged, you store the wall-clock `09:00:00` and it later compares as if it were 09:00 UTC — five hours wrong. Rule for this codebase: **normalize every incoming aware datetime to UTC, then strip `tzinfo`, and store naive-UTC.** Do the same for the "now" value you compare against. Decide this once and apply it in exactly one place (see step 3) so the model, the routes, and the tests can't drift apart.

**D3. PATCH must distinguish "absent" from "null".** `TodoUpdate` currently has optional fields, and the existing PATCH handler almost certainly treats `None` as "not provided". That works while every field is a value type, but `due_at` has a legitimate `None` meaning: *clear the due date*. If you reuse the existing "skip `None` fields" logic, clients will have no way to remove a due date. You must switch the handler to unset-based detection (Pydantic v2's `model_dump(exclude_unset=True)` / `model_fields_set`), which changes behavior for `title` and `done` too. Verify the existing PATCH tests still pass after that change — that's the main regression risk in this task.

**D4. `overdue` semantics.** Overdue = `due_at IS NOT NULL AND due_at < now AND done IS FALSE`. Three separate conditions; a todo with no due date is never overdue, and a completed todo is never overdue regardless of its date.

**D5. `overdue=false` and SQL NULL.** Do not implement the false case as a blanket negation of the overdue expression. In SQL, `NOT (NULL < now AND ...)` evaluates to NULL, not TRUE, so rows with `due_at IS NULL` would be silently dropped from the result — a todo with no due date would disappear from `?overdue=false`, which is clearly wrong. Write the false branch as an explicit disjunction: `due_at IS NULL OR due_at >= now OR done IS TRUE`.

**D6. `done` and `overdue` combine with AND.** The existing `done` param stays independent; passing both just intersects them. Note the consequence and don't treat it as a bug: `?done=true&overdue=true` is by definition always empty, because done todos are never overdue. Keep it as a legal query returning `[]` rather than adding a 400 — a special-case error here is more code and more surprise than an empty list.

**D7. "Now" is evaluated in Python, once per request.** Compute the comparison instant in the handler and pass it into the query as a bound parameter. Don't use a SQL-side `CURRENT_TIMESTAMP`: SQLite's string comparison against your stored format is fragile, and an injected Python value is what makes the filter testable without sleeping (see step 7).

## Step 1 — `app/models.py`: add the column

1. Add `due_at` to the `Todo` model as a nullable `DateTime` column with no server default and no `default`. Follow whatever style the file already uses for `created_at` (`Mapped[...]` / `mapped_column(...)` in SQLAlchemy 2.0 style) — match it exactly, including whether `DateTime(timezone=True)` is used for `created_at`. If `created_at` uses `timezone=True`, use it here too for consistency; it doesn't change SQLite's behavior but keeps the two columns declared alike.
2. The annotation must be `datetime | None` so type checkers and Pydantic's ORM mode agree it's optional.
3. Do not add an index in this step. The table is small and unindexed today; adding an index is a separate, measurable decision, and doing it here would also mean a larger migration. Note it in the PR description as a follow-up if the todos table is expected to grow.

## Step 2 — `alembic/versions/`: new migration

1. Generate a new revision (`alembic revision -m "add due_at to todos"`) rather than hand-writing the file, so the revision id and `down_revision` chain are correct. Confirm `down_revision` points at `0001_create_todos`.
2. Fill in `upgrade()` to add the nullable `due_at` column to `todos`, and `downgrade()` to drop it.
3. SQLite supports `ALTER TABLE ... ADD COLUMN` for a nullable column with no default, so a plain `op.add_column` is fine on the way up. Dropping a column is the operation older SQLite versions can't do natively — if `alembic downgrade` fails on the project's SQLite version, wrap the downgrade in `op.batch_alter_table`, which rebuilds the table. Test the downgrade; don't assume it works.
4. Verify by hand against a scratch copy of `todo.db`: run `alembic upgrade head`, inspect the schema, run `alembic downgrade -1`, inspect again, then `upgrade head` once more. Do not run this against a real `todo.db` you care about — copy it first.
5. Remember the test suite does **not** run migrations; it builds tables from the models. That means a green test suite proves nothing about this migration. Step 4 is the only verification this migration gets, so actually do it.

## Step 3 — Shared UTC normalization helper

1. Add one small helper that takes a `datetime` and returns naive-UTC (convert aware values with `astimezone(UTC)` then drop `tzinfo`; leave already-naive values alone, treating them as UTC by convention).
2. Put it in `app/schemas.py` if it's only used by validators, or in a new `app/time.py` if the routes need it too. Do **not** put it in `app/db.py` — that file is described as holding the engine, session factory, and `get_db` and nothing else; keep that boundary.
3. Both the request-side normalization (step 4) and the "now" value in the query (step 5) must go through this helper. One definition, two callers.

## Step 4 — `app/schemas.py`: expose the field

1. **`TodoCreate`**: add `due_at: datetime | None = None`. Optional with a `None` default, so every existing client that posts only a title keeps working unchanged.
2. **`TodoUpdate`**: add `due_at: datetime | None = None`. This field is what makes step D3 necessary — the default `None` here means "not provided", and an explicit JSON `null` also arrives as `None`, so only the unset-tracking in step 6 can tell them apart.
3. **`TodoOut`**: add `due_at: datetime | None`. It has no default, since the server always knows the value; every response now carries the key, `null` when unset.
4. Attach a field validator on `due_at` in both `TodoCreate` and `TodoUpdate` that runs the step-3 normalizer, so tz-aware input is converted at the boundary and the rest of the app only ever sees naive-UTC.
5. Decide whether past due dates are allowed on create. **Allow them** — backfilling a todo that was already due is a real use case, and rejecting it would make the overdue filter nearly untestable. Don't add a "must be in the future" validator.
6. Leave `TodoOut`'s serialization alone; whatever config it uses for `created_at` (`from_attributes` / ORM mode) covers the new field automatically.

## Step 5 — `app/routes.py`: `GET /todos`

1. Add an `overdue: bool | None = None` query parameter alongside the existing `done` param, following the same declaration style. Three states: omitted (no filtering), `true`, `false`.
2. Build the query by conditionally appending `.where(...)` clauses, matching how the existing `done` filter is applied. Keep the `done` filter exactly as it is.
3. Compute the comparison instant once at the top of the handler using the step-3 helper, so both branches compare against the same value.
4. `overdue=true` branch: AND together `due_at IS NOT NULL`, `due_at < now`, and `done IS FALSE`.
5. `overdue=false` branch: the explicit OR from D5 — `due_at IS NULL` OR `due_at >= now` OR `done IS TRUE`. Write it as a disjunction; do not negate the true-branch expression.
6. Add a short docstring or `description=` on the parameter stating the definition of overdue, since it shows up in the generated OpenAPI docs and is the only place a consumer can learn the semantics.
7. Leave `POST`, `GET /{id}`, and `DELETE /{id}` untouched — they pick up `due_at` for free through the schemas.

## Step 6 — `app/routes.py`: `PATCH /todos/{id}`

1. Change the handler to derive the set of fields to apply from what the client actually sent (`exclude_unset=True`) instead of from which values are `None`.
2. Apply each present field to the ORM object, including an explicit `due_at: null`, which must set the column to `None`.
3. Re-read the existing `title`/`done` patch tests before you change this. Under the old logic, a body of `{"title": null}` was likely a silent no-op; under the new logic it will try to write `NULL` into a non-nullable column and raise. If those tests don't cover it, add a test asserting the behavior you want — the sensible choice is to keep `title` non-nullable and let Pydantic reject `null` for it by typing `TodoUpdate.title` as `str | None` only in the "omittable" sense your Pydantic version supports, or by adding a validator that rejects an explicit null title with a 422.
4. Confirm `updated`/`created_at` handling is unchanged — this step should not touch timestamps other than `due_at`.

## Step 7 — `tests/test_todos.py`

All twelve existing tests must stay green; new tests go alongside them in the same file and style (pytest + `TestClient`).

1. **Create without a due date** — response contains `"due_at": null`. This is the backward-compatibility check.
2. **Create with a due date** — round-trips through GET by id unchanged.
3. **Create with a tz-aware due date** carrying a non-UTC offset — assert the stored/returned value is the correct UTC instant, not the raw wall-clock. This is the regression test for D2 and the one most likely to fail first.
4. **Patch sets a due date** on a todo that had none.
5. **Patch clears a due date** by sending explicit `null` — assert it becomes `null`, not "unchanged". This is the test for D3.
6. **Patch omitting `due_at`** leaves an existing due date intact.
7. **`?overdue=true`** returns only the past-due, not-done todos. Seed at least four todos in the setup: past + not done (matches), past + done (excluded), future + not done (excluded), no due date (excluded).
8. **`?overdue=false`** over the same seed returns exactly the three non-matching ones — and explicitly assert the no-due-date todo is present. That assertion is the test for D5; without it the NULL bug ships silently.
9. **`?done=true&overdue=true`** returns `[]` (D6).
10. **No `overdue` param** returns all four, proving the default is "no filtering".
11. Seed times relative to a fixed offset from `datetime.now(UTC)` (e.g. one hour back, one hour forward) rather than hardcoded calendar dates, so the suite doesn't rot. Never `sleep` to cross a boundary.

## Step 8 — Verification and wrap-up

1. Run the full suite; all twelve original tests plus the new ones must pass.
2. Start the app and check `/docs`: `due_at` appears on the create/update/response models and `overdue` appears as a boolean query param on `GET /todos`.
3. Exercise the migration path once more end to end on a copy of a real database (upgrade, insert a row with a due date through the API, downgrade, upgrade) — this is the path the tests never touch.
4. Update `README.md` if it documents the endpoints or query params.
5. In the PR description, call out the PATCH semantics change from step 6 (it affects `title` and `done`, not just the new field) and note the deferred index from step 1.
