12. tests/test_todos.py: add the new test cases listed below, using `datetime.now(timezone.utc) ± timedelta(hours=1)` for past/future fixtures so the real clock is never near a boundary.

Tests:
- POST /todos with no `due_at` returns 201 and `due_at: null`.
- POST /todos with an ISO-8601 UTC `due_at` returns it unchanged on read-back via GET /todos/{id}.
- POST /todos with a `due_at` carrying a non-UTC offset (e.g. `+05:00`) stores and returns the equivalent UTC instant.
- POST /todos with a non-datetime `due_at` (e.g. `"tomorrow"`) returns 422.
- PATCH setting `due_at` on a todo that had none persists the new value.
- PATCH with `{"due_at": null}` clears an existing due date.
- PATCH with `{"title": "x"}` only leaves an existing `due_at` untouched (regression guard for the `exclude_unset` change).
- GET /todos?overdue=true returns only past-due, not-done todos.
- GET /todos?overdue=true excludes a past-due todo whose `done` is true.
- GET /todos?overdue=true excludes a todo with `due_at` in the future.
- GET /todos?overdue=true excludes a todo with `due_at` null.
- GET /todos?overdue=false returns exactly the complement: no-due-date, future-due, and done-past-due todos.
- GET /todos with no `overdue` param returns all todos (existing twelve tests must stay green).
- GET /todos?done=false&overdue=true returns the same set as `overdue=true` alone; `done=true&overdue=true` returns an empty list.
- GET /todos?overdue=notabool returns 422.
- A todo whose `due_at` is a few seconds in the past is reported overdue (strict `<` boundary, no accidental `<=` on equality of a stored value).

Risks:
- Timezone mismatch between stored `due_at` and the value used for "now": pick the convention from `created_at` in step 2, funnel every write and every comparison through the same two helpers, and add the non-UTC-offset test so a naive/aware mix fails loudly instead of silently shifting results by the local offset.
- SQLite stores datetimes as strings and compares lexicographically: verify the column type matches `created_at` exactly so the existing ISO format is preserved and `<` still orders correctly; a mismatched type would make comparisons wrong only for some values.
- PATCH cannot currently distinguish omitted from explicit-null: the `exclude_unset` switch in step 7 changes behavior for `title` and `done` too, so run the full existing suite after that edit and keep the "PATCH title only" test as the guard.
- The test suite creates tables from the models and never runs migrations, so a broken 0002 would ship green: manually run `alembic upgrade head` then `alembic downgrade -1` against a copy of a populated `todo.db` before merging.
- Existing production rows get NULL `due_at`, and NULL comparisons in SQL are never true: the explicit `due_at IS NOT NULL` in `_overdue_clause()` is required for the `overdue=false` branch (`NOT (NULL < now)` is NULL, not true) — the "excludes null due_at" and "overdue=false complement" tests together cover this.
- Adding `due_at` to `TodoOut` is a response-shape change for any existing client: it is additive and nullable so it should be safe, but confirm no client does strict schema validation before deploying.
- `overdue=false` semantics are a judgment call (complement vs. "ignore the filter"): the plan defines it as the strict complement so `overdue=true` and `overdue=false` partition the collection; if the product wants otherwise, change step 9 and the complement test together.
