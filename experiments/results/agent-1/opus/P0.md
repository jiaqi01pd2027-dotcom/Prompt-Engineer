## Two decisions to make first

**`date` or `datetime`?** A `date` column ("due Sept 12") sidesteps timezones entirely and is what most todo apps actually want. A `datetime` ("due at 5pm") is more expressive but drags in the whole tz problem below. This is painful to change later once clients depend on the format, so pick deliberately.

**Nullable.** It has to be nullable — existing rows have no due date, and "no due date" is a legitimate state, not a missing value. This also makes the migration trivial on SQLite.

## The changes, file by file

**app/models.py** — add `due_at: Mapped[datetime | None] = mapped_column(DateTime, nullable=True, index=True)`. Follow whatever convention `created_at` already uses. Note that `DateTime(timezone=True)` is a **no-op on SQLite**: SQLAlchemy stores the string without an offset and hands you back a naive datetime. Your `created_at` already lives with this, so match it rather than inventing a second convention in the same table.

**app/schemas.py** — `due_at: datetime | None = None` on `TodoCreate`, `TodoUpdate`, and `TodoOut`. Add a field validator that normalizes to UTC and strips tzinfo before it reaches the DB. Without it, a client sending `2026-09-12T17:00:00-04:00` gives you an aware datetime that will `TypeError` the moment you compare it against a naive value read back from SQLite. Also decide what a naive input means — either assume UTC or reject it outright; silently guessing is the bug you'll be debugging in three months.

**app/routes.py** — two things:

1. *Clearing a due date via PATCH.* With `due_at: datetime | None = None`, "omitted" and "explicitly `null`" are the same value. Check what your patch handler does today — if it's `model_dump(exclude_none=True)` or `if data.title is not None:`, clearing is impossible. It needs `model_dump(exclude_unset=True)`, which uses Pydantic's `model_fields_set` to tell the two apart. This is the single most likely thing to get quietly wrong.
2. *Filtering and sorting.* Add query params alongside the existing `done` — `due_before: datetime | None`, and optionally `overdue: bool`. If you sort by due date, SQLite orders NULLs **first** ascending, so undated todos float to the top of the list, which is backwards. Use `order_by(Todo.due_at.is_(None), Todo.due_at)` to push them to the end.

**alembic/versions/0002_add_due_at.py** — `op.add_column` with `nullable=True`, plus `op.create_index` to mirror the model, and a `drop_index`/`drop_column` downgrade. Adding a nullable column works fine on SQLite; if you ever need a NOT NULL column or a constraint change, SQLite can't ALTER for that and you'd need `batch_alter_table` with `render_as_batch=True` in `env.py`, which recreates the table.

**Watch this**, given how your repo is set up: tests build the schema from the models, production builds it from migrations. The two are only equal because someone keeps them equal by hand. If you add the index to `models.py` and forget it in `0002`, every test passes and production silently runs without the index. Same for any constraint or default. Worth a `--autogenerate` diff check as a habit.

**tests/test_todos.py** — the 12 existing tests stay green *unless* any of them assert exact response equality (`assert r.json() == {...}`), which the new `TodoOut` field will break; grep for that first. New cases worth having: create with and without a due date, PATCH to set one, **PATCH with explicit `null` to clear one** (this is the test that catches the `exclude_unset` bug), filtering by `due_before`, sort ordering with undated todos mixed in, and rejection of a malformed or naive datetime.

One thing I'd *not* add: validation rejecting past due dates. Backfilling an already-overdue todo is normal, and "overdue" is a read-time question, not a write-time constraint.
