**Approach.** A single verbose regex encodes the grammar as two mutually exclusive branches — the week form `PnW` and the calendar/clock form `P[nY][nM][nD][T[nH][nM][nS]]` — with the fraction allowed only on the seconds field. Everything else is arithmetic over the matched groups.

Two things the regex alone can't reject, handled after the match:
- `"P"` (and `"PT"`) match the all-optional branch with every group `None`, so an explicit check raises `ValueError`.
- `"P1DT"` — a `T` with no time components — needs its own check, since making the time block non-empty in the pattern would complicate the branch.

The anchor is `\Z`, not `$`. `$` matches before a trailing newline, so `"P1Y\n"` parsed successfully until I caught it in testing — that was the one bug the test suite surfaced.

**Return type.** `int` when the duration is a whole number of seconds, `float` otherwise, per the `float | int` signature: `parse_iso_duration("PT2.0S")` returns `2`, `parse_iso_duration("PT1.5S")` returns `1.5`.

**Beyond the spec.** Comma as the decimal separator (`"PT1,5S"`) is accepted — ISO 8601 permits it, and it's the preferred form in the standard. A non-`str` argument raises `TypeError` rather than `ValueError`, since that's a caller mistake rather than a malformed duration. Say the word if you'd rather have either one tightened.
