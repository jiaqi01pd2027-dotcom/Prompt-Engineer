**The function** (stdlib only, single validating regex):

```python
_DURATION_RE = re.compile(
    r"""
    \A P
    (?:
        (?P<weeks>[0-9]+) W
      |
        (?= [0-9] | T[0-9] )
        (?: (?P<years>[0-9]+)   Y )?
        (?: (?P<months>[0-9]+)  M )?
        (?: (?P<days>[0-9]+)    D )?
        (?:
            T (?= [0-9] )
            (?: (?P<hours>[0-9]+)   H )?
            (?: (?P<minutes>[0-9]+) M )?
            (?: (?P<seconds>[0-9]+ (?: \. [0-9]+ )? ) S )?
        )?
    )
    \Z
    """,
    re.VERBOSE,
)

def parse_iso_duration(s: str) -> float | int:
    if not isinstance(s, str):
        raise TypeError(f"expected a str, got {type(s).__name__}")
    match = _DURATION_RE.match(s)
    if match is None:
        raise ValueError(f"invalid ISO-8601 duration: {s!r}")
    total: float | int = 0
    for name, unit_seconds in _UNIT_SECONDS.items():   # years/months/weeks/days/hours/minutes
        value = match.group(name)
        if value is not None:
            total += int(value) * unit_seconds
    seconds = match.group("seconds")
    if seconds is not None:
        total += float(seconds) if "." in seconds else int(seconds)
    return total
```

**Design points worth knowing**
- Validation is entirely structural — anything the pattern doesn't describe raises `ValueError`, so no separate check list can drift out of sync. The two lookaheads are what reject bare `"P"`, `"PT"`, and `"P1DT"`.
- `int` is returned unless the string carries a fractional-seconds field; `"PT1.5S"` → `1.5`, `"PT36H"` → `129600` as an `int`. `"PT0.0S"` returns `0.0` (float), following the syntax rather than the value.
- `[0-9]` instead of `\d` so non-ASCII digits (`"P١D"`) are rejected — `int()` would otherwise accept them. `\A`/`\Z` instead of `^`/`$` because Python's `$` also matches before a trailing newline, which would have let `"P1D\n"` through.
- Weeks are exclusive of all other components (`"P2W3D"`, `"P2WT1H"` raise), matching ISO 8601.
- Comma as a decimal separator (`"PT1,5S"`) is rejected. ISO 8601 permits it, but your spec listed unknown characters as invalid and used `.` throughout — flag it if you'd rather accept both.
- Non-`str` input raises `TypeError`, not `ValueError`.
