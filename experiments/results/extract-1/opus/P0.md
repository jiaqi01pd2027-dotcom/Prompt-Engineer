**TICKET-1 — Duplicate subscription charge: two $29 charges on same billing date**
- Type: Bug · Area: Billing/Payments · Severity: P1 (money out of a customer's account)
- Description: Customer was charged twice for the same subscription period. Card statement shows two $29 charges dated the 3rd of this month.
- Repro: Unknown — reported from statement, not reproduced.
- Expected: One charge per subscription per billing period. Actual: Two.
- First actions: pull the customer's subscription + invoice records for the 3rd; check whether two subscription objects exist or one subscription produced two payment intents; check for a retry-after-timeout path in the billing job (a webhook timeout that got retried is the usual cause); check whether other customers were double-charged on the same date (scope check — if yes, escalate to P0).
- Resolution must include: refund of the duplicate charge and confirmation to the customer.
- Missing info: customer/account ID, last 4 of card, exact timestamps of both charges.

**TICKET-2 — Google SSO login fails, redirects back to login page**
- Type: Bug · Area: Auth/SSO · Severity: P1 (blocks account access)
- Description: "Sign in with Google" hangs briefly, then returns the user to the login screen with no error. Reported as happening every time.
- Repro (to confirm): 1. Go to login page. 2. Click Sign in with Google. 3. Complete Google consent. 4. Land back on login page, not signed in.
- Expected: Authenticated session, redirect to dashboard. Actual: Silent failure back to login.
- First actions: check OAuth callback logs for this user's attempts; verify redirect URI allowlist matches the environment the user is on; check session-cookie attributes (SameSite/Secure/domain) — a silent bounce back to login is usually the session cookie not being set on the callback; check whether the Google account's email collides with an existing password-based account.
- Note: user gets no error message at all — even if the root cause is a data conflict, the silent failure is a separate defect worth its own fix.
- Missing info: browser + version, OS, whether it ever worked, whether other SSO providers work.

**TICKET-3 — PDF export truncates the last column of tables**
- Type: Bug · Area: Export/PDF rendering · Severity: P2
- Description: Tables exported to PDF lose the rightmost column. Customer reports this started after the release last week — likely a regression.
- Repro (to confirm): 1. Create/open a document containing a wide table. 2. Export to PDF. 3. Last column is clipped at the page edge.
- Expected: Full table fits the page (scaled, wrapped, or paginated). Actual: Last column cut off.
- First actions: bisect against last week's release — diff changes to the PDF renderer, page margins/paper size, and any table layout/column-width logic; determine the column-count or total-width threshold at which clipping begins.
- Missing info: column count and page size (A4 vs Letter) in the failing document; a sample export.

**TICKET-4 — iOS: bottom navigation bar overlaps Save button, blocking saves**
- Type: Bug · Area: Mobile/iOS UI · Severity: P1 (blocks a core action)
- Description: On iPhone, the bottom nav bar sits on top of the Save button, making it untappable. User cannot save at all.
- Repro (to confirm): 1. Open the app on iPhone. 2. Navigate to a screen with a Save button at the bottom. 3. Save button is behind the nav bar.
- Expected: Save reachable; content inset above the nav bar and home indicator. Actual: Covered, no way to save.
- First actions: check safe-area inset handling and bottom padding on the affected screen(s); check whether the nav bar is fixed-position over scroll content without a matching content inset; identify which screens are affected (may be more than the one reported).
- Missing info: iPhone model and iOS version, app version, which screen(s), native app vs mobile web.

**TICKET-5 — Repeat email notifications for already-read comments**
- Type: Bug · Area: Notifications/Email · Severity: P2 (high annoyance, churn/spam-complaint risk)
- Description: User receives repeated email notifications (~5/day) for comments they have already read.
- Expected: One notification per comment event; suppressed once the comment is read in-app. Actual: Same comments re-notified repeatedly.
- First actions: check whether the notification job marks items as sent (idempotency key / sent-at flag) or re-queries unsent-by-time; check whether in-app read state feeds back into email suppression at all — likely the read receipt and the email digest use separate state; check for a digest job running on a schedule that re-includes the same window.
- Consider alongside fix: notification frequency controls / digest batching, and an unsubscribe path so users can self-mitigate.
- Missing info: whether the emails are individual notifications or a digest, account ID, sample email headers/timestamps.

**TICKET-6 — Dashboard load time exceeds 20s at 100+ projects**
- Type: Bug / Performance · Area: Dashboard · Severity: P1 (product unusable for the customer's power users)
- Description: Dashboard takes 20+ seconds to load for an account with more than a hundred projects. Degradation correlates with project count.
- Expected: Dashboard loads in under ~2s regardless of project count. Actual: 20s+ at 100+ projects.
- First actions: profile the dashboard request for a large account; look for N+1 queries (per-project stats/permissions/last-activity lookups are the usual culprit) and for missing indexes on the project list query; check whether all projects are fetched and rendered rather than paginated.
- Likely fixes to evaluate: batch/aggregate per-project data into one query, paginate or virtualize the project list, cache computed per-project summaries.
- Add: a regression test or benchmark at 100/500/1000 projects so this does not silently return.
- Missing info: account ID and exact project count, whether load time grows linearly, and whether it is server response time or client render time (needs a HAR or trace).
