## Bug 1: `tag_records` — mutable default argument accumulates across calls

`tags=[]` is evaluated once, when the function is defined, so every call that omits `tags` shares the same list object. Each call then does `tags.append("processed")` on that shared list, so the second call sees `["processed", "processed"]`, the third `["processed", "processed", "processed"]`, and so on. That is exactly the "records processed later in a batch pick up duplicate 'processed' tags" report. The same line also mutates any list a caller explicitly passes in, which is a side effect they would not expect.

Corrected:

```python
def tag_records(records, tags=None):
    """Attach `tags` plus a 'processed' marker to every record."""
    tags = list(tags) if tags else []
    tags.append("processed")
    return [dict(record, tags=list(tags)) for record in records]
```

`None` as the default means a fresh list is built on every call, and copying with `list(tags)` means a caller-supplied list is never modified. Output now: `[{'id': 1, 'tags': ['processed']}]` then `[{'id': 2, 'tags': ['processed']}]`.

## Bug 2: `moving_average` — off-by-one in the loop bound

`range(len(values) - window)` stops one window short. For `n` values and window `w` there are `n - w + 1` full slices (the last one starts at index `n - w`), but `range(n - w)` excludes that final start index. With `[1, 2, 3, 4]` and window 2, `range(2)` yields starts 0 and 1 only, producing `[1.5, 2.5]` and dropping the `[3, 4]` slice, which is why the analyst gets two values instead of three.

Corrected:

```python
def moving_average(values, window):
    """Return the average of every consecutive `window`-sized slice."""
    averages = []
    for start in range(len(values) - window + 1):
        chunk = values[start:start + window]
        averages.append(sum(chunk) / window)
    return averages
```

Output now: `[1.5, 2.5, 3.5]`. When `window` exceeds the list length the range is empty and it still returns `[]`, so no new edge case is introduced.

## Not a bug: `number_lines`

`enumerate(lines, start=1)` already yields 1-based numbers, so `["alpha", "beta"]` gives `['1: alpha', '2: beta']`, matching the 1-based diff viewer. The background note about 1-based numbering is consistent with the current code, so it stays as is.
